# Журнал архитектурных решений

Формат записи: контекст → решение → причины → последствия → статус.
Статусы: `Proposed` (предложено, ждёт независимой проверки), `Accepted`
(проверено и принято), `Superseded` (заменено другим ADR), `Rejected`.

Решение, влияющее на криптографию, формат протокола или границы модулей,
переходит в `Accepted` только после независимой проверки (см. `AGENT_TASKS.md`).
Менять общую архитектуру без записи здесь нельзя.

## ADR-0001. Размещение проекта в каталоге `phantom/` репозитория NinnikuNPV

- **Дата:** 2026-11-10. **Статус:** Accepted (обратимо).
- **Контекст.** Рабочая сессия имеет доступ к одному репозиторию. Он содержит
  другой проект — панель NinnikuNPV на Python.
- **Решение.** Все файлы PHANTOM лежат в `phantom/`. Каталог не импортирует код
  панели и не меняет её файлы, сборку и CI.
- **Причины.** Единственное доступное место для сохранения работы; контейнер
  сессии эфемерный. Изоляция в одном каталоге позволяет вынести проект в
  отдельный репозиторий без правок содержимого.
- **Последствия.** Когда появится код на Rust, CI панели (`make check`) его не
  проверяет: нужен отдельный workflow с фильтром по `phantom/**` (этап 8).
  Перенос в отдельный репозиторий — по решению владельца.

## ADR-0002. Правила доказательности

- **Дата:** 2026-11-10. **Статус:** Accepted.
- **Контекст.** Задание требует не выдавать предположения за факты и не
  объявлять показатели достигнутыми без измерений.
- **Решение.**
  1. В исследовательских документах утверждения размечаются метками
     **[Факт]**, **[Вывод]**, **[Предположение]**, **[Не проверено]**.
  2. Архитектурное решение может опираться только на **[Факт]** и на явно
     названные **[Вывод]**; опора на **[Предположение]** записывается в ADR
     как риск.
  3. Чужие измерения производительности не переносятся на PHANTOM. Свои
     показатели появляются только после этапа 12 вместе с методикой и сырыми
     данными.
  4. Слова «проверено» и «протестировано» используются только для реально
     выполненных проверок; иначе пишется, что не проверено и почему.
- **Последствия.** Документы длиннее, зато каждое решение прослеживается до
  источника.

## ADR-0003. Криптографический слой — только TLS 1.3

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Контекст.** Потоки исследования разошлись: R1 рекомендовал ядро по образцу
  WireGuard (Noise), R4 — TLS 1.3 как единственный слой. Сравнение —
  `docs/research/07-comparative-report.md`, раздел 4.
- **Решение.** Канал защищает только TLS 1.3: в QUIC и поверх TCP. Собственного
  рукопожатия, собственного record layer, прямых вызовов AEAD и KDF нет.
- **Причины.** Требование задания не комбинировать примитивы самостоятельно;
  anti-replay, обновление ключей, согласование версий и защита от понижения —
  часть протокола; единственный стандартизованный и реализованный путь к
  post-quantum; один слой на оба транспорта; формальный анализ TLS 1.3.
- **Последствия.** Большой объём доверенного кода, включая C и ассемблер в
  AWS-LC; аудит `rustls` — 2020 год, аудит `quinn` не найден; ожидаемая
  производительность ниже WireGuard; сервер отвечает на рукопожатие любому
  клиенту, то есть обнаруживается зондированием.
- **Отвергнуто.** Собственный протокол на Noise; WireGuard без изменений (нет
  TCP-режима и стандартного PQ); двойной слой TLS + Noise (нет недоверенного
  терминатора TLS в модели угроз).

## ADR-0004. Профиль TLS

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** Только TLS 1.3; единственная группа `X25519MLKEM768`; 0-RTT и
  resumption выключены; провайдер `aws-lc-rs`; одна функция сборки конфигурации
  для обоих транспортов; время жизни соединения ограничено, пересоединение по
  схеме «сначала новое, потом закрыть старое».
- **Причины.** Защита записанного трафика; отсутствие понижения до классической
  группы; forward secrecy. RUSTSEC-2026-0349 показал понижение до X25519 через
  состояние клиента, связанное с resumption: без resumption и с единственной
  группой этот класс ошибок недостижим.
- **Последствия.** Нет совместимости с пирами без этой группы (допустимо: обе
  стороны свои). Каждое соединение — полное рукопожатие с ClientHello большего
  размера. Feature `prefer-post-quantum` и список групп задаются явно и
  проверяются тестом.
- **Риск.** Аутентификация остаётся классической (Ed25519).

## ADR-0005. Идентичность — закреплённые ключи, взаимная аутентификация TLS

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** Сервер и клиент имеют ключи Ed25519. Клиент закрепляет SHA-256
  от SubjectPublicKeyInfo сервера; сервер хранит список отпечатков клиентов.
  Публичный WebPKI в MVP не используется. Паролей и bearer-токенов нет.
- **Причины.** Нет разбора чужих цепочек до аутентификации; аутентификация
  целиком внутри TLS; отзыв клиента — удаление отпечатка.
- **Последствия.** Распространение отпечатка сервера — вне протокола.
  Запрос клиентского сертификата виден зондирующему. Открыт выбор между
  самоподписанными сертификатами и raw public keys (RFC 7250).

## ADR-0006. Транспорты MVP: QUIC с DATAGRAM и TLS поверх TCP

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** T1 — QUIC (`quinn`): IP-пакеты в DATAGRAM, управление в потоке.
  T2 — TLS 1.3 поверх TCP на порту 443 с кадрами «тип, длина, данные».
  Общий интерфейс `Transport`/`Tunnel`. Congestion control штатный.
- **Причины.** DATAGRAM не даёт вложенной повторной передачи; TCP 443 нужен
  там, где UDP недоступен; оба транспорта используют один профиль TLS.
- **Последствия.** T2 — режим с деградацией (TCP поверх TCP). Собственный ALPN
  виден в ClientHello.
- **Отложено.** T3 — HTTP/3 с CONNECT-IP и RFC 9729 на собственном домене.

## ADR-0007. Сеанс — «ключ клиента → внутренний адрес»

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** Токенов сеанса нет. Смена транспорта или сети — новое полное
  рукопожатие; сервер переносит маршрут внутреннего адреса на новое
  аутентифицированное соединение. Внутренние адреса статичны. Проверка адреса
  источника по ключу (cryptokey routing).
- **Причины.** Перенос сеанса без собственной криптографии; соединения
  приложений переживают переключение.
- **Последствия.** Один ключ — одно устройство. Нужен лимит частоты смены
  активного соединения.

## ADR-0008. Сеть клиента: запрет по умолчанию на уровне firewall

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** Kill switch — правила nftables с запретом по умолчанию, policy
  routing с fwmark. Два состояния: `off` и `enforcing`. Правила переживают
  падение процесса. IPv6 либо в туннеле, либо запрещён. DNS только через
  туннель. Локальная сеть по умолчанию закрыта.
- **Причины.** Атаки на таблицу маршрутов (TunnelVision, TunnelCrack) не
  зависят от протокола; таблицы маршрутов недостаточно.
- **Последствия.** Нужны права `CAP_NET_ADMIN`; при сбое клиент остаётся без
  сети до явного отключения — это намеренно.

## ADR-0009. Выбор транспорта: гонка, память по сети, гистерезис

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** Автомат из `ARCHITECTURE.md` §7. Одна неудача не меняет
  состояние. Диагностика сообщает наблюдения, а не причины. Пробы — только к
  собственному серверу.
- **Причины.** Практика Chromium и curl; ложные срабатывания измерительных
  проектов (R5 §3).
- **Последствия.** Все числовые параметры — стартовые, уточняются измерениями.

## ADR-0010. Фиксированный MTU туннеля

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** MTU интерфейса TUN фиксирован и одинаков для обоих транспортов
  (исходное предложение — 1280). Путь, не пропускающий нужный размер
  датаграммы, делает T1 непригодным в этой сети. MSS clamping обязателен.
- **Причины.** DATAGRAM не фрагментируется; смена MTU при переключении
  транспорта рвёт соединения приложений.
- **Риск.** Требование RFC 9484 о 1280 байт для IPv6 по первичному тексту не
  сверено. Значение уточняется на этапе 6.

## ADR-0011. Стек: Rust, tokio, quinn, rustls с aws-lc-rs

- **Дата:** 2026-11-11. **Статус:** Proposed.
- **Решение.** По `docs/research/06-rust-stack.md`, раздел 4. Нижние границы
  версий: `rustls` ≥ 0.23.46, `quinn-proto` ≥ 0.11.18, `tokio` ≥ 1.53.3.
  `cargo-deny` и `cargo-audit` в CI; версии закреплены в `Cargo.lock`.
- **Последствия.** Код на C и ассемблере в доверенной базе; переход на
  `rustls` 0.24 впереди; `h3` для T3 пока экспериментален.

## ADR-0012. Отдельный репозиторий проекта

- **Дата:** 2026-11-12. **Статус:** Accepted (решение владельца). Заменяет ADR-0001.
- **Решение.** PROJECT PHANTOM ведётся в собственном Git-репозитории с
  независимой историей. История шести коммитов этапов 1–4 перенесена из
  каталога `phantom/` репозитория NinnikuNPV через `git subtree split`;
  содержимое после переноса сверено побайтно.
- **Ограничение.** У репозитория нет remote: публикация запрещена до
  разрешения владельца. Рабочая среда эфемерна, поэтому до появления
  собственного remote резервная копия хранится в ветке разработки NinnikuNPV:
  каталог `phantom/` (зеркало рабочего дерева) и файл
  `phantom/project-phantom.bundle` (полная история; восстановление:
  `git clone project-phantom.bundle project-phantom`).
- **Последствия.** Источник истины — отдельный репозиторий. Зеркало в
  NinnikuNPV удаляется только после того, как владелец подтвердит перенос и
  задаст постоянное место хранения.

## ADR-0013. Raw public keys вместо самоподписанных сертификатов

- **Дата:** 2026-11-14. **Статус:** Accepted (проект). Изменяет ADR-0005.
- **Решение.** Обе стороны аутентифицируются raw public keys по RFC 7250
  (Ed25519). Отпечаток — SHA-256 от DER SubjectPublicKeyInfo, запись
  `ed25519-spki-sha256:<64 hex>`. Отката к X.509 нет.
- **Причины.** Разбор X.509 уходит из пути до аутентификации; сертификат не
  несёт лишних полей; сообщение `Certificate` у всех клиентов одной длины.
  `rustls` 0.23.46 поддерживает RPK (проверено чтением исходников).
- **Риск.** Работа RPK через `quinn` выведена из кода, тестом не подтверждена.
  Это первый проверочный эксперимент этапа реализации; запасной вариант —
  самоподписанный сертификат с тем же отпечатком SPKI.
- **Последствие для совместимости.** Сторонние клиенты на Xray-core RPK не
  используют; режим совместимости возможен только через отдельный транспорт T3
  (`docs/architecture/CLIENT_COMPATIBILITY.md`).

## ADR-0014. Сторож `phantom-guard` и таблица nftables с владельцем

- **Дата:** 2026-11-14. **Статус:** Proposed. Изменяет ADR-0008.
- **Контекст.** Перепроверка признала исправление S-01 недостаточным (V-06).
- **Решение.** Привилегированный сторож `phantom-guard` без кода разбора сети
  владеет таблицами nftables (флаги `owner` и `persist`), хранит состояние
  kill switch и исполняет закрытый перечень операций. Демон туннеля
  `phantom-netd` работает без привилегий. Если ядро не поддерживает `persist`,
  сторож работает в запасном режиме и сообщает, что защита от `flush ruleset`
  недоступна.
- **Отвергнуто.** Только порядок unit-ов (окно остаётся); приложения в
  отдельном network namespace — как умолчание (ломает сетевую обвязку рабочей
  станции; оставлен как профиль после MVP); eBPF на cgroup (не покрывает
  транзит и мосты).
- **Почему Proposed.** Решение не перепроверено независимо; поведение флагов
  выведено из исходников ядра; минимальные версии ядра и `nft` не установлены;
  проверка возможна только на стенде с systemd. Это главный технический риск
  системной части.

## ADR-0015. Клиенты: собственный клиент на едином ядре; сторонние — только через T3

- **Дата:** 2026-11-14. **Статус:** Proposed (нужно согласование владельца).
- **Контекст.** INCY и Happ построены на Xray-core, код закрыт, механизмов
  подключения стороннего протокола нет.
- **Решение.** Основной путь — собственный клиент с единым ядром на Rust:
  Linux, затем Windows, Android, macOS и iOS. Совместимость с INCY и Happ
  рассматривается только как отдельный транспорт T3 (MASQUE CONNECT-IP,
  RFC 9484) после MVP и после эксперимента на реальных устройствах.
- **Последствия.** Режим совместимости слабее основного профиля (пароль вместо
  ключа, нет явной активации); включать его — решение владельца.

**Дополнение к ADR-0012 (2026-11-14).** Владелец создал репозиторий
`ninn1ku/project-phantom`; история отправлена в ветку `main`. Он является
постоянным местом хранения. Зеркало `phantom/` и bundle в репозитории NinnikuNPV
больше не обновляются и удаляются по команде владельца.
