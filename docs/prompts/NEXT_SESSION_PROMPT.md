# PROJECT PHANTOM — задание на архитектурную приёмку и подготовку MVP

Ты принимаешь PROJECT PHANTOM после исследовательской фазы и становишься
главным техническим архитектором проекта. Работай с максимальной глубиной
анализа.

Сначала изучи репозиторий и проверь результаты предыдущей фазы. Не переписывай
архитектуру без причины: меняй только то, что не выдерживает проверки, и
каждое изменение записывай в ADR.

## 2. Продукт

PROJECT PHANTOM — защищённая сетевая платформа с собственными сервером и
клиентом. Пользовательский сценарий:

1. Арендовать Linux-сервер и установить PHANTOM SERVER.
2. Создать устройство и получить его конфигурацию.
3. Импортировать конфигурацию в PHANTOM CLIENT.
4. Нажать Connect и пользоваться защищённым соединением.

Пользователь не разбирается в криптографии, MTU, маршрутах, DNS и транспортах.

Приоритеты: безопасность, надёжность, производительность, простота,
поддерживаемость, воспроизводимые тесты. Не жертвуй криптографической
безопасностью ради скорости и стабильностью ради красивых идей. Не добавляй
сложность без измеримой пользы.

Не обещай необнаружимость, невозможность блокировки или постоянную
доступность серверных адресов.

## 3. Главная практическая проблема

Владелец регулярно теряет доступ к зарубежным серверам и меняет их адреса.
Не делай вывод, что каждый отказ означает распознавание протокола. Причины
могут быть разными: блокировка адреса, подсети или ASN, ограничения
хостинг-провайдера, потеря маршрутизации, DNS, обычные сбои, ограничения
отдельных транспортов, ложные срабатывания фильтров.

Нужна **диагностическая система**, которая по измерениям указывает вероятную
причину и сообщает наблюдения, а не догадки. Основа уже есть:
`docs/research/08-availability-loss-causes.md`.

Исследование DPI и фильтрации используй для модели угроз, совместимости и
понимания сетевой среды. Не разрабатывай механизмы сокрытия трафика от
сетевых операторов и обхода их средств обнаружения. Резервирование серверов —
механизм отказоустойчивости, а не обещание обхода блокировок.

## 4. Порядок платформ и проверяемость

Владелец не может самостоятельно проводить технические тесты. Поэтому
порядок разработки определяется тем, где результат можно проверить
автоматически.

**Порядок:**

1. **Общее ядро и сервер на Linux.** Сервер всё равно работает на Linux
   (Ubuntu Server LTS, Debian Stable).
2. **Эталонный клиент для Linux** — консольный, без графического интерфейса.
   Он не является продуктом для владельца. Его назначение — сквозные
   автоматические тесты протокола, транспортов, восстановления и защиты от
   утечек в network namespaces, где всё можно проверить без людей.
3. **Клиент для Windows 10/11 x64** — первый продуктовый клиент с
   графическим интерфейсом. Он добавляет к общему ядру только платформенный
   слой: службу Windows, Wintun, Windows Filtering Platform, DNS, интерфейс.
4. Остальные платформы — после MVP.

**Где что проверяется** (зафиксируй в `ARCHITECTURE_REVIEW.md` и
`MVP_ACCEPTANCE_CRITERIA.md`):

| Среда | Что проверяется |
|---|---|
| Контейнер сессии (Linux, root, `CAP_NET_ADMIN`, `/dev/net/tun`, `nft`, network namespaces; нет systemd, `ip`, `tc`, netem, KVM) | Ядро, криптография, транспорты, сервер, эталонный клиент, утечки на Linux, fuzz, эмулятор потерь и MTU |
| GitHub Actions, Ubuntu | То же в чистой среде; systemd и порядок служб (без перезагрузки) |
| GitHub Actions, Windows | Сборка, установка службы, создание адаптера Wintun, установка и снятие фильтров WFP, утечки DNS и IPv6 на одной машине, падение и перезапуск службы |
| Компьютер владельца | Только финальная ручная проверка по короткому пошаговому чек-листу: установка, импорт, Connect, сон и пробуждение, переключение Wi-Fi и Ethernet, обновление приложения |

Требования:

- Всё, что можно проверить автоматически, проверяется автоматически.
- Ручные проверки владельца — короткий чек-лист без технических знаний.
  Сценарий, проверенный только чек-листом или не проверенный вовсе, явно
  помечается так в документах и отчётах.
- Минуты GitHub Actions ограничены, а Windows-задания расходуют их быстрее:
  длинные и нагрузочные тесты запускай не на каждый коммит.
- Измерения производительности в контейнере и на GitHub Actions не
  сравниваются с эталонами. Для них нужен отдельный стенд — опиши требования
  к нему и спроси владельца.

## 5. Сервер

Компоненты: `phantom-server`, `phantom-admin`, `phantom-config`,
`phantom-monitor`, `phantom-update`, `phantom-guard`.

Возможности: установка, первичная настройка, идентичность сервера, создание
устройств и их конфигураций, отзыв доступа, ротация ключей, контроль
состояния, мониторинг, обновление, удаление.

- Установщик идемпотентный: повторный запуск не повреждает конфигурацию.
- Секреты не попадают в журналы.
- Предусмотрено безопасное восстановление после сбоев.

## 6. Клиент для Windows

Предварительная структура: `phantom-ui`, `phantom-core`, `phantom-service`,
`phantom-network`, `phantom-guard`, `phantom-updater`.

Исследуй: Wintun, Windows Filtering Platform, Service Control Manager,
брандмауэр Windows, маршрутизацию, DNS, IPv4 и IPv6, безопасное
взаимодействие интерфейса с привилегированной службой.

Защиту от утечек на Windows проектируй отдельно — не переноси решения для
Linux (nftables, `phantom-guard` на Linux) механически. Сценарии: падение
клиента, перезапуск службы, смена интерфейса, переключение Wi-Fi и Ethernet,
выход из сна, потеря соединения с сервером, обновление приложения.

Интерфейс: статус, Connect/Disconnect, выбранный сервер, задержка, время
подключения, скорость, состояние защиты, понятные ошибки. Разделы: серверы,
конфигурации, устройства, диагностика, настройки, обновления. Простота важнее
количества параметров. Предложи технологию интерфейса с обоснованием.

## 7. Криптография

Проверь `docs/protocol-spec/CRYPTO_PROFILE.md` и связанные ADR против
реальных версий библиотек. Поддержка алгоритма библиотекой не доказывает
корректность архитектуры. Требования: стандартные алгоритмы, взаимная
аутентификация, защита от MITM, повторов и понижения параметров, управление
ключами, отзыв, ротация, хранение секретов (на Windows — отдельно).
Собственной криптографии нет.

## 8. Транспорт

Проверь QUIC и TCP-реализации с точки зрения производительности, потерь,
задержек, восстановления, памяти и сопровождения. Переключение транспорта не
должно нарушать идентичность клиента, сеанс, маршруты, ключи и порядок
сообщений. Резервный транспорт не считается работающим без интеграционных
тестов.

## 9. Инфраструктура

Несколько независимых серверов, мониторинг доступности, сетевые метрики,
диагностика причин отказа, резервные серверы, безопасное обновление списка
серверов, восстановление соединений, отсутствие единой точки отказа.
Отдельно — влияние адреса, подсети, ASN и хостинг-провайдера на доступность.

## 10. Конфигурации и устройства

Единый формат: подпись, целостность, версия, защита от отката, срок действия,
идентичность устройства, отзыв, безопасное обновление, несколько серверов.
У каждого устройства своя идентичность; общего секрета на все устройства нет.

## 11. Производительность

Реалистичные цели — только после измерений. Пропускная способность,
нагрузка на CPU, память, задержки, потери, время установления и
восстановления соединения, масштабирование числа клиентов. Сравнение с
подходящими реализациями (в первую очередь WireGuard) в одинаковых условиях.
Воспроизводимый набор бенчмарков. Не придумывай показатели.

## 12. Безопасность

Сохрани независимый аудит. Повторно проверь: исправленные High, переработанный
`phantom-guard`, 37 замечаний Medium, 19 разрешённых расхождений
спецификации, модель угроз, ADR, механизмы обновления, привилегированные
компоненты, межпроцессное взаимодействие. Не закрывай замечания без тестов.

## 13. Совместимость

Основной путь — собственный клиент. Совместимость с INCY, Happ и
MASQUE CONNECT-IP изучена в `docs/architecture/CLIENT_COMPATIBILITY.md`.
Не трать ресурсы на совместимость, которая ухудшает безопасность или
усложняет поддержку; уточняй у владельца.

## 14. План реализации

| Фаза | Содержание |

| 4 — Клиент для Windows | Служба, Wintun, WFP, ядро, импорт конфигурации, Connect/Disconnect, защита от утечек, интерфейс; тесты в GitHub Actions; чек-лист владельца |
| 5 — Надёжность | Восстановление, диагностика, резервирование, мониторинг |

## 15. Субагенты

Используй их для независимых направлений: криптография, сеть Windows,
серверная часть Linux, транспорт, аудит безопасности, производительность,
архитектура продукта. Сначала определяй зависимости, не запускай всё сразу.
Для критичных решений требуй независимой проверки. Выводы субагентов — не
результаты испытаний.
