# Архитектура PROJECT PHANTOM

**Версия:** 0.2 (черновик этапа 4, после ревью V1 и V2). **Дата:** 2026-11-11.
**Статус:** предложение. Замечания уровня High из `reviews/` исправлены автором; исправления независимо не перепроверены. Решения — ADR-0003…0010 в
`ARCHITECTURE_DECISIONS.md`. Кода нет; имена типов ниже — эскиз интерфейсов,
а не готовый API.

## 1. Принципы

1. **Нет своей криптографии.** Весь канал защищает TLS 1.3 из библиотеки.
   Проект не вызывает AEAD, KDF и обмен ключами напрямую.
2. **Стандартные протоколы на проводе.** QUIC и TLS поверх TCP без
   собственных заголовков снаружи шифрования.
3. **Запрет по умолчанию.** Любой сбой переводит клиент в состояние, где
   трафик не выходит мимо туннеля.
4. **Ядро не знает о транспорте.** Транспорт — заменяемый модуль с узким
   интерфейсом.
5. **Привилегии отдельно от разбора сети.** Код, читающий данные из сети,
   работает без прав на изменение маршрутов и firewall.
6. **Измеримость.** Каждое свойство из модели угроз имеет тест.

зависят от остальных crate проекта.

## 3. Криптография и идентичность

### 3.1. Профиль TLS

| Параметр | Значение | Зачем |
|---|---|---|
| Версия | только TLS 1.3 | Нет понижения до 1.2 |
| Группы обмена ключами | только `X25519MLKEM768` | Защита записанного трафика; нет понижения до классической группы |
| Cipher suites | по умолчанию библиотеки для TLS 1.3 | Выбор не делается проектом |
| 0-RTT | выключен на обеих сторонах | Early data воспроизводимы |
| Resumption | выключен: tickets не выдаются и не принимаются | Forward secrecy; каждое соединение — новый обмен; нет состояния, через которое возможно понижение |
| Провайдер | `aws-lc-rs` | Единственный провайдер `rustls` с этой группой |
| ALPN | T1: `phantom/1`; T2: `phantom/1` | Версия протокола согласуется штатно и защищена рукопожатием |
| Аутентификация сервера | Самоподписанный сертификат Ed25519; клиент сравнивает SHA-256 от SubjectPublicKeyInfo с закреплённым значением и проверяет подпись рукопожатия | Нет цепочек и внешних CA |
| Аутентификация клиента | Обязательный клиентский сертификат Ed25519; сервер ищет отпечаток ключа в списке разрешённых | Нет паролей и bearer-токенов |

Одна и та же конфигурация используется обоими транспортами. Она собирается
одной функцией в `phantom-crypto`; тесты проверяют согласованную версию,
группу и отказ при отклонении от профиля.

#### Проверка закреплённого ключа (нормативно)

Проверяющая сторона (клиент для сервера, сервер для клиента) выполняет все
шаги; отказ на любом — закрытие соединения:

1. Из сертификата конечной сущности извлекается SubjectPublicKeyInfo. Цепочка,
   имена, сроки и расширения не используются и не влияют на решение.
2. Алгоритм ключа — Ed25519; иной алгоритм отвергается.
3. SHA-256 от DER-кодировки SubjectPublicKeyInfo сравнивается с закреплённым
   значением (у клиента — до двух значений; у сервера — список разрешённых).
4. Подпись `CertificateVerify` проверяется этим ключом штатной функцией
   библиотеки. Собственный verifier **не может** возвращать успех для проверки
   подписи без вызова этой функции; допустимая схема подписи одна — Ed25519.
5. Сервер считает клиента аутентифицированным только после `Finished` клиента
   и до этого не отправляет данных приложения.

Обязательные тесты, в обе стороны: (а) чужой ключ отвергается; (б) **верный
сертификат при чужом приватном ключе отвергается** — этот тест ловит verifier,
пропускающий проверку подписи; (в) сертификат с ключом другого алгоритма
отвергается; (г) клиент без сертификата отвергается; (д) пир без ALPN или с
чужим ALPN отвергается в обоих транспортах.

Raw public keys (RFC 7250) рассматриваются как замена сертификатам на этапе
спецификации: они убирают разбор X.509, но их поддержку в `quinn` нужно
подтвердить.

### 3.2. Ключи

| Ключ | Где живёт | Срок | Ротация |
|---|---|---|---|
| Ключ идентичности сервера (Ed25519) | Файл с правами 0600; в systemd — `LoadCredential` | Долгий | Вручную; период перекрытия: клиент принимает до двух закреплённых ключей |
| Ключ идентичности клиента (Ed25519) | То же | Долгий | Вручную; сервер хранит список отпечатков; отзыв — удаление из списка |
| Ключ подписи конфигураций (Ed25519) | Вне сервера, у оператора | Долгий | Процедура — этап 13 |
| Сеансовые ключи TLS | Память, внутри `rustls` | Время жизни соединения | Key update средствами библиотеки; полное пересоединение по таймеру |

Проект не копирует сеансовые ключи в собственные буферы и не экспортирует их.

### 3.3. Время жизни соединения

Соединение живёт ограниченное время (параметр спецификации; исходное
предложение — порядка часа). По истечении клиент поднимает новое соединение,
проверяет его и только затем закрывает старое. Это даёт свежий обмен ключами
без разрыва туннеля.

## 4. Сеанс

Сеанс определяется парой «отпечаток ключа клиента → внутренний адрес». Отдельных
идентификаторов и токенов сеанса нет.

- Сервер держит таблицу `отпечаток → {внутренние адреса IPv4 и IPv6, активное
  соединение}`. Адреса назначаются статически в конфигурации сервера.
- Аутентифицированное соединение само по себе маршрут **не получает**. Оно
  становится активным только после управляющего сообщения клиента
  `Activate{seq}` и ответа сервера `Activated{seq}`. `seq` — монотонный
  64-битный счётчик клиента; сервер хранит последнее принятое значение для
  ключа и отвергает `seq` не больше него. Клиент хранит счётчик на диске и
  увеличивает его с запасом при запуске.
- Проигравшие в гонке транспортов соединения, фоновые пробы и соединение,
  поднятое для плановой замены, `Activate` не отправляют, пока клиент не решит
  переключиться. Поэтому сервер и клиент всегда согласны, какое соединение
  активно, а задержанное атакующим рукопожатие маршрут не уводит.
- После `Activated` прежнее активное соединение получает `Superseded` и
  закрывается после короткой паузы. Клиент шлёт пакеты в новое соединение
  только после `Activated`.
- Лимит частоты применяется к сообщениям `Activate`, а не к рукопожатиям, и
  не может запереть клиента: превышение задерживает активацию, но не
  блокирует её.
- Внутренние адреса не меняются при смене транспорта и сети, поэтому
  соединения приложений переживают переключение.
- Ключ на несколько устройств не поддерживается: два устройства с одним
  ключом будут вытеснять друг друга, это видно в журнале сервера.
- Сервер закрывает соединения отозванного ключа немедленно при перечитывании
  списка и сам ограничивает время жизни соединения, не полагаясь на клиента.
- Cryptokey routing: пакет из туннеля принимается, только если адрес источника
  принадлежит ключу этого соединения. Пакет в туннель отправляется по адресу
  назначения в активное соединение владельца адреса.

## 5. Транспорты

### 5.1. Интерфейс

```rust
// Эскиз. Точные сигнатуры — этап 8.
trait Transport {
    /// Установить аутентифицированное соединение или вернуть типизированную ошибку.
    async fn connect(&self, target: &ServerAddr, deadline: Instant)
        -> Result<Box<dyn Tunnel>, ConnectError>;
}

trait Tunnel {
    async fn send_packet(&self, packet: &[u8]) -> Result<(), SendError>;
    async fn recv_packet(&self, buf: &mut [u8]) -> Result<usize, RecvError>;
    async fn send_control(&self, msg: &ControlMessage) -> Result<(), SendError>;
    async fn recv_control(&self) -> Result<ControlMessage, RecvError>;
    fn max_packet_size(&self) -> usize;
    fn health(&self) -> TunnelHealth;   // наблюдения, без выводов о причинах
    async fn close(&self, reason: CloseReason);
}
```

`ConnectError` различает: тайм-аут без единого ответа, отказ в соединении,
сброс, ошибку TLS, ошибку аутентификации, несовпадение версии. Автомат выбора
использует эти типы, а не тексты ошибок.

### 5.2. T1 — QUIC

- Библиотека `quinn`. Один IP-пакет — один кадр DATAGRAM. Фрагментации нет:
  пакет больше `max_packet_size` отбрасывается с ICMP «packet too big» в
  сторону отправителя.
- Один двунаправленный поток для управляющих сообщений.
- Congestion control — штатный для библиотеки. Отключение и агрессивные
  контроллеры запрещены.
- Роуминг — штатная миграция соединения с проверкой пути.
- Retry включается сервером под нагрузкой.

### 5.3. T2 — TLS 1.3 поверх TCP

- `rustls` через `tokio-rustls`, порт 443.
- Один поток байтов. Кадр: `тип (1 байт) | длина (2 байта) | данные`. Типы:
  пакет, управление. Один IP-пакет — один кадр.
- Очередь на отправку ограничена и отбрасывает лишнее, чтобы внутренний TCP
  видел потери, а не растущую задержку. Параметры — по измерениям.
- Это режим совместимости с известной деградацией (TCP поверх TCP).

### 5.4. Управляющие сообщения

Общие для обоих транспортов; формат — этап 6. Набор для MVP:

| Сообщение | Направление | Назначение |
|---|---|---|
| `Hello` | клиент → сервер | Версия, запрошенные возможности |
| `Config` | сервер → клиент | Внутренние адреса, MTU, DNS, интервал keepalive, время жизни соединения |
| `Ping`, `Pong` | обе | Проверка живости и оценка RTT в T2 |
| `Activate`, `Activated` | клиент → сервер, сервер → клиент | Явный перенос маршрута на это соединение (§4) |
| `Superseded` | сервер → клиент | Соединение заменено более новым |
| `Close` | обе | Причина закрытия |

Все поля проверяются на границы; неизвестный тип — закрытие соединения.
Разборщики — цели fuzz-тестов.

### 5.5. T3 — HTTP/3 с CONNECT-IP (после MVP)

Собственный домен и сертификат WebPKI, ALPN `h3`, туннель по RFC 9484,
аутентификация по RFC 9729, для остальных клиентов — обычный сайт. В MVP не
входит: библиотека `h3` экспериментальная, поддержка CONNECT-IP в Rust не
подтверждена (`docs/research/06-rust-stack.md`). Интерфейс `Transport`
проектируется так, чтобы T3 добавлялся без изменения ядра.

## 6. Сеть

### 6.1. MTU

- MTU интерфейса TUN фиксирован и одинаков для обоих транспортов. Исходное
  предложение — 1280: минимум IPv6, запас на заголовки при внешнем MTU 1500.
- Для 1280 байт внутри DATAGRAM нужен UDP payload около 1310 байт — больше
  гарантированных QUIC 1200. Клиент проверяет это пробой при установлении T1.
  Если размер не проходит, T1 считается непригодным в этой сети и выбирается T2.
- MSS clamping для TCP SYN в обе стороны.
- Динамически MTU интерфейса не меняется.

### 6.2. Клиент: маршруты, kill switch, DNS

Схема — по образцу `wg-quick`: метка fwmark на собственных сокетах клиента,
отдельная таблица маршрутизации для остального трафика, правила nftables.

Правила kill switch (таблица nftables `inet phantom`, запрет по умолчанию):

| Разрешено | Условие |
|---|---|
| Весь трафик через интерфейс TUN | — |
| Трафик к адресам сервера на портах транспортов | Только с меткой клиента |
| Loopback | — |
| DHCP и обнаружение соседей | Минимум, нужный для работы сети |
| Локальная сеть | Только если включено в конфигурации; по умолчанию закрыто |
| Всё остальное, включая IPv6 и порт 53 мимо TUN | Запрещено |

Таблица выше описывает цепочку `output`. Дополнительно:

- **`forward`**: запрет по умолчанию. Трафик контейнеров, виртуальных машин и
  других network namespaces либо идёт через TUN, либо отбрасывается.
- **`input`**: пакеты на адрес туннеля, пришедшие не с интерфейса TUN,
  отбрасываются; с физических интерфейсов принимаются только ответы
  установленных соединений клиента с сервером и минимум DHCP и NDP.
- **Установленные соединения**: при переходе в `enforcing` записи conntrack,
  не относящиеся к TUN и к соединению с сервером, сбрасываются; правила не
  содержат общего «established, related — принять» для физических интерфейсов.

Жизненный цикл:

- Состояния kill switch: `off`, `enforcing`. Режима «разрешить, если туннель
  упал» нет. Состояние хранится на диске.
- `enforcing` включается при первом подключении и снимается **только** явной
  командой `disconnect`. Падение процесса, остановка службы и выключение
  системы правил не снимают.
- При загрузке системы отдельный unit без сетевого кода восстанавливает
  правила из сохранённого состояния до поднятия сетевых интерфейсов
  (`Before=network-pre.target`). Пока он не отработал, остаётся окно (RR15).
- Соответствие автомату §7: `Disconnected` означает `off` только после явного
  `disconnect`; до первого подключения система тоже в `off`. «Kill switch
  включён по умолчанию» (§9) означает: подключение всегда включает
  `enforcing`, отдельного флага «без kill switch» нет.
- Стороннее ПО с правами root может удалить таблицу (`nft flush ruleset`).
  Клиент следит за таблицей и восстанавливает её, но между удалением и
  восстановлением есть окно. Это остаточный риск, а не гарантия.
- DNS: адрес резолвера приходит в `Config`; назначается интерфейсу TUN через
  systemd-resolved; запросы к другим резолверам мимо TUN запрещены firewall.
- IPv6: либо внутри туннеля, либо запрещён. Конфигурация «IPv4 в туннеле,
  IPv6 напрямую» невозможна по построению.
- Адрес сервера задаётся в конфигурации IP-адресом. Имя допускается, но тогда
  его разрешение — видимый снаружи запрос до поднятия туннеля; это
  документируется.

### 6.3. Сервер

- TUN, пересылка, NAT для исходящего трафика — правилами nftables.
- Фильтр адресов источника (раздел 4).
- Между клиентами трафик по умолчанию запрещён.

### 6.4. Привилегии

Целевая схема: процесс с `CAP_NET_ADMIN` создаёт TUN, ставит маршруты и правила,
затем сбрасывает права; сетевой код работает без них. Выбор между одним
процессом со сбросом прав и отдельным helper — этап 8. Конфигурацию из сети
привилегированный код принимает только как типизированные значения, прошедшие
проверку (адреса, префиксы, числа), и никогда как строки для командной оболочки.

## 7. Автомат соединения клиента

```
Disconnected -> Probing -> Connecting -> Connected -> Degraded -> Reconnecting
      ^                                     |             |            |
      +----------- Blocked <----------------+-------------+------------+
```

| Состояние | Трафик пользователя | Переход |
|---|---|---|
| `Disconnected` | Kill switch `off`; обычная сеть | Команда «подключить» |
| `Probing` | Запрещён | Проверка captive portal и локальной сети |
| `Connecting` | Запрещён | Гонка транспортов |
| `Connected` | Через туннель | Потеря keepalive, ошибка транспорта |
| `Degraded` | Через туннель | Серия потерь; фоновая проверка другого транспорта |
| `Reconnecting` | Запрещён (пакеты отбрасываются) | Попытки с backoff |
| `Blocked` | Запрещён | Все транспорты и адреса исчерпаны; ожидание с backoff или смена сети |

### 7.1. Выбор транспорта

Числа — стартовые значения для измерений, не нормы.

1. Старт T1. T2 стартует с задержкой: 250 мс при неизвестном RTT, иначе около
   удвоенного RTT, не больше 3 с. Побеждает первое **аутентифицированное**
   соединение.
2. «UDP недоступен» означает отсутствие любого ответа. Если пришёл хотя бы
   один корректный пакет QUIC, T1 получает дополнительное время.
3. Результат запоминается по сети (интерфейс и шлюз). «T1 не работает» — на
   5 минут с удвоением до потолка в часы. При смене сети память не применяется.
4. Потеря связи в середине сеанса: серия тайм-аутов без подтверждений. Сначала
   проба меньшим пакетом, чтобы отличить проблему MTU, затем переключение.
5. Возврат с T2 на T1 — только после нескольких успешных фоновых проб подряд
   и минимального времени на T2. Новый транспорт поднимается и проверяется до
   снятия старого.
6. Лимит переключений в единицу времени. При превышении клиент остаётся на T2
   до смены сети.
7. Одна неудачная попытка не меняет ни память по сети, ни состояние.
8. Переход на следующий адрес сервера — только когда на текущем не работает ни
   один транспорт. Запасные адреса не проверяются, пока основной работает.

### 7.2. Диагностика

Клиент сообщает наблюдения, а не причины: «от сервера нет ответа по UDP за N
секунд; TCP 443 соединяется; рукопожатие TLS завершено». Формулировка
«заблокировано» не используется. Пробы идут только к собственному серверу;
сторонние сервисы для проверок не применяются.

## 8. Сервер: ресурсы и злоупотребления

- Лимиты: одновременные рукопожатия, соединения на адрес источника, общее число
  соединений, скорость на клиента (опционально).
- До аутентификации не выделяются ресурсы туннеля. Тайм-аут рукопожатия короткий.
- Журналы: события подключения и отключения с отпечатком ключа клиента и
  причиной; без адресов назначения, без содержимого, без внутренних потоков.
  Адрес клиента — на уровне отладки, по умолчанию выключен.
- Секреты в журналы не попадают: типы секретов не реализуют `Debug` и `Display`.

## 9. Конфигурация и обновления

- Формат TOML. Неизвестные поля — ошибка. Приватные ключи лежат в отдельных
  файлах; в основном файле только пути.
- Проверка до применения: `phantom-client check`, `phantom-server check`.
- Обновление конфигурации — подписанный конверт. Подписываются, с
  фиксированной строкой-префиксом назначения: формат, **номер версии**
  (монотонный), время создания, **срок действия**, **адресат** (отпечаток
  ключа узла), **минимально допустимая версия** и байты конфигурации.
- Якорь доверия — публичный ключ оператора, установленный при первичной
  настройке вне канала обновлений. Режим проверки Ed25519 — строгий.
- Узел хранит наибольшую принятую версию и отвергает: неверную подпись, чужого
  адресата, истёкший срок, версию не выше принятой, версию ниже минимально
  допустимой. Повтор старой подписанной конфигурации поэтому не проходит.
- Откат — только к непосредственно предыдущей версии, только если она не ниже
  минимально допустимой из текущей, и только по команде оператора на узле.
  Автоматического отката нет: при ошибке запуска с новой конфигурацией узел
  остаётся в состоянии «запрещено» и сообщает об ошибке. Изменения, связанные
  с отзывом ключей, оператор выпускает с повышением минимально допустимой версии.
- Сообщение `Config` от сервера не может ослабить локальную политику: оно
  задаёт только внутренние адреса, MTU не выше локального предела и DNS из
  диапазона туннеля; всё остальное определяется подписанной конфигурацией.
- Значения по умолчанию безопасны: kill switch включён, доступ к локальной сети
  закрыт, журналирование адресов выключено.

## 11. Тестовый стенд

- Сквозные тесты — в network namespaces с veth-парами: клиент, «сеть», сервер,
  «интернет».
- В контейнере разработки доступны root, `CAP_NET_ADMIN`, `/dev/net/tun`,
  `nft`, `unshare`. Отсутствуют `ip`, `tc`, `ping`, `tcpdump`, `resolvectl`;
  модуль netem в ядре выключен; PID 1 — не systemd.
- Следствия: потери, задержка и ограничение MTU эмулируются userspace-прокси
  между namespaces; настройка сети в тестах идёт через netlink из кода;
  интеграция с systemd-resolved и sandbox unit-файла в этой среде не проверяются
  и требуют отдельного стенда.
- Сравнение с WireGuard и измерения производительности требуют отдельного
  оборудования (этап 12).
