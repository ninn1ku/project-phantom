# Архитектура PROJECT PHANTOM

**Версия:** 0.3. **Дата:** 2026-11-14.
**Статус:** сведено с детальными спецификациями; независимо не перепроверено; кода нет.
Документ — нормативное резюме. Полные правила, обоснования, источники и тесты лежат в детальных документах; при
расхождении побеждают они, а расхождения между ними вынесены в §14. Решения — ADR-0003…0015 в
`ARCHITECTURE_DECISIONS.md`. Имена типов — эскиз интерфейсов, а не API. Числа с пометкой «⟂» — стартовые значения,
уточняются измерением (этап 12).

Ссылки: **CP** — `docs/protocol-spec/CRYPTO_PROFILE.md` (требования `CP-nn`); **TS** —
`docs/protocol-spec/TRANSPORT_AND_SESSION.md`; **SYS** — `docs/architecture/SYSTEM_AND_LEAK_PROTECTION.md`; **RV** —
`docs/architecture/reviews/REVERIFY_HIGH.md` (V-01…V-09); **CC** — `docs/architecture/CLIENT_COMPATIBILITY.md`;
**TST** — `docs/testing/TEST_STRATEGY.md`.

## 1. Принципы

1. **Нет своих примитивов, KDF и рукопожатия.** Канал защищает TLS 1.3 (RFC 9846) из библиотеки. Собственный код
   безопасности остаётся и требует проверки: verifier закреплённых ключей, автомат сеанса (`Activate`), управляющие
   сообщения, подпись конфигураций (CP §3.5).
2. **Стандартные протоколы на проводе.** QUIC v1 и TLS 1.3 поверх TCP без собственных заголовков снаружи шифрования.
   Необнаружимость не обещается (RR1).
3. **Запрет по умолчанию.** Любой сбой оставляет хост в состоянии, где трафик не выходит мимо туннеля.
4. **Ядро не знает о транспорте и платформе.** Транспорт и системная часть — заменяемые модули за узкими trait-ами
   (SYS §6).
5. **Привилегии отдельно от разбора сети.** Разбор недоверенных данных — в непривилегированном `phantom-netd`;
   привилегированный `phantom-guard` не читает сеть и исполняет закрытый перечень операций (SYS §2.5).
6. **Измеримость.** Каждое свойство модели угроз имеет тест на указанном стенде; отрицательный тест утечки без
   положительного контроля не засчитывается (TST §2).

## 2. Компоненты и crate-ы

```
 клиент: CLI --unix--> phantom-guard (CAP_NET_ADMIN: nftables owner+persist, TUN fd, SO_MARK, маршруты, DNS)
                            ^ закрытый перечень операций (guard.sock)
         phantom-netd (без capabilities): phantom-core -> phantom-transport (T1, T2) -> phantom-crypto
                                                              ||  сеть
 сервер: phantom-server: phantom-core (сеансы, last_seq, лимиты) -> phantom-transport -> phantom-crypto
         phantom-network (TUN, NAT, фильтр назначения);  общий phantom-config (конверт, подпись, state)
```

| Crate / процесс | Ответственность | Не делает |
|---|---|---|
| `phantom-crypto` | Одна функция сборки `CryptoProvider` и конфигураций `rustls` для T1 и T2; RPK-verifier; `identity(spki) -> [u8; 32]`; типы секретов без `Debug`/`Display` (CP §3.4, §4) | Не реализует алгоритмы; не знает о сети |
| `phantom-transport` | `Transport`/`Tunnel`, T1 (`quinn`), T2 (`tokio-rustls`), кодек TLV, SizeProbe (TS §4–§5) | Не выбирает транспорт; не трогает TUN |
| `phantom-core` | Автомат клиента, сеанс и активация, keepalive, память по сети, таблица сеансов сервера (TS §5.4–§8) | Не делает системных вызовов для маршрутов и firewall |
| `phantom-network` | Trait-ы платформы: `TunDevice`, `KillSwitch`, `ProtectedSocketFactory`, `RouteManager`, `DnsConfigurator`, `NetworkMonitor`, `ControlChannel`, `PrivilegeBoundary` (SYS §6) | Не разбирает данные из недоверенной сети |
| `phantom-guard` (новый) | Владеет таблицами `inet phantom` и `bridge phantom_l2` (флаги `owner`+`persist`), хранит состояние kill switch, создаёт TUN и сокеты с меткой, ставит маршруты и DNS, слушает `NFNLGRP_NFTABLES` (SYS §1.3–§1.4, §2.5) | Не открывает сетевых сокетов, кроме netlink и unix; не разбирает трафик |
| `phantom-config` | Конверт, подпись Ed25519 до разбора TOML, хранение `state`, откат, смена якоря (SYS §1.8) | Не хранит секреты в общем файле |
| `phantom-client`, `phantom-server` | Сборка, CLI, unit-ы systemd, диагностика; клиентский демон — `phantom-netd` | Не содержат логики протокола |

Зависимости направлены вниз; `phantom-crypto` и `phantom-config` не зависят от остальных crate-ов проекта;
`phantom-core` и `phantom-transport` зависят только от trait-ов `phantom-network` (SYS §6). Ядро проектируется как
библиотека с FFI и интерфейсом «пакеты внутрь/наружу» без собственного TUN — для будущих клиентов Windows, Android,
macOS/iOS (CC §7–§8, ADR-0015). Целевая платформа MVP — Linux.

## 3. Криптография и идентичность

### 3.1. Профиль TLS (CP §4, ADR-0004)

| Параметр | Значение | Требование |
|---|---|---|
| Версия | только TLS 1.3; feature `tls12` выключена | CP-01, CP-02 |
| Группа | только `X25519MLKEM768` на обеих сторонах; ML-KEM-1024 и «чистый» ML-KEM отвергнуты | CP-03 |
| Cipher suites | три TLS 1.3 suite `aws-lc-rs`; `TLS13_AES_128_GCM_SHA256` обязателен (нужен `quinn` для Initial) | CP-04 |
| Подпись | только Ed25519; набор `WebPkiSupportedAlgorithms` содержит только `ED25519` — `supported_verify_schemes()` лишь объявляет схемы (V-01) | CP-05 |
| Early data, 0.5-RTT | выключены; `send_half_rtt_data = false`; `Connecting::into_0rtt()` не вызывается нигде (проверка в CI) | CP-06, CP-07, CP-14, CP-15 |
| Resumption | нет: `Resumption::disabled()`, tickets 0, `NoServerSessionStorage` | CP-08…CP-10 |
| Сжатие сертификатов | нет; features `brotli`, `zlib` не включаются | CP-17 |
| HRR | сервер не отправляет; клиент отвергает HRR с предложенной группой и без изменений | CP-18 |
| Экспорт секретов | нет (`NoKeyLog`, `enable_secret_extraction = false`); `Debug` объектов `rustls` не логируется | CP-22, CP-28 |
| Провайдер | `aws-lc-rs`, собирается одной функцией, `install_default` не используется | CP-29 |

### 3.2. Аутентификация: raw public keys (CP §3.4, ADR-0013)

Обе стороны предъявляют RPK по RFC 7250 (только SPKI Ed25519), X.509 не поддерживается, отката нет (CP-16).
Проверяющая сторона (клиент для сервера, сервер для клиента) отвергает соединение, если не выполнено любое из условий:

1. Список промежуточных пуст; `end_entity` — ровно 44 байта с префиксом DER SPKI Ed25519 (префикс сверить тестом с
   `aws-lc-rs`). Имя сервера и время игнорируются.
2. `identity(end_entity) = SHA-256(end_entity)` совпадает с закреплённым значением (у клиента — отпечатки сервера из
   подписанной конфигурации; у сервера — подписанный список клиентов). Эта же функция даёт ключ таблицы сеансов — один
   разбор SPKI (V-01).
3. Подпись `CertificateVerify` проверяется `verify_tls13_signature_with_raw_key` с `{ED25519}`;
   `verify_tls12_signature` всегда ошибка; `assertion()` — только в модуле verifier (TST §1.8).
4. Сервер: `offer_client_auth`, `client_auth_mandatory` = `true`, `root_hint_subjects` пуст.
5. Сторона аутентифицирована только после завершения рукопожатия библиотекой (для сервера — проверен `Finished`
   клиента, RFC 9001 §4.1.1); до этого данные приложения, включая `Config`, не отправляются и не обрабатываются
   (CP-15).

После рукопожатия обе стороны в обоих транспортах проверяют `alpn_protocol() == "phantom/1"`, версию TLS 1.3 и группу
(CP-13; чтение группы в T1 требует решения, CP §5 п. 3).

**Отпечаток.** 32 байта SHA-256 от 44-байтного SPKI; текстовая форма `ed25519-spki-sha256:` + 64 строчные hex-цифры,
иные формы — ошибка разбора; человеку показываются первые 16 цифр, сравнивается полное значение. Хеш, а не ключ, —
ради перехода на ML-DSA в профиле v2.

**Риск.** RPK в `quinn` выведен из кода, не запуском; запасной вариант — самоподписанный сертификат с тем же
отпечатком SPKI (ADR-0013). Тесты — CP §3 (T-RPK1…6, T-ID1/2, T-AL1…4, T-HR1), TST T-G02-*, T-G03-*.

### 3.3. Ключи и роли (CP §3.10)

| Ключ | Где живёт | Обновление и отзыв |
|---|---|---|
| Идентичность сервера (Ed25519) | Файл 0600 / `LoadCredential` | Вручную; число одновременно закреплённых у клиента ключей и процедура смены не зафиксированы (§14, N-8) |
| Идентичность клиента (Ed25519) | То же | Отзыв — удаление из подписанного списка клиентов; сервер закрывает соединения с `KEY_REVOKED` |
| Подпись конфигураций (Ed25519) | Вне сервера, у оператора; `key_id` в конверте | Смена якоря — конвертом, подписанным текущим ключом (§9) |
| Сеансовые ключи TLS | Внутри `rustls`/`quinn` | §3.4 |

Три роли — разные ключевые пары; загрузка конфигурации отвергает ключ сервера в списке клиентов, совпадение ключа
подписи с ключом идентичности, повтор отпечатка и пересечение внутренних адресов (CP-25). Проверка подписи
конфигурации — `aws_lc_rs::signature` с `ED25519`, подпись с `S >= L` отвергается (CP-26, T-ED1).

### 3.4. Обновление ключей и срок жизни соединения (CP §3.1)

- Автоматическое обновление по лимиту AEAD в обеих библиотеках не отключается (CP-22). При ChaCha20 по объёму
  обновления нет, поэтому каждая сторона вызывает обновление по таймеру `KEY_UPDATE_INTERVAL` = 600 с ⟂ (T2 —
  `refresh_traffic_keys()`, T1 — `force_key_update()`) (CP-20).
- Свежий обмен ключами даёт только новое соединение: клиент заменяет его по схеме «новое, `Activate`, затем закрыть
  старое» (§4, TS §8.2); сервер закрывает соединение по своему пределу сам, не полагаясь на клиента. Числа срока жизни
  в CP-21 и TS §6 расходятся — §14, N-1. Срок считается по `CLOCK_BOOTTIME` (TS §7.4).
- **G4a** (forward secrecy относительно долговременных ключей): кража ключа идентичности после рукопожатия не
  раскрывает трафик соединения; не зависит от срока жизни; допущение — resumption и 0-RTT выключены.
- **G4b** (ущерб от утечки сеансовых ключей): чтение памяти в момент t раскрывает трафик соединения от последнего
  обновления ключей (не более `KEY_UPDATE_INTERVAL` назад, если библиотека удаляет прежние ключи — не проверено, CP §5
  п. 4) до закрытия соединения (не позже серверного предела).
- **G17** (идентичность клиента): публичный ключ клиента не раскрывается пассивному наблюдателю и активному атакующему
  без приватного ключа закреплённого сервера; защищён гибридом от T9. Клиент отправляет `Certificate` только после
  проверки сервера; длина `Certificate` одинакова у всех клиентов (CP-23, CP-24).

### 3.5. Поведение до аутентификации (CP §3.3, §3.7)

- T2: сервер разбирает ClientHello через `Acceptor`/`LazyConfigAcceptor` и закрывает соединение до криптографии, если
  ALPN не ровно `["phantom/1"]`, нет `X25519MLKEM768` или типы сертификатов не ровно `[RawPublicKey]` (CP-12).
  Закрывать молча или alert-ом — не решено (§14, N-12).
- T1: ALPN проверяет библиотека (ошибка 0x0178). ClientHello с долей 1216 байт занимает не меньше двух Initial; под
  нагрузкой сервер требует Retry (CP-19, TS §5.7).
- Версия протокола PHANTOM определяется только ALPN; `Hello.version` иной — `VERSION_MISMATCH` (CP-14).

## 4. Сеанс

Сеанс — пара «отпечаток клиента → внутренние адреса IPv4/IPv6», заданные статически в подписанной конфигурации
сервера. Токенов сеанса нет. Полные правила — TS §5.4–§5.5, §8.2; оговорки — RV §2.

- **Порядок.** Аутентификация → `Hello` клиента в течение `T_HELLO` = 5 с ⟂ → `Config` сервера → соединение
  «кандидат». Пакеты от кандидата отбрасываются; «пробное» соединение — это просто соединение без `Activate`.
  Сообщение не по порядку — `PROTOCOL_ERROR`.
- **Активация.** `Activate{seq}` клиента переводит кандидата в активное. Сервер сначала переключает маршрут, затем
  шлёт `Superseded` прежнему и `Activated{seq}` новому, закрывает прежнее через 2 с ⟂ с `SUPERSEDED`. Клиент шлёт
  пакеты в новое соединение только после `Activated`; принятое по старому доставляет ещё 2 с ⟂. Проигравшие в гонке,
  фоновые пробы и соединение для плановой замены `Activate` не шлют, пока клиент не решил переключиться; задержанное
  атакующим рукопожатие маршрут не уводит.
- **Счётчик `seq`.** 64-битный, монотонный. Клиент хранит его на диске; блок значений резервируется и записывается
  (`fsync`) до первой отправки; невозможность записи — явная ошибка (RV §2). Сервер отвергает `seq` не больше
  сохранённого сообщением `ActivateRejected{seq, min_next_seq}`; клиент ставит счётчик в `min_next_seq` и повторяет —
  так восстанавливается потерянный или откатанный счётчик (V-02).
- **`last_seq` на сервере** хранится в памяти: перезапуск рвёт все соединения, задержанный `Activate` доставить
  некуда. Перечитывание списка ключей не сбрасывает `last_seq`, пока у ключа есть живые соединения (RV §2). В TS это
  правило ещё не записано.
- **Лимиты.** Не более 6 активаций на ключ в минуту ⟂; превышение задерживает `Activated`, но не отвергает; в очереди
  задержанных — одно последнее значение на ключ (RV §2). Не более 2 кандидатов на ключ (SYS §3.7).
- **Cryptokey routing.** Пакет из туннеля принимается, только если адрес источника принадлежит ключу соединения; в
  туннель — по адресу назначения в активное соединение владельца. Внутренние адреса не меняются при смене транспорта и
  сети.
- **Отзыв.** При перечитывании подписанного списка сервер немедленно закрывает соединения отозванного ключа
  (`KEY_REVOKED`, у клиента — `Halted(Auth)`).
- **Одно устройство на ключ.** Второе устройство вытесняет первое; `SUPERSEDED` без собственной активации —
  диагностический признак у клиента (TS §5.6).

Не закрыто из V-03: утрата `Activated` после приёма `Activate` сервером, `Superseded` без `Activated`, приём пакетов
из прежнего соединения в паузе, снятие маршрута при закрытии активного без замены (§13).

## 5. Транспорты

### 5.1. Интерфейс

Эскиз (сигнатуры — этап 8): `Transport::connect(target, deadline) -> Result<Tunnel, ConnectError>`; `Tunnel`
отправляет и принимает пакеты и управляющие сообщения, отдаёт `health()` (наблюдения, без выводов о причинах) и
закрывается с кодом `Close`. `ConnectError` различает: тайм-аут без ответа, отказ в соединении, сброс, ошибку TLS,
ошибку закрепления ключа сервера, отказ аутентификации, несовпадение версии. Ошибки закрепления и аутентификации не
являются наблюдениями о транспорте (TS §7.3). Размер пакета — всегда `MTU_TUN` (§6.1).

### 5.2. T1 — QUIC с DATAGRAM (TS §2.1, §4, §5.2; ADR-0006)

- `quinn`. Данные — кадры DATAGRAM: `Context (varint)` + содержимое; контекст 0 — IP-пакет, 1 — SizeProbe, иные —
  отбросить со счётчиком. Отсутствие `max_datagram_frame_size` у пира или `max_datagram_size()` < 1 + MTU_TUN —
  закрытие `MTU_UNUSABLE`.
- Управление — единственный двунаправленный поток (ID 0), открытый клиентом; сервер разрешает 1 bidi и 0 uni, клиент —
  0/0; окно 16 КиБ ⟂; закрытие потока — закрытие соединения.
- Профиль: `min_mtu = initial_mtu = REQ_UDP = 1319`, `max_udp_payload_size ≥ 1319`, DPLPMTUD включён, длина CID 8;
  буфер отправки датаграмм 64 КиБ ⟂ вместо 1 МиБ; congestion control — CUBIC (по умолчанию); BBR (`Experimental!`) и
  отключение CC запрещены.
- Фрагментации нет: сокет с запретом фрагментации, при `may_fragment()` T1 не используется (M4). Процесс PHANTOM ICMP
  не формирует (M5, §6.1).
- Роуминг — штатная миграция с path validation; после смены локального адреса клиент делает rebind и SizeProbe. Retry
  — при > 64 ⟂ одновременных рукопожатиях или > 8/с ⟂ с одного префикса (TS §5.7).
- Keepalive: `max_idle_timeout` 30 с ⟂; `keep_alive_interval` 15 с ⟂ только у клиента; `Ping` по потоку управления раз
  в 60 с ⟂ (TS §6).

### 5.3. T2 — TLS 1.3 поверх TCP (TS §5.3)

- `rustls` через `tokio-rustls`, порт по умолчанию 443. Поток после рукопожатия — последовательность TLV; тип `0x00` —
  IP-пакет, остальные — управляющие, как в T1. SizeProbe не используется.
- Конец потока без `close_notify` или обрыв посреди кадра — ошибка (C-15).
- Отправитель держит две очереди: управление (приоритет) и пакеты (ограниченная, с отбрасыванием). RTT по `Pong` —
  только диагностика, не основание для переключения (TCP поверх TCP, RR16).
- Живость: клиент шлёт `Ping` после 15 с ⟂ без отправленных кадров; сервер закрывает соединение без входящих байтов 60
  с ⟂.

### 5.4. Кадрирование и управляющие сообщения (TS §5.1, §5.4–§5.6)

Формат `Message { Type (varint), Length (varint), Value }` совпадает с капсулой RFC 9297. Varint — только кратчайший;
значение содержит ровно поля описания; длина проверяется до чтения значения; типы `0x00–0x3F` обязательны (неизвестный
— `PROTOCOL_ERROR`), `0x40+` пропускаются; строк в сообщениях нет.

| Тип | Сообщение | Направление | Назначение |
|---|---|---|---|
| 0x01 | `Hello` | К→С | `version`, `caps`; ровно одно, ≤ 5 с после рукопожатия |
| 0x02 | `Config` | С→К | Адреса v4/v6, `mtu`, до 4 DNS, `keepalive_ms` (5000…60000), `lifetime_s` (600…7200), `caps` |
| 0x03 / 0x04 | `Activate` / `Activated` | К→С / С→К | Перенос маршрута (§4) |
| 0x05 | `ActivateRejected` | С→К | `seq`, `min_next_seq` |
| 0x06 | `Superseded` | С→К | `seq` нового активного |
| 0x07 / 0x08 | `Ping` / `Pong` | обе | Живость; ≤ 4 без ответа, ответ ≤ 4/с ⟂ |
| 0x09 | `GoAway` | С→К | Сервер скоро закроет (≤ 3600 с); клиент начинает замену |
| 0x0A | `Close` | обе | Код; в T1 дублируется в CONNECTION_CLOSE |

Коды `Close`: 0 `NO_ERROR`, 1 `PROTOCOL_ERROR`, 2 `VERSION_MISMATCH`, 3 `CONFIG_MISMATCH`, 4 `KEY_REVOKED`, 5
`SUPERSEDED`, 6 `LIFETIME_EXPIRED`, 7 `SERVER_SHUTDOWN`, 8 `RESOURCE_LIMIT`, 9 `HELLO_TIMEOUT`, 10 `MTU_UNUSABLE`;
действия клиента — TS §5.6. Разборщики — цели fuzz (TST §1.5).

### 5.5. T3 — HTTP/3 с CONNECT-IP (после MVP)

Собственный домен с WebPKI, ALPN `h3`, туннель по RFC 9484. В MVP не входит: `h3` экспериментален, CONNECT-IP в Rust
не подтверждён. Профиль CP (RPK, `phantom/1`) для T3 не предназначен (CP §2.3). Xray-core (с v26.10.21) и sing-box
(1.15.0-alpha) содержат клиент MASQUE CONNECT-IP — единственный реалистичный путь к INCY и Happ без их разработчиков,
но с более слабым профилем: пароль вместо ключа, нет RFC 9729 ни в одном ядре, нет `Activate`, в Xray закрепляется хеш
сертификата, kill switch — на стороннем клиенте (CC §4.4). Включение такого режима — решение владельца (ADR-0015); до
эксперимента совместимость не обещается.

## 6. Сеть

### 6.1. MTU (TS §4; ADR-0010)

- **M1.** `MTU_TUN = 1280` на клиенте и сервере, одинаково для T1 и T2, не меняется ни при смене транспорта, ни по
  `Config` (`Config.mtu` ≠ локальному — `CONFIG_MISMATCH`).
- **M2–M3.** Инвариант T1 `max_datagram_size() ≥ 1 + MTU_TUN` на всё время жизни соединения; обеспечивается
  `min_mtu = initial_mtu = 1319`: дополненные Initial доказывают прохождение 1319 байт UDP payload в обе стороны,
  детектор чёрной дыры не опускает MTU ниже `min_mtu`. REQ_UDP = 1319 считается по границе `quinn` (на проводе
  1310–1313; внешний пакет 1347/1367 байт для IPv4/IPv6).
- **SizeProbe** (контекст 1): BIG (1 + MTU_TUN) и SMALL (64 байта); сервер отвечает ACK и ECHO; до 3 попыток с
  `T_PROBE = max(3·PTO, 1 с)` ⟂. Обязательна после рукопожатия T1 до `Activate`, после смены локального адреса, после
  пробуждения, при подозрении потери связи и раз в 10 мин ⟂. BIG не прошёл при прошедшем SMALL — наблюдение F3 и
  `MTU_UNUSABLE`.
- **M5.** Процесс ICMP не генерирует: пакеты больше MTU_TUN в туннель не попадают — PTB отвечает ядро при пересылке в
  TUN.
- **M6.** Внешний ICMP не влияет на выбор транспорта и память по сети; в T2 поддельный PTB может уменьшить MSS
  внешнего TCP — остаточный риск (RR5, не проверено для Linux).
- **M7.** MSS clamping: на сервере в forward для SYN/SYN-ACK через TUN (1240 IPv4 / 1220 IPv6), на клиенте — для
  транзита.

### 6.2. Клиент: kill switch (SYS §1; ADR-0014)

- **Сторож.** `phantom-guard` — системная служба, независимая от демона туннеля: `DefaultDependencies=no`,
  `Wants=network-pre.target`, `Before=network-pre.target nftables.service firewalld.service ufw.service`,
  `Restart=always`, без `ExecStop`. Таблицы создаются с флагами `owner` + `persist`: чужой `nft flush ruleset` их не
  удаляет, пока сторож жив; после падения сторожа таблица остаётся «сиротой» и действует, перезапущенный сторож её
  усыновляет и сверяет (режим B). Без `persist` в ядре — режим A: `After=nftables.service …`, восстановление по
  событию `NFNLGRP_NFTABLES` не позже 100 мс ⟂, явное сообщение «защита от `flush ruleset` недоступна».
- **Состояние.** `off|enforcing` и полный текст правил последнего `enforcing` — в `/var/lib/phantom/killswitch.state`
  с атомарной записью. `off → enforcing`: записать, затем применить; `enforcing → off`: снять таблицы, затем записать.
  Повреждённый файл — минимальная запретительная таблица (только `lo`). Правила используют `iifname`/`oifname` и не
  называют физических интерфейсов.
- **Жизненный цикл.** `enforcing` включается командой `connect`; единственный путь в `off` — команда `disconnect`
  администратора через управляющий сокет сторожа. `phantom-netd` перевести систему в `off` не может. Падение
  процессов, остановка демона, перезагрузка, сон правил не снимают. Удаление пакета выполняет `disconnect` до удаления
  сторожа.
- **G8 (формулировка SYS §1.5).** Пока `enforcing`, трафик процессов корневого namespace и пересылаемый трафик (L3 и
  L2-мост) не выходит через нетуннельные интерфейсы, кроме транспорта к серверу с меткой клиента, DHCP/NDP/MLD и явно
  разрешённой LAN; в том числе при `nft flush ruleset`, **пока жив сторож и ядро поддерживает `persist`**. Не
  покрывает: окно загрузки до сторожа (initramfs, `ip=`) и окно выключения в режиме A (RR15); процессы с
  `CAP_NET_ADMIN`/`CAP_NET_RAW`, `AF_PACKET` (RR23); macvlan/ipvlan и иные namespaces со своим выходом. Слова
  «гарантия против root» не используются.

### 6.3. Клиент: правила, маршруты, DNS (SYS §2–§4)

- **Наборы правил** (эскиз SYS §4.1, синтаксис проверен только `nft -c`): `output` — `lo`, TUN, запрет
  53/853/5353/5355 мимо TUN **раньше** LAN, транспорт к `адрес . протокол . порт` сервера только с меткой `0x50480001`
  (с `ct mark set meta mark`), DHCP/NDP/MLD, LAN, затем reject; `input` — ответы TUN, установленные соединения с
  меткой клиента, ICMP-ошибки только `related` к ним, DHCP/NDP/RA/MLD с проверкой `hoplimit`, Redirect запрещён;
  `forward` — `drop` (опция `forward_via_tunnel` с маскарадингом на TUN); `preraw` — защита от CVE-2019-14899;
  `bridge phantom_l2` — пересылка между портами мостов запрещена, кроме явного списка портов ВМ. Нет общего
  `established accept` на физических интерфейсах; записи conntrack сбрасываются при переходе в `enforcing`. Каждая
  замена правил — одна транзакция; порядок включения: таблицы → маршруты → DNS, выключения — обратный.
- **Policy routing** по схеме `wg-quick`: `not fwmark` → своя таблица с `default dev phantom0`,
  `main suppress_prefixlength 0`; метку получают только сокеты транспорта через сторож (SYS §2.3).
- **DNS** (S-06): resolved через D-Bus (`SetLinkDNS`, домен `~.` на TUN, `RevertLink`); без менеджера — атомарная
  замена `/etc/resolv.conf` с резервной копией; иное — отказ подключения или явный `dns.mode = "file-force"`. Утечку в
  любом режиме закрывает firewall.
- **LAN** закрыта по умолчанию; `allow_lan` разрешает только пересечение подключённых подсетей с частными и link-local
  диапазонами, не шире /16 и /48 (S-05).
- **IPv6** — либо в туннеле, либо запрещён; «IPv4 в туннеле, IPv6 напрямую» невозможно по построению.
- **Адрес сервера** — IP; имя разрешается однократно в состоянии `off` при `connect`, результат входит в снимок
  правил. Не более 8 адресов сервера.
- **Captive portal** (S-08): исключений автомат не открывает; команда администратора `portal --minutes N` ставит
  временное правило только для uid `phantom-portal` с `timeout` в наборе. Нужен ли портал в MVP — §13.

### 6.4. Привилегии (SYS §2.5; ADR-0014)

- `SO_MARK`, rtnetlink-изменения, nfnetlink и создание TUN требуют `CAP_NET_ADMIN`, поэтому один процесс со сбросом
  прав неосуществим. `phantom-netd` работает без capabilities (`CapEff=0`).
- Закрытый перечень операций сторожа для `phantom-netd`: `OpenTransportSocket{family, proto, server_index}` (адрес —
  из подписанной конфигурации по индексу), `OpenTun` (fd по `SCM_RIGHTS`, не persistent), `TunnelUp{config_digest}`
  (маршруты и адреса только из локальной подписанной конфигурации), `SetDns`, `ReportState`. Операции `off` нет.
- Сокеты `/run/phantom/guard.sock` (группа `phantom-net`) и `control.sock` (группа `phantom-admin`), проверка
  `SO_PEERCRED`, фиксированные бинарные сообщения ≤ 4 КиБ. `phantom-guard` — `panic = abort`; `phantom-netd` —
  `panic = unwind` с изоляцией задачи соединения.
- Сервер: сокет на 443 открывает привилегированная часть или socket activation; `CAP_NET_BIND_SERVICE` демону не
  выдаётся (SYS §3.12).

### 6.5. Сервер: сеть (SYS §3.6, §4.2)

- TUN, пересылка, NAT; IPv6 — NAT66 из ULA `/64` (маршрутизируемый префикс отклонён: постоянный идентификатор).
- Фильтр назначения: `forward` `drop` по умолчанию; запрещены специальные, частные, link-local (включая metadata
  `169.254.169.254`, `fd00:ec2::254`), групповые диапазоны, собственные адреса сервера и префиксы сети хостинга из
  конфигурации. Клиент ↔ клиент — `drop`, также в процессе.
- `input` с TUN: только `established,related`, DNS туннеля на адрес шлюза, echo-request с лимитом.
- Таблица сервера без `persist`: при остановке службы транзит прекращается. `check` обнаруживает Docker с
  `FORWARD drop`.

### 6.6. Кроссплатформенные границы (SYS §6, CC §7)

Linux-специфичны TUN, netlink, nftables, fwmark, systemd, resolved, `SO_PEERCRED`. На Android, iOS/macOS и Windows
trait-ы `phantom-network` реализуются средствами ОС (`VpnService`, `NEPacketTunnelProvider`, Wintun + WFP); G8
формулируется на платформу и на мобильных ОС слабее или иная. Главный технический риск iOS — лимит памяти Network
Extension (порядка 15–50 МиБ по выдаче поиска, не проверено).

## 7. Автомат соединения клиента (TS §7; ADR-0009)

| Состояние | Трафик пользователя | Смысл |
|---|---|---|
| `Disconnected` | по состоянию kill switch: `off` — обычная сеть; `enforcing` — запрещён | Туннеля нет; kill switch — отдельная ось (SYS §1.4 п. 10, V-09) |
| `WaitNetwork` | запрещён | Нет маршрута по умолчанию или адреса |
| `Connecting` | запрещён | Гонка транспортов по списку адресов |
| `Connected(T)` | через туннель | Есть `Activated`; T ∈ {T1, T2} |
| `Suspect(T)` | через туннель | Подозрение потери связи, идут пробы |
| `Switching(T→T')` | через туннель (старое) | Новое поднимается; старое активно до `Activated` |
| `Reconnecting` | запрещён | Активное потеряно; backoff 1…60 с ±20 % ⟂ |
| `Blocked` | запрещён | Три круга без успеха; удвоение до 300 с ⟂; сам в `Disconnected` не переходит |
| `Halted(R)` | запрещён | R ∈ {Auth, Pin, Version, Config, Protocol, Portal}; нужен человек |

Полная таблица переходов — TS §7.2. Ключевые правила:

- **Потеря связи:** за `T_SUSPECT` = 2 с ⟂ отправлено, ничего не получено → `Suspect`; три пробы раз в 1 с (T1 —
  SizeProbe SMALL, T2 — `Ping`); без ответа — `Reconnecting`. Потери отдельных датаграмм основанием не служат.
- **Гонка** на каждом адресе: T1 сразу (если не помечен), T2 через D = 250 мс без истории или
  `clamp(2·srtt, 100 мс, 2 с)`. Пакет QUIC лишь продлевает попытку T1 до `T1_HS_MAX` = 6 с ⟂ и **не задерживает T2**.
  Побеждает первое соединение, прошедшее аутентификацию и (для T1) SizeProbe.
- **Наблюдения F1–F4** о непригодности T1 (TS §7.3). Одно наблюдение переводит текущий сеанс на T2, но не меняет
  память; метка «T1 непригоден в сети N» — после двух наблюдений за 10 мин ⟂, срок 5 мин с удвоением до потолка 60 мин
  ⟂; по истечении — фоновая проба T1. Ошибки аутентификации и закрепления, исключённые коды `Close`, `RESOURCE_LIMIT`,
  события первых 10 с после пробуждения или смены сети наблюдениями не являются.
- **Возврат на T1:** не раньше 60 с ⟂ на T2 и после двух успешных фоновых проб T1 с интервалом ≥ 30 с ⟂.
  **Анти-flapping:** не более 4 смен транспорта за 10 мин ⟂, затем заморозка рабочего транспорта на 10 мин; потеря
  соединения всегда ведёт в `Reconnecting` с гонкой обоих транспортов.
- **Адреса сервера:** до 8 ⟂, последний работавший первым, затем по списку с чередованием семейств; следующий адрес —
  через 2 с ⟂ без ответа или сразу при явном отказе обоих транспортов; запасные не проверяются, пока работает
  основной; на запасном — фоновая проба первого раз в 10 мин ⟂ (TS §8.1).
- **Сон:** скачок `CLOCK_BOOTTIME − CLOCK_MONOTONIC` > 5 с ⟂ или сигнал logind → проба живости и SizeProbe; неуспех —
  `Reconnecting` без учёта в памяти. Kill switch на время сна не снимается.
- **Плановая замена** (`GoAway`, срок жизни, возврат на T1, смена адреса): «сначала новое» — новое соединение,
  `Config` совпадает с текущим, SizeProbe (T1), `Activate{seq+1}`, переход после `Activated`; неуспех — повтор 5, 10,
  20 с ⟂, пока старое живо (TS §8.2).
- **Диагностика** сообщает наблюдения, а не причины; «заблокировано» не говорится; пробы — только к своему серверу.
  Портал: «TCP 443 соединяется, но вместо ServerHello иное» → `Halted(Portal)`.

## 8. Сервер: ресурсы, разбор, журналы

- **До аутентификации** ресурсы туннеля не выделяются. Лимиты (SYS §3.7, TS §5.7): одновременные рукопожатия по
  источнику и общий предел, Retry в T1 под нагрузкой, анти-усиление ≤ 3× принятого до проверки адреса, в T2 — SYN
  cookies ядра и тайм-аут рукопожатия 10 с ⟂, фильтр ClientHello (CP-12). Конкретные пороги в TS и SYS расходятся
  (§14, N-3).
- **После аутентификации:** ≤ 4096 новых записей conntrack на клиента; один поток QUIC; ограниченный размер
  управляющего сообщения (§14, N-2) и очереди к клиенту (§14, N-4); `Hello` ≤ 5 с; ≤ 2 кандидата на ключ.
- **Критерий G13** (стартовый): при 10 000 неаутентифицированных попыток/с с 1000 адресов на ВМ 2 vCPU/2 ГиБ
  легитимный клиент подключается с p95 ≤ 3× от времени без нагрузки, RSS ≤ 512 МиБ, подключённые не теряются.
- **Разбор недоверенного ввода** (S-16): границы — библиотеки TLS/QUIC, кадры и сообщения, IP-заголовок из туннеля
  (версия, длина, `total length` = длине кадра, источник = адрес ключа), заголовок конверта, TOML после подписи,
  сообщения управляющих сокетов, ответы netlink/D-Bus. В модулях проекта — запрет `unwrap`, `expect`, индексации без
  проверки и неявной арифметики; длины проверяются до выделения.
- **Журналы** (S-14, белый список полей): по умолчанию — агрегированные счётчики за час; по клиенту — только ошибки
  (отказ аутентификации, отозванный ключ, лимит) с меткой, заданной оператором, временем до минуты и кодом причины.
  Успешные подключения по клиенту — только при `log.client_events = true`. Адрес клиента — только уровень отладки;
  адресов назначения, DNS и объёмов по клиенту — никогда. `LogNamespace=phantom`, `LimitCORE=0`,
  `PR_SET_DUMPABLE = 0`; секретные типы не реализуют `Debug`/`Display`.

## 9. Конфигурация и обновления (SYS §1.8, V-04, V-05)

- **Формат.** TOML, неизвестные поля — ошибка; приватные ключи в отдельных файлах. Проверка до применения —
  `phantom-client check`, `phantom-server check`.
- **Конверт** — фиксированный двоичный заголовок: `magic "PHANTOM-CFG\0"`, `purpose` (клиентская конфигурация | список
  клиентов сервера | смена якоря), `key_id[16]`, `version`, `min_version`, `created_at`, `not_after`, `recipient[32]`,
  `payload_len`, payload, подпись Ed25519 по всему предыдущему. **Подпись проверяется до разбора**; TOML разбирается
  из тех же байтов. Список клиентов сервера подписывается тем же механизмом, поэтому отзыв ключа покрыт G15.
- **Приём** отвергает: неверную подпись, чужой `key_id`, чужого адресата, истёкший срок, версию не выше сохранённого
  максимума, версию ниже минимально допустимой.
- **Хранение.** `/var/lib/phantom/config/`: `v<N>.env` с `fsync`, затем атомарная замена `state` (`max_version`,
  `current`, `min_version`, `key_id`); точка фиксации — `rename`. Без `state` обновления по сети не принимаются —
  только ручная установка оператором вместе с якорем (`trust install`).
- **Срок.** По истечении `not_after + grace` (7 суток ⟂) новые подключения не устанавливаются, kill switch остаётся
  `enforcing` — отказ, а не предупреждение (единственный ограничитель сценария «украденный ключ сервера + блокировка
  доставки обновлений»). Состояние автомата для этого случая не согласовано (§14, N-6).
- **Часы.** `created_at > now` — не ошибка; монотонность версии не зависит от часов. Часы в будущем запирают узел —
  выход локальной командой `clock-override --until <дата>` с записью в журнал; остаточный риск — в RR.
- **Откат** — только командой оператора: `current = N−1`, `max_version` не уменьшается, следующий принимаемый номер >
  N; истёкшая N−1 — только с `--force-expired`. Автоматического отката нет; «ошибка запуска» — только локальная ошибка
  проверки или применения, не неудача подключения (RV §3).
- **Смена якоря** — конвертом `purpose = смена якоря`, подписанным текущим ключом; затем старый `key_id` отвергается.
  Компрометация якоря и «сжигание» версии `2^64−1` — только ручной `trust reset` (RR21).
- **`Config` от сервера** не ослабляет локальную политику: адреса, MTU, DNS сверяются с локальной подписанной
  конфигурацией, несовпадение — закрытие (`CONFIG_MISMATCH`); маршруты и DNS ставятся только из локальной конфигурации
  (SYS §2.5, TS §5.4; уточнение — §14, N-9).
- **Безопасные умолчания:** подключение всегда включает `enforcing` (флага «без kill switch» нет), LAN закрыта,
  `forward` закрыт, журнал адресов и событий по клиенту выключен.

## 11. Тестовый стенд (TST §3)

| Стенд | Что проверяет | Ограничения |
|---|---|---|
| A — контейнер разработки | Unit, proptest, integration, fuzz, E2E в network namespaces (`cli`–`net`–`srv`–`inet`, `atk`), большинство тестов утечек | Есть root, `CAP_NET_ADMIN`, `/dev/net/tun`, `nft` 1.0.9 (без `persist`), `unshare`; нет `ip`, `tc`, `tcpdump`, `ping`, netem, systemd как PID 1. | B — ВМ с systemd | Порядок загрузки и выключения сторожа (V-06), resolved, NetworkManager, Docker, firewalld, `persist` на целевых ядрах, sandbox unit, сверка эмулятора с netem | Список дистрибутивов утверждает владелец |

## 13. Открытые вопросы

1. Практические проверки CP §5: RPK через `quinn` и `peer_identity()`; чтение группы в T1; удаление прежних ключей
   после обновления (условие G4b); уравнение Ed25519 в AWS-LC и `S >= L`; префикс DER SPKI.
2. Padding записей и потока (кроме `Certificate` клиента, CP-24) — не решён; цена не оценена.
3. V-03: утрата `Activated`, `Superseded` без `Activated`, приём пакетов из прежнего соединения в паузе, снятие
   маршрута при закрытии активного без замены.
4. Минимальные версии ядра и `nft` с `persist`; свой кодировщик nfnetlink или `libnftables` (C в доверенной базе).
5. Нужны ли в MVP captive portal, `allow_lan`, `forward_via_tunnel`; срок `grace`.
6. Работает ли `phantom-guard` и на сервере (TUN, сокет 443) или там отдельный привилегированный процесс.
7. Число закреплённых ключей сервера у клиента и процедура смены ключа сервера (N-8).
8. T3: нужен ли режим совместимости с Xray-клиентами и допустим ли более слабый профиль (CC §9, ADR-0015).
9. Нетипичность Initial 1319 байт для наблюдателя; поведение `TCP_NOTSENT_LOWAT`, TCP keepalive; поддельный PTB для T2
   в Linux.
10. Все числа «⟂» не измерены: `T_SUSPECT`, `T1_HS_MAX`, потолок памяти 60 мин, бюджет переключений, лимиты G13.
11. Тело ADR-0007 по-прежнему описывает перенос маршрута по рукопожатию (V-09) — правка ADR.

## 15. Что изменилось относительно v0.2

- **Криптография:** самоподписанные X.509 заменены RPK на обеих сторонах; проверка переписана по CP-16 (44 байта SPKI,
  один разбор, только Ed25519 через `WebPkiSupportedAlgorithms`); добавлены формат отпечатка, роли ключей, фильтр
  ClientHello T2, проверки после рукопожатия, запрет `into_0rtt`, HRR/Retry, обновление ключей по таймеру,
  G4a/G4b/G17; убрано «до двух закреплённых ключей»; TLS 1.3 — RFC 9846.
- **Сеанс:** `ActivateRejected` и восстановление счётчика, порядок записи `seq`, хранение `last_seq`, лимиты активаций
  и кандидатов, порядок переключения маршрута, окно стока, `GoAway`.
- **Транспорты и MTU:** единый TLV для T1 и T2 с таблицами типов и кодов `Close`; байт контекста в DATAGRAM; один
  поток QUIC; CUBIC, BBR запрещён; удалено «отбрасывается с ICMP» — процесс ICMP не формирует (M5); «около 1310»
  заменено на REQ_UDP = 1319 и `min_mtu = initial_mtu = 1319`; SizeProbe; выводы о T3 и Xray/sing-box.
- **Сеть:** вопрос «один процесс или helper» закрыт сторожем `phantom-guard` (новый компонент); `owner`+`persist`,
  порядок unit-ов по V-06, режим A; L2-мост, ICMP через `ct mark`, `preraw`; DNS-режимы, LAN, DHCP/NDP, портал; G8 по
  SYS §1.5; сервер — фильтр назначения и NAT66.
- **Автомат:** 9 состояний вместо 7 (убраны `Probing`, `Degraded`); строка `Disconnected` больше не утверждает `off`;
  F1–F4, память после двух наблюдений с потолком 60 мин; T2 не ждёт форы T1; D ≤ 2 с; заморозка на 10 мин вместо «до
  смены сети».
- **Сервер, конфигурация, стек, стенд:** белый список полей журнала (в v0.2 — все подключения с отпечатком); двоичный
  конверт с `key_id` и `purpose`, подпись до разбора, подписанный список клиентов, срок, часы, откат, смена якоря;
  нижние границы `rustls-webpki` и `aws-lc-sys`; стенды A–D и эмулятор на `AF_PACKET`.
- Открытые вопросы v0.2 №1–5 закрыты детальными документами (кроме N-1 для срока жизни); добавлены §14 и §15.
