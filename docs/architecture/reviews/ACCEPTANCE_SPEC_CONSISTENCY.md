# Приёмка: согласованность спецификации и замечания Medium

**Дата:** 2026-11-14. **Исполнитель:** независимый аудитор фазы 0 (не автор решений, не автор замечаний).
**Фаза:** 0 — архитектурная приёмка без кода. **Статус:** отчёт проверки по документам; ничего не запускалось.

Метки: [Факт: документ §] — текст прочитан в этом репозитории; [Вывод]; [Предположение]; [Не проверено].
Ни одно замечание не переведено в `Verified`: кода и тестов нет, а статус требует прохождения теста и проверки
не автором исправления.

Сокращения документов: **CP** — `docs/protocol-spec/CRYPTO_PROFILE.md`; **TS** —
`docs/protocol-spec/TRANSPORT_AND_SESSION.md`; **SYS** — `docs/architecture/SYSTEM_AND_LEAK_PROTECTION.md`;
**REC** — `docs/protocol-spec/RECONCILIATION.md`; **ARCH** — `docs/architecture/ARCHITECTURE.md` v0.3; **TM** —
`docs/threat-model/THREAT_MODEL.md` 1.0-rc; **TST** — `docs/testing/TEST_STRATEGY.md` 0.1; **HO** —
`OPUS_5_5_MASTER_HANDOFF.md`; **SF** — `SECURITY_FINDINGS.md`; **RV** — `reviews/REVERIFY_HIGH.md`; **RS** —
`reviews/REVIEW_SECURITY.md`; **RC** — `reviews/REVIEW_CRYPTO.md`; **RTM** — `threat-model/REVIEW_THREAT_MODEL.md`;
**R8** — `docs/research/08-availability-loss-causes.md`; **NSP** — `docs/prompts/NEXT_SESSION_PROMPT.md`.

Среды проверки (по NSP §4): **К** — контейнер Linux (root, `CAP_NET_ADMIN`, `/dev/net/tun`, `nft`, namespaces; нет
systemd, `ip`, `tc`, netem, KVM); **GU** — GitHub Actions Ubuntu (systemd, без перезагрузки); **GW** — GitHub Actions
Windows; **ЧВ** — чек-лист владельца; **НП** — автоматически не проверяется ни в одной доступной среде.

Влияние смены платформы (Linux-клиент — только консольный эталон для автотестов, продуктовый клиент — Windows 10/11,
сервер — Ubuntu LTS / Debian Stable): **ядро** — требование общего ядра, переносится на Windows без изменений;
**→Win** — переносится как требование, но механизм на Windows проектируется заново; **эталон** — относится только к
эталонному Linux-клиенту; **сервер** — только сервер; **снимается**.

## 0. Вердикт

1. **Спецификация как целое внутренне не согласована, и это в первую очередь проблема применения, а не
   решений.** Из 19 решений REC в целевых документах применены полностью — ни одно; частично — 5 (N-5, N-7, N-10,
   N-16 и косвенно N-1); остальные 14 записаны только в REC [Вывод из §2]. CP, TS и SYS по-прежнему содержат
   исходные противоречащие формулировки, а TM, ARCH и TST ссылаются то на старый, то на новый вариант. Правило
   «побеждает REC» (HO §2) делает это допустимым для чтения, но не для реализации: исполнитель, читающий CP-12, TS
   §8.1 или SYS §3.7, получит отменённое требование.
2. **37 замечаний Medium — число сходится** (C-04…C-10 — 7, S-05…S-16 — 12, S-19 — 1, V-01…V-05 и V-07 — 6,
   M-02…M-12 — 11). Решения есть по всем, кроме остатка **V-03**. По существу достаточны 13, достаточны с
   оговорками 20, недостаточны 4 (V-03, M-07, S-19, S-13 в части автомата) [Вывод из §1]. Ни одно не закрыто.
3. **Три решения REC создают новые проблемы:** N-18 не выполняет измеряемое свойство AV1 модели угроз (60 с против
   окон 180/420 с); N-13 нереализуемо в сформулированном виде (сервер не отличает собственную замену клиента от
   второго устройства); N-17 не определяет «новый адрес» и ломает определение «круга» автомата. N-5 требует ещё
   одного перехода автомата (команда `disconnect` из `Disconnected`).
4. **Переход на Windows-клиент оставляет без нормативной основы 9 из 37 Medium** (S-05, S-06, S-07, S-08, S-09,
   V-07 и части S-14, M-02, M-05): их решения — механизмы Linux (nftables, `phantom-guard`, `skuid`, resolved).
   Нормативной спецификации платформенного слоя Windows нет вовсе: SYS §6 содержит одну строку с пометками
   [Не проверено]. Это новое замечание A-SPEC-10 (Medium), его нужно закрыть до фазы 4.
5. **Матрица тестов отстаёт от спецификации существенно** (§5: 41 конкретное расхождение), а стенды A–D не
   соответствуют средам NSP §4. Приведение — обязательная первая задача реализации (N-15), до этого ни одну
   строку TST нельзя использовать как критерий закрытия.
6. **Блокирующего для начала фазы 1 (эксперименты) нет.** Для фазы 2 (ядро) нужно: ADR со сведением и правка
   CP/TS/SYS (§7, П-1…П-6), решение V-03 (§4). Для фазы 4 — спецификация Windows (П-7, П-8).
