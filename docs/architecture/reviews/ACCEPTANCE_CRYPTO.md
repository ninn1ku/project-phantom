## 0. Вердикт

**Криптографический профиль принимается с обязательными правками до начала кода.** Дефектов, ломающих
конфиденциальность или аутентификацию канала, не найдено: выбор TLS 1.3 + `X25519MLKEM768` + RPK Ed25519, отказ от
resumption и 0-RTT, алгоритм verifier (C-01/V-01) подтверждены по исходникам текущих стабильных версий
(`rustls` 0.23.46, `quinn` 0.11.12 / `quinn-proto` 0.11.19, `aws-lc-rs` 1.19.0 / `aws-lc-sys` 0.47.0). `rustls` 0.24
существует только как dev-выпуски с несовместимым API — MVP строится на 0.23.x.

Обязательно до кода (Medium):

1. **Нижние границы версий неверны** (AC-01): `quinn-proto` нужна ≥ 0.11.19 — RUSTSEC-2026-0524 позволяет атакующему
   на пути уронить **клиент** до аутентификации, -0523 — серверу исчерпать память; `tokio` 1.54.0 (отозвана) имеет UAF
   в `Interval`; нет границы `quinn-udp`.
2. **Features `quinn` не ограничены** (AC-02): по умолчанию в сборку попадают `ring` и `rustls-platform-verifier`.
3. **Ключ подписи конфигураций «вне сервера» для владельца неосуществим** (AC-07): одна машина-сервер, нет офлайн-машины.
   Рекомендуется честно держать ключ на сервере с разделением пользователей и записать следствие: компрометация root
   на сервере = компрометация ключа подписи, восстановление — повторный импорт на каждом устройстве.
4. **Файл устройства содержит приватный ключ** (AC-09): это предъявительский секрет; обращение с ним не
   специфицировано. Рекомендуется генерация на сервере (проще для неспециалиста) с перечисленными мерами (§4.3).

Мелкие неточности профиля (Low/Info): `max_tls13_tickets`, неисполнимое CP-18 (HRR), токены `NEW_TOKEN` в T1, причина
требования AES-128-GCM, формат конверта, хранение на Windows (DPAPI в контексте `SYSTEM`, не области машины; Ed25519
в CNG нет). Подтверждено исходником, что AWS-LC отвергает подписи Ed25519 с `S ≥ L` (было «не проверено»).
Только экспериментом фазы 1: RPK через `quinn`, размер ClientHello, удаление ключей после обновления.

## 4. Конфигурация и устройства

### 4.1. Оценка конверта SYSTEM §1.8

Конверт: `magic "PHANTOM-CFG\0"`, `u8 purpose`, `key_id[16]`, `u64 version`, `u64 min_version`, `i64 created_at`,
`i64 not_after`, `recipient[32]`, `u32 payload_len`, payload, подпись Ed25519 по всему предыдущему.

| Свойство (задание §10) | Есть в SYS §1.8 | Оценка |
|---|---|---|
| Подпись, целостность | Ed25519 по всем байтам до подписи; проверка до разбора TOML | Верно. Фиксированная раскладка заголовка снимает вопрос канонизации [Вывод]. `S < L` проверяется AWS-LC (п. 2.16) |
| Разделение контекстов | `magic` + `purpose` | Достаточно при отдельном ключе подписи (CP-25); для подписи TLS (`CertificateVerify`) свой префикс контекста (RFC 8446 §4.4.3 — по CRYPTO_PROFILE, мной не перечитано) |
| Версия формата | **нет** | Добавить `u16 format = 1` сразу после `magic`: иначе переход на ML-DSA (профиль v2) или новое поле меняет смысл тех же байтов |
| Версия, защита от отката | `version`, `min_version`, `state` с `max_version` | Верно (V-05 закрыт проектом). Не хватает: правила, что `min_version ≤ version`, и потолка шага (см. §5) |
| Срок | `created_at`, `not_after`, `grace` | Верно (V-04 закрыт проектом). Не задано: единицы (секунды Unix, UTC) и порядок байт |
| Адресат | `recipient[32]` | Семантика не задана по `purpose`. Предлагается: клиентская конфигурация — отпечаток ключа устройства; список клиентов — идентификатор развёртывания (32 случайных байта, создаётся при установке); смена якоря — тот же идентификатор развёртывания |
| Идентичность ключа подписи | `key_id` = первые 16 байт SHA-256 | Верно как селектор. Нормативно записать: проверка всегда идёт полным установленным ключом-якорем, `key_id` — только для выбора и диагностики |
| Однозначная длина | `payload_len` | Добавить: общая длина файла MUST быть ровно `header + payload_len + 64`; `payload_len` ≤ 64 КиБ ⟂; порядок байт — big-endian |
| Отзыв | через список клиентов (`purpose`) и `min_version` | Работает для одного сервера; для нескольких — §6 |
| Несколько серверов | список в payload | Есть (N-8: 1…4 отпечатка на сервер) |
| Безопасное обновление | монотонность, атомарная запись `state` | Верно; доставка обновлений по туннелю (R-3) в TS не описана сообщением — см. §6 |

Вывод: формат SYS §1.8 — не собственная криптография (стандартный Ed25519 над фиксированными байтами), а собственный
формат сообщения; при перечисленных дополнениях он достаточен.

### 4.2. Свой конверт или COSE_Sign1 (RFC 9052)

[Факт: rfc9052.txt §4.4, §9] COSE_Sign1 подписывает `Sig_structure = ["Signature1", body_protected, external_aad,
payload]` в детерминированной кодировке CBOR (минимальные длины, без повторов ключей в map); алгоритм и `kid` — в
заголовках; `crit` — список обязательных к пониманию параметров (§3.1).

| Критерий | Свой фиксированный конверт | COSE_Sign1 |
|---|---|---|
| Разбор до проверки подписи | Фиксированный заголовок известной длины, без парсера | Нужен разбор CBOR (массив из 4 элементов, bstr защищённых заголовков) — разборщик недоверенного ввода до аутентификации (граница S-16 п. 4 растёт) |
| Канонизация | Не нужна: подписываются байты как есть | Подписывается пересобранный `Sig_structure`; требование детерминированной кодировки RFC 9052 §9 |
| Разделение контекстов | `magic` + `purpose` | Строка `"Signature1"` + защищённые заголовки |
| Версия, срок, адресат | Поля заголовка | Нужно класть в payload или в заголовки (CWT-утверждения — RFC 8392, мной не читан [Не проверено]) |
| Типичные ошибки | Нет поля алгоритма — нет путаницы алгоритмов | Нужно жёстко зафиксировать `alg = EdDSA` в защищённом заголовке и игнорировать незащищённые; обработка `crit` |
| Зависимости | Нет | `coset`/`ciborium` или аналог — новые крейты в доверенной базе [Не проверено: их аудит] |
| Совместимость со сторонними инструментами | Нет | Есть, но проекту не нужна |

**Рекомендация:** оставить свой фиксированный конверт SYS §1.8 с дополнениями п. 4.1 (`format`, порядок байт, точная
длина, предел `payload_len`, семантика `recipient`). COSE не уменьшает риски, а добавляет разборщик до проверки
подписи и зависимости. minisign/signify и `ssh-keygen -Y` (предложение C-03) не дают полей версии, срока и адресата —
их пришлось бы класть в payload, выигрыша нет [Вывод; форматы по памяти рецензента C-03, мной не перечитывались].

### 4.3. Файл устройства: где генерировать ключ

Сценарий владельца: сервер выдаёт файл, пользователь импортирует его в клиент.

| Критерий | А. Ключ генерирует сервер (`phantom-admin`) и кладёт в файл | Б. Ключ генерирует клиент, регистрация |
|---|---|---|
| Шаги пользователя | Один: перенести файл и импортировать | Б1: передать отпечаток обратно на сервер (два направления). Б2: одноразовый код приглашения, клиент сам регистрирует ключ |
| Приватный ключ вне устройства | Да: в файле, при передаче, на сервере до удаления файла | Нет |
| Новый код безопасности | Нет | Б2: протокол регистрации до аутентификации клиента, хранение и одноразовость кода, лимиты; код приглашения — предъявительский секрет, что противоречит ADR-0005 «паролей и bearer-токенов нет» |
| Утечка файла / кода | Файл = полноценный доступ до отзыва (RR9) | Б2: код до использования = чужая регистрация; после использования бесполезен |
| Обнаружение утечки | Только по журналу (N-13: вытеснение соединения) | Б2: отказ регистрации у законного пользователя |
| Работа без сети при импорте | Да | Б2: нужна связь с сервером |

**Рекомендация для MVP: вариант А** с обязательными мерами:

1. Файл устройства — **секрет** уровня приватного ключа. Это записывается в интерфейс (импорт предупреждает и
   предлагает удалить исходный файл), в документацию владельца и в модель угроз (новый актив: файл устройства в пути).
2. Сервер хранит только отпечаток устройства; приватный ключ генерируется в памяти `phantom-admin` (`aws-lc-rs`,
   системный ГСЧ), пишется только в файл выдачи `0600` во временном каталоге root (или выводится в терминал) и не
   сохраняется в состоянии сервера. Повторная выдача того же файла невозможна: «выдать заново» = новый ключ и отзыв
   старого в одной версии списка (§6).
3. Файл связывает ключ и конфигурацию: при импорте клиент проверяет подпись конверта якорем из файла и равенство
   `recipient` отпечатку открытого ключа, вычисленного из приватного. Несовпадение — отказ.
4. Состав файла (контейнер, не подписывается целиком): якорь (открытый ключ подписи, 32 байта), приватный ключ
   устройства (PKCS#8 Ed25519 — формат, который читает `aws-lc-rs`, [Факт: `aws-lc-rs` `src/ed25519.rs`
   `from_pkcs8` → `parse_rfc5208_private_key`]), подписанный конверт клиентской конфигурации. Якорь в файле не защищён подписью — доверие к нему
   даёт только канал передачи файла (граница B7). Это нормально для первичной установки, но должно быть записано.
5. После импорта клиент хранит ключ по §7; исходный файл удаляется пользователем (на SSD удаление не гарантирует
   стирания — остаточный риск).
6. Вариант Б2 — после MVP, отдельным ADR, если владелец захочет устройства без переноса секретов.

Что из этого следует: украденный или пересланный не тем адресатом файл даёт подключение от имени устройства и
раскрывает адреса серверов (в том числе запасные) и отпечатки. Отзыв устройства закрывает доступ, но не «отзывает»
раскрытые адреса [Вывод].

## 5. Ключ подписи конфигураций

Документы требуют: «вне сервера, у оператора» (handoff §7, ARCH §3.3, G15 «Допущение»). У владельца один сервер и
нет отдельной машины. Варианты честно:

| Вариант | Что защищает | Чего не защищает | Простота |
|---|---|---|---|
| A. На сервере, отдельный файл root `0600`, читает только `phantom-admin`; `phantom-server` работает под своим пользователем и доступа к файлу не имеет | Сетевого атакующего; RCE в `phantom-server` (разбор сети — самый вероятный путь компрометации) не даёт ключ подписи при разделении пользователей | Компрометация root на сервере = компрометация ключа подписи: атакующий подписывает конфигурации с адресами и отпечатками своих серверов, «сжигает» версию, меняет якорь. Восстановление — только повторный импорт файла на **каждом** устройстве | Высокая |
| Б. На компьютере владельца (Windows), операции с устройствами — через клиент | Компрометацию сервера | Компрометацию ПК владельца (почта, браузер — поверхность больше, чем у сервера) [Вывод]; нужен удалённый административный канал к серверу — новая поверхность атаки | Низкая |
| В. На сервере, зашифрован парольной фразой, расшифровывается только на время команды `phantom-admin` | Утечку файла или резервной копии; атакующего, который читает диск, но не ждёт ввода | Root, перехватывающий ввод; утрата фразы = обновления невозможны, только повторный импорт. Требует стандартного формата шифрования ключа (PBES2 по RFC 8018 или иной) — поддержка в `aws-lc-rs` [Не проверено] | Средняя |
| Г. Два ключа: корневой (бумажная копия/ПК, используется редко) делегирует онлайн-ключу на сервере с коротким сроком | Ограничивает время, в течение которого украденный онлайн-ключ действует, и даёт удалённое восстановление | Сложнее формат (делегирование, срок, отзыв делегирования); корневой ключ всё равно надо где-то хранить | Низкая для MVP |

**Рекомендация.** MVP — вариант A, с изменением допущения G15 и записью остаточного риска:

- G15, «Допущение»: «ключ подписи хранится вне сервера» заменить на «ключ подписи недоступен процессу `phantom-server`
  (разделение пользователей); компрометация root на сервере равна компрометации ключа подписи (RR21)».
- RR21 дополнить: «восстановление после компрометации root или ключа подписи — повторный импорт нового файла на каждом
  устройстве; удалённое восстановление невозможно» — для личного развёртывания с несколькими устройствами это
  приемлемо, и это нужно сказать владельцу прямо.
- Ключ подписи не загружается через `LoadCredential` службы `phantom-server`, не попадает в её окружение и журналы.
- Клиент показывает пользователю существенные изменения из обновления: смену отпечатка сервера, адресов, якоря — как
  событие (обнаружение, не защита).
- Потолок шага версии: клиент отвергает `version > max_version + 2^32` ⟂ — «сжигание» `2^64−1` одним конвертом
  становится невозможным [Вывод: это ограничение, а не защита — атакующий с ключом может слать серию конвертов, но
  ему нужен работающий канал доставки].
- Смена якоря по сети (SYS §1.8 п. 7) в MVP — **не поддерживать**: при варианте A она не даёт безопасного
  восстановления (атакующий с ключом сменит якорь первым), а лишь добавляет код. Смена якоря = повторный импорт.
- Вариант Г — кандидат после MVP (модель «корень делегирует онлайн-ключу»), отдельным ADR.

## 6. Ротация и отзыв (по N-8 и SYS §1.8)

| Операция | Схема в спецификации | Работает? | Чего не хватает |
|---|---|---|---|
| Ротация ключа сервера | N-8: в конфигурации клиента 1–4 отпечатка на сервер; добавить новый → перевести сервер → убрать старый | Да, по построению: клиент принимает любой из закреплённых, RPK без согласования | (1) Сервер не знает, какие устройства уже получили конфигурацию с новым отпечатком: `Hello` несёт только `version`, `caps` (TS §5.4). Предлагается поле `config_version` в `Hello` и счётчик «устройства на старой конфигурации» в `phantom-admin status`. (2) Канал доставки обновлений по туннелю не описан сообщением в TS §5.4 (R-3) — нужен тип сообщения «конверт конфигурации» (С→К) с пределом длины, отдельный от `Config`. (3) Устройство, пропустившее шаг «добавить», после перевода сервера получает `Halted(Pin)` — нужен понятный текст «нужен новый файл устройства». (4) Аварийная ротация при краже ключа сервера: обладатель старого ключа может выдавать себя за сервер устройствам, ещё не получившим обновление, и блокировать доставку обновления; ограничитель — только `not_after + grace` (RR29) — записать в процедуру |
| Отзыв устройства | Удаление отпечатка из подписанного списка; сервер закрывает соединения (`KEY_REVOKED`) | Да для одного сервера | (1) Несколько серверов: отзыв действует только на серверах, получивших новый список; нужна команда проверки «версия списка на каждом сервере». (2) Отозванное устройство знает адреса серверов — раскрытие не отзывается. (3) `min_version` списка поднимать при каждом отзыве (иначе откат командой оператора возвращает ключ) — записать в процедуру |
| Ротация ключа устройства | Не описана | Только через повторную выдачу | Записать: ротация = новый файл устройства; старый и новый отпечаток с одним внутренним адресом не могут сосуществовать (CP-25 «пересечение адресов»), поэтому замена — одной версией списка: удалить старый, добавить новый. Счётчик `seq` у нового ключа начинается заново — корректно, `last_seq` хранится по отпечатку (N-16) |
| Ротация ключа подписи | SYS §1.8 п. 7: конверт `purpose = смена якоря` | См. §5 | В MVP — только повторный импорт |

### 7.2. Клиент Windows

Факты по документации Microsoft (исходники документации в репозиториях `MicrosoftDocs/sdk-api` и `MicrosoftDocs/win32`
на GitHub; `learn.microsoft.com` через прокси недоступен — ответ 403):

- [Факт: `nf-dpapi-cryptprotectdata.md`] `CryptProtectData`: обычно расшифровать может только пользователь с теми же
  учётными данными входа и на том же компьютере; **с флагом `CRYPTPROTECT_LOCAL_MACHINE` расшифровать может любой
  пользователь этого компьютера**. Данные защищены MAC от изменения.
- [Факт: `cng-algorithm-identifiers.md`, ms.date 05/27/2025] в перечне идентификаторов алгоритмов CNG есть ECDSA P-256,
  P-384, P-521 и ECDH, **EdDSA/Ed25519 нет**. [Факт: `cng-named-elliptic-curves.md`] `BCRYPT_ECC_CURVE_25519` есть как
  именованная кривая (по таблице — без OID); подписи Ed25519 это не даёт [Вывод].
- TPM и Ed25519: документацию Microsoft о поддерживаемых TPM кривых получить не удалось [Не проверено]. Исходное
  условие задания «TPM не поддерживает Ed25519» принимается как [Предположение]; с фактом про CNG оно согласуется.

Следствие: неизвлекаемое хранение ключа Ed25519 средствами Windows (CNG KSP, TPM) недоступно; ключ устройства
неизбежно находится в памяти службы при каждом рукопожатии (подпись `CertificateVerify` делает `aws-lc-rs`).

| Вариант | Что даёт | Чего не даёт |
|---|---|---|
| Файл в `%ProgramData%\Phantom\` с явным ACL: `SYSTEM` — полный, `Administrators` — полный, наследование отключено, `Users` — нет | Защита от обычных пользователей и процессов без прав администратора | Защита при копировании файла (резервная копия, пакет диагностики, ошибка ACL) |
| + DPAPI `CryptProtectData` из службы `LocalSystem` **без** `CRYPTPROTECT_LOCAL_MACHINE`, с `CRYPTPROTECT_UI_FORBIDDEN` | Файл, скопированный отдельно от системы, не расшифровывается; расшифровать может только контекст `SYSTEM` | Защиту от администратора (может действовать от имени `SYSTEM`) и от вредоносного кода в службе |
| DPAPI с `CRYPTPROTECT_LOCAL_MACHINE` | То же для копии файла | **Хуже предыдущего**: при ошибке ACL любой локальный пользователь расшифрует ключ [Факт выше] — не рекомендуется |
| TPM / Platform Crypto Provider | Неизвлекаемый ключ | Недоступно для Ed25519. Возможно только при смене схемы подписи устройств на ECDSA P-256 и собственном `SigningKey` через NCrypt — изменение профиля (CP-05), второй алгоритм у сервера; кандидат после MVP, отдельным ADR |

**Рекомендация (Windows):** ключ, конфигурация, `state` и `seq` — в `%ProgramData%\Phantom\` с явным ACL (`SYSTEM`,
`Administrators`); приватный ключ дополнительно обёрнут DPAPI в контексте `SYSTEM` без флага области машины. Интерфейс
(`phantom-ui`, пользователь) ключа не получает никогда: при импорте передаёт байты файла службе по именованному
каналу; служба проверяет, сохраняет, интерфейс предлагает удалить исходный файл. Отчёты о сбоях Windows (WER) могут
сохранить дамп памяти службы с ключом — нужна проверка и, если подтвердится, отключение локальных дампов для службы
[Не проверено]. ACL `%ProgramData%` по умолчанию мной по документации не проверялся [Не проверено] — поэтому ACL
каталога задаётся явно установщиком и проверяется тестом.

### 7.3. Эталонный клиент Linux

Ключ — файл `0600`, владелец — пользователь `phantom-netd` (ключ нужен процессу TLS, не сторожу); каталог состояния
