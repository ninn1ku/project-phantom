## 2. MTU

**Расчёт REQ_UDP верен.** [Факт-код: §1 выше] 1319 − 29 − 9 = 1281 = 1 + MTU_TUN. Внешний пакет: IPv4 1319 + 20 +
8 = **1347**, IPv6 1319 + 40 + 8 = **1367** — совпадает с TS §4.2. Оговорки:

1. [Вывод] В расчёт входит длина CID **пира** (`rem_cids.active().len()`): у клиента — длина CID сервера, у
   сервера — клиента. Обе — 8 по умолчанию; проверка M2 на обеих сторонах это ловит. Записать в профиль: длина CID
   генератора 8 на **обеих** сторонах (TS говорит «на обеих», это верно).
2. [Вывод] IPv6 с extension headers или туннели на пути (6in4, GRE, IPsec, DS-Lite для IPv4) уменьшают PMTU;
   учёт — только опытом (проба), расчёт их не покрывает. Это нормально.
3. [Вывод] `datagram_receive_buffer_size` MUST быть ≥ 1281 + `size_of::<Datagram>()`, иначе принятая полная
   датаграмма закрывает соединение `PROTOCOL_VIOLATION` (`datagrams.rs` 133–135). Значение по умолчанию 1,25 МБ —
   это лимит памяти на соединение на сервере; задать явно, например 64 КиБ ⟂.

**Путь с PMTU < 1347 (IPv4) / 1367 (IPv6).**

- При рукопожатии: Initial дополняются до 1319 (TS §2.1 п. 6), не проходят → наблюдение F1 → T2. Правильно.
- [Вывод, A-TR-10] **Локальный интерфейс с MTU меньше нужного** (клиент внутри другого VPN, привязка с MTU 1280):
  на Linux с `IP_PMTUDISC_PROBE` `sendmsg` вернёт `EMSGSIZE`, `quinn-udp` его журналирует и превращает в `Ok`
  (`unix.rs` 207–222). Снаружи это неотличимо от «чёрной дыры»: F1 и запись в память сети, хотя причина локальна и
  известна заранее. Предложение: до гонки читать MTU интерфейса маршрута к серверу (Linux — `IP_MTU` на
  подключённом сокете; Windows — MTU интерфейса через IP Helper **[Не проверено]**) и при MTU < 1347/1367 не
  запускать T1, сообщая наблюдение «MTU локального интерфейса X», без записи в память сети.
- [Вывод, A-TR-03] **PMTU уменьшился ниже 1347/1367 посреди сеанса.** `quinn` этого не увидит: пакеты с
  полноразмерной датаграммой имеют размер ≤ 1319 = `min_mtu`, а серия потерь с пакетом ≤ `min_mtu` не считается
  подозрительной (`mtud.rs` 465–468). Маленькие пакеты (ACK QUIC, поток управления, короткие IP-пакеты) проходят,
  поэтому критерий «Подозрение» TS §6 («ничего не получено 2 с») **не срабатывает**. Остаётся периодическая
  SizeProbe раз в 10 мин ⟂: до 10 минут крупные пакеты пользователя теряются, TCP-соединения приложений «висят».
  Предложение — §10 п. 3.
- На Linux внешний ICMP PTB не уменьшает размер T1 (`IP_PMTUDISC_PROBE`) — TS M6 подтверждаю по 0.5.16.

**Windows.**

- [Вывод, A-TR-02] `quinn-udp` на Windows ставит только DF (`IP_DONTFRAGMENT`/`IPV6_DONTFRAG`); режима «игнорировать
  кэш PMTU» нет. Если стек Windows по ICMP «fragmentation needed»/PTB запоминает PMTU < 1347 для адреса сервера и
  отвергает отправку большего UDP с DF — **[Не проверено]**, — то поддельный ICMP на пути клиента Windows переводит
  его на T2, и правило M6 для Windows не выполняется. Проверить экспериментом (стенд D или ВМ Windows с
  генератором ICMP; в GitHub Actions Windows — только на loopback, что вряд ли показательно).
- Wintun MTU: задаётся через IP Helper отдельно для IPv4 и IPv6 интерфейса — **[Не проверено]**, документацию
  Wintun не читал. Требование: оба значения = 1280, проверка чтением после установки (тест в GitHub Actions
  Windows выполним: адаптер Wintun там создаётся по плану задания).
- MSS clamping на Windows: штатного аналога правила nftables в клиенте Windows нет **[Предположение]**. [Вывод] Он и
  не нужен для MVP: TS M7 требует clamping на **сервере** в forward для SYN и SYN-ACK через TUN, а это покрывает оба
  направления любого TCP-соединения через туннель, включая транзитное. Локальные TCP-сокеты Windows берут MSS из
  MTU интерфейса Wintun **[Предположение]**. Клиентское clamping (M7, «на клиенте в forward») при этом избыточно и на
  Linux; если в MVP нет пересылки через клиент (вопрос владельцу 11.4 п. 7), его можно убрать.

## 3. T2: TLS 1.3 поверх TCP

**TCP поверх TCP.** [Вывод] Внешний TCP повторяет потерянные сегменты и держит все последующие (HoL для всех
потоков пользователя); внутренний TCP во время восстановления внешнего видит рост RTT и может сделать ложный
повтор по RTO — повтор занимает ту же полосу. Устранить нельзя; можно не усугублять очередями. Количественных
оценок не даю (чужие измерения не переносятся).

**Цепочка буферов на отправке** [Факт-код, §1]: очередь пакетов PHANTOM (64 КиБ ⟂, отбрасывание головы) →
`sendable_tls` `rustls` (до 64 КиБ по умолчанию) → буфер сокета ядра (автонастройка, на Linux до мегабайт —
**[Не проверено]** для целевых ядер). [Вывод, A-TR-07] Отбрасывание головы в очереди PHANTOM бесполезно, пока
нижние буферы большие: пакеты стареют в `rustls` и ядре, где их уже не выбросить, а `Ping`/`Close`/`Activate`
стоят за ними. Нужно:

1. `TCP_NODELAY` на обеих сторонах (иначе Nagle задерживает короткие кадры — ACK внутреннего TCP).
2. `rustls` `set_buffer_limit(Some(16 КиБ ⟂))` на обеих сторонах.
3. Linux: `TCP_NOTSENT_LOWAT` ≈ 16 КиБ ⟂ (не ограничивает окно, ограничивает неотправленное). Windows: аналог —
   **[Не проверено]** (возможно, ideal send backlog); до проверки на Windows — только пункты 1, 2, 4.
4. Запись пачкой: собрать готовые кадры (управление первым) в один буфер до ~16 КиБ и сделать одну запись — одна
   запись TLS на пачку, меньше накладных и системных вызовов. Таймера ожидания «добора» нет.
5. Предел времени «запись стоит» (`write-stall`): если за 30 с ⟂ не удалось отдать ни байта — закрыть соединение.
   Это верхняя граница памяти на мёртвого пира на сервере (очередь + `rustls` + сокет).
6. Linux: `TCP_USER_TIMEOUT` ≈ 30 с ⟂, чтобы ядро не держало соединение с неподтверждёнными данными до ~15 мин
   (значение `tcp_retries2` по умолчанию — **[Не проверено]**). Windows: `TCP_MAXRT` — **[Не проверено]**.
7. TCP keepalive ядра не нужен при прикладном `Ping` 15 с; оставить выключенным, чтобы не было двух механизмов.

**Приём и память.** Длина кадра проверяется до чтения значения (L3, ≤ 1280 для пакета, ≤ 1024 для управления):
буфер приёма PHANTOM ограничен одним кадром; `rustls` держит не больше одной записи TLS (≤ 16 КиБ + накладные)
**[Предположение]** по устройству TLS; окно приёма TCP ограничивает остальное. Итог: память T2 на соединение
ограничена константой, если выполнены пункты 2, 3, 5.

**Живость T2** [Вывод, A-TR-08]. Критерий TS §6 «за 2 с отправлял, ничего не получил» для T2 даёт ложные
срабатывания: при потере на внешнем TCP RTO и экспоненциальный повтор задерживают **все** байты дольше 2 с, хотя
соединение живо. Три `Ping` по 1 с тоже стоят за теми же байтами. Итог — ложный `Reconnecting`, а новое TCP на том
же пути работает не лучше. Предложение: для T2 `T_SUSPECT` ≥ max(10 с ⟂, 4·srtt), пробы `Ping` через 5 с ⟂,
«потеряно» — не раньше 20–30 с ⟂ без единого байта; плюс `TCP_USER_TIMEOUT`.

**Размер кадров.** Один IP-пакет на кадр TLV — верно; объединять в записи TLS (п. 4), но не «склеивать» пакеты в
один кадр. Предел 1280 для пакета T2 одинаков с T1 — обязательное условие M1.

профиль TLS и один ключ клиента, новое соединение — полное рукопожатие (ADR-0007). Внутренние адреса статичны и
берутся из подписанной конфигурации; `Config` нового соединения MUST совпасть (TS §8.2 п. 2) — маршруты и DNS
клиента при переключении не меняются, MTU одинаков (M1). Порядок «кто активен» задаёт `seq`: задержанный `Activate`
старого соединения отвергается (REVERIFY_HIGH §2). Порядок управляющих сообщений определён **внутри** соединения
(один поток QUIC или поток TCP); между соединениями порядок не нужен, кроме `seq`.

**Порядок IP-пакетов на стыке.** [Вывод] IP допускает переупорядочивание и потери, нарушения протокола нет. Окно
переупорядочивания на стыке = задержка очередей старого соединения: для T1 — очередь датаграмм `quinn` (§1), для T2
— очередь PHANTOM + `rustls` + сокет (§3). Внутренний TCP при переупорядочивании ≥ 3 сегментов может сделать ложную
быструю повторную передачу и однократно уменьшить окно; величину не оцениваю — **[Не проверено]**, измерить в
IT-05. Дублей нет: каждый пакет отправляется один раз. Ограничение окна стыка — те же меры, что в §3 (малые
буферы).

**Дыры.**

| № | Что | Последствие | Предложение |
|---|---|---|---|
| H1 | Сервер после `Activate` B принимает ли **восходящие** пакеты из A? TS определяет окно стока 2 с только у клиента; пакеты кандидата сервер отбрасывает (TS §5.4), а у A после `Superseded` статус не задан | Пакеты, отправленные клиентом в A до получения `Activated` (≈ 1 RTT), теряются или, хуже, принимаются без правила | Сервер принимает восходящие пакеты из A до его закрытия (2 с ⟂) с той же проверкой адреса источника по ключу; нисходящие в A не направляет. Записать в TS §5.5 |
| H2 | Утрата `Activated` / `Superseded` без `Activated` (остаток V-03, ARCH §13) не решена | «Чёрная дыра» до тайм-аута | `Superseded{n}` в A, где `n` = ожидаемый клиентом `seq` по B, — неявное подтверждение: клиент переходит на B. Если B при этом потеряно — `Reconnecting` (A через 2 с закроется, повторно активировать A нельзя). Сервер: активное соединение закрылось без замены — маршрут ключа «никуда», нисходящие пакеты отбрасываются со счётчиком до следующего `Activate` |
| H3 | `Superseded{m}`, где `m` не ожидался (второе устройство с тем же ключом, ARCH §4) — TS §5.6 даёт лишь «диагностику», а клиент уходит в `Reconnecting` и снова активируется | Два устройства с одним ключом вытесняют друг друга без конца; лимит 6/мин превращает это в постоянные обрывы у обоих (A-TR-06) | После неожиданного `Superseded`: не реактивироваться автоматически раньше 60 с ⟂; второе такое событие за 10 мин ⟂ → `Halted(DuplicateKey)` с понятным сообщением. Новое значение R в TS §7.1 |
| H4 | Живость старого соединения после `Activated` | Обрыв A в окне стока может быть записан как F4 или вызвать `Suspect` | После `Activated` нового старое не участвует в наблюдениях и в детекторе живости; его `Close(SUPERSEDED)` — норма |
| H5 | `GoAway`, `Ping`, `Pong` в старом соединении после переключения | Неопределённость обработки | Сообщения неактивного соединения, кроме `Close`, игнорируются со счётчиком; ожидание `Pong` по нему снимается |
| H6 | Лимит кандидатов на ключ = 2 (SYS §3.7) против `Switching` с гонкой T1+T2 и фоновой пробы T1 (TS §7.3 п. 3, §7.6) | Третье соединение получит `RESOURCE_LIMIT` (A-TR-12) | Фоновая проба и гонка `Switching` не идут одновременно; либо лимит 3 ⟂. Записать явно |
| H7 | `Activated` задержан лимитом 6/мин, а A за это время потеряно — по TS §7.2 это `Reconnecting`, хотя B живо и ждёт ответа | Лишняя гонка, разрыв | В `Switching` при потере A и живом B ждать `Activated` по B до 15 с ⟂, затем `Reconnecting` |
| H8 | Срок жизни: клиент считает свой (3600 + 0…600 с), сервер — `lifetime_s` из `Config` (600…7200) + 900 | При `lifetime_s` < клиентского срока замену запускает только `GoAway` (за 300 с) — работает, но два источника срока | Клиентский срок = min(свой, `Config.lifetime_s`) − 120 с; одно правило в TS §6 |
| H9 | `Connected(T1)` + смена адреса: при провале rebind TS ведёт в `Switching`, который предполагает живое старое | После смены сети старое часто мертво | Провал rebind/SizeProbe за 3 с → `Reconnecting` с немедленной гонкой (как после пробуждения) |
| H10 | T1: в соединении под полной нагрузкой поток управления может не получить места в пакете (§1: DATAGRAM пишется раньше STREAM) | `Activate`/`Close`/`GoAway`/`Pong` по нагруженному T1 задерживаются неограниченно, пока очередь датаграмм не пуста (A-TR-04) | См. §10 п. 4: очередь PHANTOM над `quinn`, малый буфер `quinn`, при ожидающем управляющем сообщении подача датаграмм приостанавливается до его отправки |
| H11 | SizeProbe идёт в той же очереди DATAGRAM с отбрасыванием головы | Под нагрузкой проба выбрасывается → ложный F3 или ложная «потеря связи» (A-TR-04) | Пробу отправлять только при `datagram_send_buffer_space() ≥ размера пробы` или через `send_datagram_wait`; неуспех пробы под нагрузкой не считать F3, пока не повторён при свободной очереди |

[Вывод] Kill switch при переключении не затрагивается: правила разрешают 5-tuple транспортов к серверу, оба
транспорта к текущему адресу должны быть разрешены всё время `enforcing`; для перехода на запасной адрес правило
добавляется сторожем **до** попытки. Это требование к SYS, проверено только по тексту TS/ARCH.

## 5. Автомат выбора транспорта — упрощения

[Вывод] Автомат TS §7 корректен по сути, но для MVP избыточен в двух местах: фоновые пробы для возврата на T1 и
бюджет переключений. Обе части защищают от проблемы, которую создают сами: частых плановых переходов T2 → T1.

**Обязательно (не упрощать):**

1. Гонка «T1 сразу, T2 через D», где T1 никогда не задерживает T2 (TS §7.3 п. 4) — главный механизм надёжности.
2. Явная активация `Activate{seq}` и «сначала новое» для плановой замены (TS §8.2) — без неё переключение рвёт
   сеанс.
3. Отдельные исходы для ошибок аутентификации/закрепления (`Halted`, без памяти и без автоповторов).
4. Память «T1 непригоден в сети N» по двум наблюдениям с истечением (≤ 60 мин). Без неё каждое переподключение
   снова выбирает T1, который быстрее рукопожатием, но рвётся через секунды (F3/F4) — циклические обрывы.
5. Backoff с разбросом и пол 60 с после трёх неудач (N-18); последовательный перебор адресов (N-17).
6. Обработка сна (`CLOCK_BOOTTIME`) и смены сети; независимость kill switch от автомата (N-5).

**Можно упростить без потери надёжности:**

| Сейчас (TS §7) | Предложение | Почему безопасно |
|---|---|---|
| 9 состояний | 5 основных: `Disconnected`, `WaitNetwork`, `Connecting{round}`, `Connected(T)`, `Halted(R)`; `Suspect` — флаг детектора живости внутри `Connected`; `Switching` — подпроцесс «замена» внутри `Connected`; `Blocked` = `Connecting` с `round ≥ 3` (другой backoff) | Переходы те же; меньше пар «состояние × событие» для тестов. Интерфейс пользователя всё равно показывает 4–5 состояний |
| Возврат T2 → T1: ≥ 60 с на T2, две фоновые пробы T1 с интервалом ≥ 30 с, затем `Switching` | Возврат на T1 **только** при плановой замене (срок жизни, `GoAway`, ≈ раз в час), смене сети и пробуждении: эти события уже запускают гонку с учётом памяти | Убирает фоновые пробы, переход `Connected(T2)` → `Switching(T2→T1)` и связанные тесты. Цена — до ~1 ч на T2 после восстановления UDP; T2 при этом работает |
| Бюджет 4 смены за 10 мин, заморозка на 10 мин | При возврате только на плановой замене бюджет не нужен: смена транспорта происходит только при отказе (в сторону T2) или раз в час. Оставить простой предохранитель «не больше 1 гонки в 10 с ⟂» | Флаппинг больше не порождается автоматом; отказы и так ведут в `Connecting` |
| Ключ сети = HMAC(интерфейс, IP и MAC шлюза) | Оставить; это дёшево. Хранение только в памяти — верно | — |
| Уровни удвоения метки (5, 10, 20, 40, 60 мин) | Оставить, но потолок метки ≤ срока жизни соединения, чтобы следующая плановая замена совпадала с повторной попыткой T1 | Согласует метку с точкой возврата |

[Вывод] При таком упрощении T-06 (анти-flapping) сводится к проверке «переключений не больше, чем отказов + плановых
замен», а T-04 сохраняется.

## 6. Будущее T2/T3 (не MVP)

Сравнение только по надёжности и сопровождению. RFC 9484, 9297, 8441 этим исполнителем **не перечитывались** —
факты взяты из TS §2.2 и §3 (там они помечены как прочитанные).

| Критерий | TLS 1.3/TCP + TLV (T2, MVP) | HTTP/2 extended CONNECT + CONNECT-IP (капсулы) | HTTP/3 CONNECT-IP (T3) |
|---|---|---|---|
| Надёжность канала | TCP-over-TCP, HoL | То же + окна flow control HTTP/2 поверх TCP: ещё один уровень, который может остановить поток (TS §3, «H §3.2») | Как T1 (DATAGRAM), плюс HTTP/3 |
| Восстановление | Новое соединение + `Activate` | То же | Миграция QUIC + `Activate` |
| Объём своего кода | Кодек TLV (общий с T1) | Обвязка `h2` + extended CONNECT + разбор капсул + адресные капсулы RFC 9484 | `h3` (экспериментален по R6) + CONNECT-IP: готового крейта нет (R6) |
| Сопровождение | Минимум зависимостей | Зависимость `h2` **[Не проверено]**: зрелость не оценивал | Высокий риск (экспериментальные крейты) |
| Польза | Работа без UDP | Совместимость с клиентами MASQUE по HTTP/2 — только если ADR-0015 решит в пользу совместимости | То же для HTTP/3 |

[Вывод] По надёжности ни один вариант не лучше T2: TCP-over-TCP и HoL — свойство TCP, а не кадрирования. Другой
резервный транспорт в MVP не нужен. HTTP/2 CONNECT-IP имеет смысл только как часть решения владельца по ADR-0015
(совместимость), и тогда — вместе с T3; формат TLV уже совпадает с капсулами (TS §3), переход — обёртка. Отдельный
порт UDP для T1 у каждого адреса уже предусмотрен конфигурацией (TS §8.1); нового механизма не предлагаю.

## 8. Эмулятор канала в userspace

TEST_STRATEGY §3.3 (L2 через `AF_PACKET` между двумя veth) — правильная основа. Минимальный набор для транспорта:

| Воздействие | Минимум | Нужен для |
|---|---|---|
| Потери | Бернулли по направлению + Гилберт–Эллиот | IT-07, F4 |
| Задержка | Фиксированная + джиттер без переупорядочивания | IT-02, IT-07 |
| Переупорядочивание | Вероятность и глубина | IT-05 (оценка стыка) |
| Ограничение размера | Порог по **длине IP-пакета**, режим «молча» и «ICMP PTB/frag needed от эмулятора» | IT-04, T-01, T-03 |
| «Чёрная дыра» UDP | Drop по протоколу/порту по расписанию | IT-02, IT-03 |
| Сброс TCP | Инъекция RST с верным `seq` по отслеживаемому потоку; обрыв без RST (drop всего потока) | IT-06 |
| Полоса | Token bucket по направлению | IT-07, IT-08, IT-12 |
| Расписание | «время → параметры» | IT-03, IT-04 |

**Обязательная оговорка (A-TR-11).** [Вывод] veth по умолчанию поддерживает GSO/TSO и частичные контрольные суммы
**[Предположение по устройству Linux; на стенде не проверено]**. Тогда `AF_PACKET` видит «суперпакеты» больше MTU:
`quinn` отправляет UDP GSO-пачки до 64 сегментов (`quinn-udp` `unix.rs` 831–857), TCP — TSO-сегменты до 64 КиБ.
Порог MTU, потери «по пакету» и подсчёт переупорядочивания станут неверными, а тест MTU может пройти ложно. Решение:
(а) отключить на обоих veth TSO, GSO, GRO и offload контрольных сумм (на стенде нет `ethtool` — через ioctl
`SIOCETHTOOL` или ethtool-netlink из кода harness), либо (б) читать с `PACKET_VNET_HDR` и сегментировать самому.
Предпочтительно (а). Отключать GSO в самом `quinn` (`enable_segmentation_offload(false)`) нельзя: это меняет
проверяемый продукт.

**Самопроверка (`emu-selftest`), дополнение к TEST_STRATEGY §3.3:**

1. Положительный контроль каждого воздействия **не-PHANTOM** трафиком: UDP-эхо и обычный TCP. Без прохода контроля
   набор недействителен.
2. Порог размера точен до байта отдельно для IPv4 и IPv6 и для UDP-пакета, отправленного с GSO (проверка, что
   суперпакетов нет: максимальная длина кадра на входе ≤ MTU veth).
3. RST-инъекция действительно рвёт обычное TCP-соединение (контроль: `ECONNRESET` у клиента).
4. «Чёрная дыра» UDP не задевает TCP и наоборот.
5. Собственная добавленная задержка и потолок пропускной способности эмулятора измерены и опубликованы; тесты идут
   ниже потолка с запасом.
6. Счётчик потерь `PACKET_STATISTICS` = 0 на входе эмулятора за прогон; иначе прогон недействителен.
7. Тот же seed — тот же набор решений (TEST_STRATEGY §3.3).
