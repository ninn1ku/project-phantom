## 1. C-01 — проверка закреплённого ключа

**(1) Проблема.** Сравнение SHA-256 от SPKI не аутентифицирует: сертификат публичен. Нужна проверка
`CertificateVerify` ключом из этого SPKI; в `rustls` маркер `HandshakeSignatureValid::assertion()`
создаётся без проверки, и ошибочный verifier проходит тесты «чужой ключ отвергается».

**(2) Исправление.** §3.1: нормативный алгоритм из пяти шагов (SPKI, только Ed25519, SHA-256 со
списком, подпись штатной функцией, аутентификация после `Finished` клиента) и тесты (а)–(д), включая
ключевой тест (б) «верный сертификат при чужом приватном ключе». G2 в модели угроз ссылается на тест (б).

**(3) Почему работает и где ломается.** Проверено по исходникам `rustls` 0.23.46:

- [Факт] `ServerCertVerifier` и `ClientCertVerifier` (`src/verify.rs`) содержат `verify_server_cert` / `verify_client_cert`, `verify_tls12_signature`, `verify_tls13_signature`, `supported_verify_schemes`. Маркеры `ServerCertVerified`, `ClientCertVerified`, `HandshakeSignatureValid` — публичные `assertion()` без проверки (`verify.rs` стр. 22–64). Риск C-01 реален.
- [Факт] Клиент вызывает `verify_server_cert(end_entity, …)`, затем `verify_tls13_signature(…, end_entity, cert_verify)` с тем же `end_entity` (`client/tls13.rs` 1180–1217); сервер — `verify_tls13_signature(msg, &certs[0], sig)` (`server/tls13.rs` 1202–1204). Шаги 3 и 4 применяются к одному сертификату — подмены между ними нет.
- [Факт] Штатная функция — `rustls::crypto::verify_tls13_signature(msg, cert, dss, supported_schemes: &WebPkiSupportedAlgorithms)` (`webpki/verify.rs` 192–209): отвергает схемы, не допустимые в TLS 1.3, берёт **первый** алгоритм из `supported_schemes.convert_scheme(dss.scheme)`, разбирает сертификат через `webpki::EndEntityCert` и проверяет подпись. Для raw public keys есть `verify_tls13_signature_with_raw_key` (213–228).
- [Факт] **Перед вызовом `verify_tls13_signature` `rustls` не сверяет `dss.scheme` с `supported_verify_schemes()`**: в приведённых местах `client/tls13.rs` и `server/tls13.rs` такой проверки нет; список используется для объявления (`client/hs.rs` 230, `server/tls13.rs` 765). Требование «допустимая схема одна — Ed25519» исполняется только тем, что проект передаёт в `supported_schemes` (поля `WebPkiSupportedAlgorithms` публичны, можно собрать набор только с `ED25519`), или явной проверкой схемы. Если передать `provider.signature_verification_algorithms` целиком, принятие ECDSA-подписи сдерживается только шагом 2 (ключ Ed25519) и отказом `webpki` для несовместимой пары — [Вывод], поведение `webpki` не проверено.
- [Вывод] Расхождение разборщиков. Шаги 1–3 выполняет код проекта (свой разбор SPKI), шаг 4 — `webpki` (свой разбор того же DER). Если два разборщика по-разному видят SPKI неканонического сертификата, закреплённый отпечаток и ключ подписи могут не совпасть. C-01 п. 5–6 требовал одну функцию и точное сравнение 44 байт SPKI Ed25519 (12 байт префикса + 32 байта ключа); в §3.1 этого нет. Отпечаток вычислять от SPKI, извлечённого тем же разбором, что даёт ключ для подписи (например, `ParsedCertificate::subject_public_key_info()`, который использует `CertifiedKey::keys_match`, `crypto/signer.rs` 190–199 [Факт]), либо проверять SPKI побайтно по фиксированному префиксу.
- [Вывод] Цепочка. §3.1 шаг 1: цепочка «не используется». C-01 п. 1 и тест (г) требовали отказ при наличии промежуточных сертификатов. Игнорирование безопасно для решения о доверии, но оставляет разбор лишних DER-объектов до аутентификации (S-16); тест (г) из ревью в §3.1 не перенесён.
- [Факт] Шаг 5 для T2: при клиентской аутентификации `rustls` не шлёт half-RTT данные (`server/tls13.rs` 472: `!doing_client_auth && send_half_rtt_data`; по умолчанию `false`, `server/builder.rs` 122). Для T1 — нет: в `quinn` 0.11.12 `Connecting::into_0rtt()` на входящем соединении «всегда успешен» и включает 0.5-RTT, «which may be sent before TLS client authentication has occurred» (`connection.rs` 110–125). Шаг 5 выполним, только если сервер никогда не вызывает `into_0rtt`; в §3.1 это не записано.
- [Вывод] Тест (б) выполним: `CertifiedKey::new` не проверяет соответствие ключей, проверку делает только `from_der`/`keys_match` (`crypto/signer.rs` 158–199) [Факт]. Стенду нужен `SigningKey` с чужим ключом, собранный через `CertifiedKey::new`.
- Не перенесены пункты C-01: п. 3 (`verify_tls12_signature` — всегда ошибка), п. 4 (`client_auth_mandatory`, `offer_client_auth` = `true`, `root_hint_subjects` пуст), п. 7 (`assertion()` — в одном модуле, проверка в CI).

**(4) Тесты.** (а)–(д) из §3.1 в обе стороны и в обоих транспортах; плюс: подпись схемой
ECDSA/RSA-PSS при сертификате Ed25519; сертификат с двумя SPKI-представлениями (неканонический DER,
лишние байты после SPKI) — отказ; цепочка из двух сертификатов — отказ; сервер T1 не отправляет
ничего по потокам и DATAGRAM до `Finished` клиента (перехват на стенде); поиск `assertion()` в CI;
мутационный тест: verifier с `HandshakeSignatureValid::assertion()` вместо вызова функции должен
ронять тест (б) — положительный контроль (S-19).

**(5) Результат: достаточно с оговорками.** Главный дефект закрыт: шаг 4 и тест (б) ловят verifier
без проверки подписи. Оговорки — V-01: принудительная схема, единый разбор SPKI, запрет `into_0rtt`.

**(6) Остаточные риски.** Ошибки в `webpki`/`aws-lc-rs` (вне проекта); разбор X.509 до
аутентификации до решения C-10; смена API в `rustls` 0.24 (`rustls-0.24.0-dev.2` в реестре, не изучался).

**Проверено по документам:** вызовы и сигнатуры `rustls`, `quinn`. **Требует практической проверки:**
поведение `webpki` на неканоническом SPKI и несовместимой схеме; отсутствие 0.5-RTT в T1.

## 2. C-02/S-02 — перенос маршрута, `Activate{seq}`

**(1) Проблема.** Маршрут переносился по завершении рукопожатия на сервере: гонка T1/T2 давала
рассогласование, задержанное атакующим рукопожатие уводило маршрут, лимит запирал клиента.

**(2) Исправление.** §4: соединение после аутентификации — кандидат; маршрут переносит
`Activate{seq}` клиента и `Activated{seq}` сервера; `seq` — монотонный 64-битный счётчик клиента на
диске, «с запасом при запуске»; сервер отвергает `seq` не больше последнего; пробы и проигравшие не
активируются; прежнее соединение получает `Superseded`; лимит — на `Activate`, задерживает, не запирает.

**(3) Почему работает и где ломается.**

- [Вывод] Задержанное рукопожатие больше ничего не меняет: без `Activate` кандидат маршрута не получает, а `Activate` внутри TLS-канала другого соединения подделать или перенести нельзя (записи привязаны к ключам соединения). Повтор `Activate` в **другом** соединении невозможен.
- [Вывод] Гонка двух `Activate`: клиент шлёт `Activate(n)` в A, затем `Activate(n+1)` в B; атакующий на пути T2 задерживает TCP-сегменты A. Сервер принимает `n+1`, позже отвергает `n`. Итог совпадает с намерением клиента — счётчик нужен именно для этого.
- [Вывод] **Потеря или откат счётчика на клиенте** (переустановка, восстановление из резервной копии, снимок ВМ, повреждение файла, перенос ключа на новое устройство): `seq` клиента ниже сохранённого сервером — все `Activate` отвергаются, клиент заперт навсегда. «Запас при запуске» помогает, только если запас больше израсходованного после снимка. Механизма восстановления нет, сообщения отказа в наборе §5.4 нет. Исправление без ослабления: сервер отвечает `ActivateStale{last}` внутри аутентифицированного канала, клиент ставит `seq = last + 1` и повторяет; задержанный старый `Activate` по-прежнему ниже.
- [Вывод] Порядок записи не задан: блок значений должен резервироваться и сохраняться (`fsync`) до первой отправки; иначе падение после отправки повторит `seq` (отказ, не уязвимость). Диск только для чтения или полон — активация невозможна; это должно быть явной ошибкой.
- [Вывод] **Рестарт сервера.** Где сервер хранит `last_seq`, не сказано. Хранение в памяти безопасно: перезапуск рвёт все соединения, задержанный `Activate` старого соединения доставить некуда. Перечитывание списка ключей (§4) не должно сбрасывать `last_seq` при живых соединениях — иначе задержанный `Activate` снова проходит. Записать оба правила.
- [Вывод] **Утрата `Activated`.** Сервер активировал B и отправил `Superseded` в A, B оборвался до доставки `Activated`. Клиент получает `Superseded` в A, не имея подтверждения, и шлёт пакеты в A, которое закрывается. Не определено: принимает ли сервер пакеты из A в паузе (C-02 п. 5 в §4 не перенесён), снимается ли маршрут при закрытии активного без замены, может ли клиент повторно активировать A. Без этого возможна «чёрная дыра» до тайм-аута keepalive.
- [Вывод] DoS. Внешний атакующий без ключа `Activate` не шлёт; на пути он и так может рвать соединения. Владелец украденного ключа (RR9) перетягивает маршрут — принято в §4. Очередь задержанных лимитом `Activate` должна хранить одно последнее значение на ключ; число кандидатов на ключ должно быть ограничено — в §4 и §8 этого нет.
- [Вывод] Предельный срок жизни соединения на сервере (§4) должен быть больше клиентского с запасом на плановую замену, иначе сервер рвёт активное соединение до `Activated` нового.
- [Факт] Тело ADR-0007 по-прежнему говорит «сервер переносит маршрут … на новое аутентифицированное соединение»; изменение записано только в приложении. Противоречие в документах.

**(4) Тесты.** Гонка T1/T2 с завершением обоих рукопожатий в любом порядке — один и тот же активный
путь у сторон; задержка `Activate(n)` после `Activate(n+1)` (прокси стенда) — отказ; клиент с
обнулённым и откатанным счётчиком восстанавливается без ручного вмешательства; рестарт сервера и
перечитывание списка при живых соединениях; обрыв B после приёма `Activate` сервером; падение клиента
между отправкой и записью счётчика; серия `Activate` выше лимита — активация задержана, не потеряна;
пробы не меняют маршрут (проверка по таблице сервера); `loom` для таблицы сеансов.

**(5) Результат: достаточно с оговорками.** Три исходных сценария закрыты по построению. Новые
пробелы — восстановление счётчика и неполный автомат (V-02, V-03).

**(6) Остаточные риски.** Перетягивание при краже ключа; DoS на пути.
**Проверено по документам:** логика сценариев. **Требует практической проверки:** всё перечисленное
в (4); формат сообщений — этап 6.

## 3. C-03/S-03 — подписанный конверт конфигурации

**(1) Проблема.** Подпись без версии, срока и адресата: старая подписанная конфигурация отменяла отзыв
ключа и ротацию; автоматический откат при ошибке запуска вызывался атакующим.

**(2) Исправление.** §9: конверт с префиксом назначения, монотонной версией, временем создания,
сроком, адресатом, минимально допустимой версией и байтами конфигурации; якорь доверия — ключ
оператора, установленный вне канала; строгий Ed25519; узел хранит наибольшую версию; откат — только
к предыдущей, не ниже минимальной, только командой оператора; автоматического отката нет.

**(3) Почему работает и где ломается.**

- [Вывод] Повтор старой версии отвергается правилом «не выше принятой»; минимальная версия поднимается при отзыве и отрезает откат командой. Автоматический откат убран — исходный сценарий S-03 закрыт. Ошибка запуска оставляет узел в «запрещено»: это отказ, а не понижение. Нужно записать, что «ошибка запуска» — только локальная ошибка проверки или применения, а не неудача подключения (иначе атакующий на пути переводит клиента в «запрещено» блокировкой нового адреса).
- [Вывод] **Первый запуск и утрата состояния.** Первую версию ставит оператор вместе с якорем. Где и как хранится «наибольшая принятая версия» и как она обновляется вместе с файлом (атомарно, C-03 п. 4), не сказано. При утрате каталога состояния узел примет любую подписанную непросроченную версию — то есть ту, что подсунет атакующий. Нужно: без сохранённого состояния — только ручная установка оператором, как при первичной настройке.
- [Вывод] **Срок действия и часы.** C-03 п. 5 прямо требовал решить, что происходит по истечении срока и при неверных часах; §9 не отвечает. Сценарии: (а) часы в прошлом (сел RTC, подмена неаутентифицированного NTP атакующим T4 в состоянии `off`) — истёкшая старая версия снова «действительна» для узла без сохранённого состояния; (б) часы в будущем — если срок проверяется при каждом запуске, узел отвергает собственную конфигурацию, туннель не поднимается, а в `enforcing` NTP мимо туннеля запрещён (§6.2) — узел заперт до ручного вмешательства; (в) блокирование доставки обновлений (канал доставки по-прежнему не определён, S-03) замораживает узел на версии с отозванным ключом сервера — ограничителем служит только срок, и только если по истечении действует отказ, а не предупреждение. Рекомендация: срок проверять при приёме обновления; для установленной версии — явное правило (отказ с понятной ошибкой либо осознанно «предупреждение» с записью в RR); монотонность версии не зависит от часов и остаётся главной защитой.
- [Вывод] **Компрометация ключа подписи** (RR21). Атакующий подписывает версию `2^64−1` или просто очень большую: узел её принимает и больше никогда не примет законную. Это «сжигание» версии неустранимо без ручного сброса состояния; та же беда от ошибки оператора. Нет идентификатора ключа подписи и правил смены якоря (C-03 п. 3 и п. 7): может ли обновление заменить якорь и только ли подписанное старым ключом — не сказано. Процедура отложена на этап 13, но формат конверта должен содержать `key_id` сейчас.
- [Вывод] **Откат против монотонности.** Откат к N−1 при принятой N противоречит правилу «версию не выше принятой — отвергать». Надо записать: откат не понижает сохранённый максимум, следующий принимаемый номер — больше N; проверяется ли срок у N−1 — решить.
- [Вывод] **Формат.** Собственный префикс вместо готового формата (C-03 п. 2) допустим, но тогда нужна однозначная кодировка полей (длины, фиксированный порядок) и правило «подпись проверяется до разбора TOML, разбираются те же байты» (C-03 п. 1) — в §9 этого нет. Не сказано, подписывается ли серверный список клиентов (C-03 п. 8); от этого зависит, распространяется ли отзыв по §4 на G15.
- [Вывод] `Config` от сервера ограничен (§9) — это C-06, не мешает конверту.

**(4) Тесты.** Помимо тестов G15: утрата файла состояния — обновление по сети не принимается;
повтор версии N, N−1, версии ниже минимальной; конверт с подменённым адресатом, префиксом, `key_id`;
одна подпись над разными разборами (лишние байты, неоднозначные длины); часы ±10 лет при запуске
и при приёме; прерывание записи между файлом и состоянием (`kill -9` на каждом шаге) — состояние
согласовано; команда отката и затем обновление N+1; «сжигание» версии — описанная процедура
восстановления работает.

**(5) Результат: достаточно с оговорками.** Откат и автоматический возврат, составлявшие High,
закрыты монотонной версией и отказом от автоотката. Неопределённые срок, хранение состояния и смена
якоря — новые Medium (V-04, V-05); без них G15 нельзя проверить полностью.

**(6) Остаточные риски.** Компрометация ключа подписи (RR21); заморозка блокированием обновлений до
истечения срока; зависимость от часов. **Проверено по документам:** логика правил §9.
**Требует практической проверки:** атомарность записи, поведение при сбоях часов.

## 4. S-01 — жизненный цикл kill switch

**(1) Проблема.** `enforcing` не переживал перезагрузку; не определены остановка службы и удаление
таблицы сторонним ПО; противоречие «включён по умолчанию» (§9) и `off` в `Disconnected` (§7).

**(2) Исправление.** §6.2: состояние на диске; снимается только `disconnect`; падение, `stop`,
выключение правил не снимают; при загрузке отдельный unit без сетевого кода ставит правила
`Before=network-pre.target` (окно RR15); клиент следит за таблицей и восстанавливает её (RR23).

**(3) Почему работает и где ломается.**

- [Факт] `systemd.special(7)`: `network-pre.target` — **пассивный** target, его «may be pulled in by services that want to run before any network is set up»; «All network management software orders itself after this target, but does not pull it in». Значит, одного `Before=` мало: без `Wants=network-pre.target` порядок может не действовать. Нужен и `DefaultDependencies=no`, иначе unit ждёт `basic.target` [Вывод].
- [Факт] Пакет `nftables` Debian/Ubuntu (контейнер, `nftables` 1.0.9): `nftables.service` имеет `Wants=` и `Before=network-pre.target`, `DefaultDependencies=no`, `ExecStart=nft -f /etc/nftables.conf`, `ExecReload=` то же, `ExecStop=nft flush ruleset`; `/etc/nftables.conf` начинается с `flush ruleset`.
- [Вывод] Следствие: unit восстановления и `nftables.service` оба стоят перед `network-pre.target` без порядка между собой. Если `nftables.service` отработает вторым, он стирает таблицу `inet phantom` **при каждой загрузке** — это не «стороннее ПО» RR23, а штатная служба дистрибутива с настройками по умолчанию. Если демон клиента не запущен (автозапуск выключен, ошибка конфигурации, §9 «запрещено»), восстановить некому, и сеть поднимается без запрета. Окно RR15 становится неограниченным — ровно исходный сценарий S-01. Исправление: `After=nftables.service firewalld.service` (и аналогов) в unit восстановления; при `ExecReload`/`restart` nftables — восстановление через слежение (только при живом демоне). Новое замечание V-06 (High).
- [Вывод] Слежение работает только при запущенном демоне. После `systemctl stop` демона правила остаются (хорошо), но удаление таблицы уже никто не заметит. Нужен либо отдельный лёгкий наблюдатель, либо явная запись в RR23 и G8 «покрыто только при работающем демоне».
- [Вывод] Обновление правил без окна: смена адресов сервера, включение LAN, `Config` после подключения требуют замены таблицы. Нужна одна транзакция `nft -f` (удаление и создание таблицы в одном файле), никогда — два вызова. Синтаксис `destroy table inet …` принимается `nft -c` 1.0.9 [Факт: проверка синтаксиса]; работу ядра и атомарность на стенде **не проверено**.
- [Вывод] Сохранённые правила должны использовать `oifname` (строка), а не `oif`: при загрузке TUN ещё нет, правило с `oif` не загрузится, unit упадёт. Повреждённый файл состояния — ставить минимальную запретительную таблицу (только `lo`), а не пропускать шаг: в §6.2 не сказано.
- [Вывод] Окно загрузки до unit: сеть initramfs (корень по NFS/iSCSI, параметр ядра `ip=`) и службы, не упорядоченные после `network-pre.target`, — вне покрытия; записать в RR15.
- [Вывод] Удаление пакета должно выполнять `disconnect`, иначе пользователь остаётся без сети.
- [Факт] Таблица §7 по-прежнему: `Disconnected` — «Kill switch `off`; обычная сеть»; после падения или перезагрузки процесс в `Disconnected`, а правило — `enforcing`. Нужна строка или оговорка.

**(4) Тесты (на стенде с systemd — в контейнере PID 1 не systemd, §11).** Перезагрузка в `enforcing`
при выключенном автозапуске демона — трафик не выходит; оба порядка запуска `nftables.service` и unit
восстановления; `systemctl restart nftables` и `nft flush ruleset` при живом и остановленном демоне —
время до восстановления и что выходит в окне; `systemctl stop`, `kill -9`, выключение — правила на
месте; смена параметров под нагрузкой — ни одного пакета мимо (захват на внешнем veth); повреждённый
файл состояния; удаление пакета.

**(5) Результат: недостаточно.** Направление верное, но при штатной `nftables.service` Debian/Ubuntu
порядок unit-ов, записанный в §6.2, не гарантирует правила после загрузки; без зависимостей
`Wants=`/`After=` исправление S-01 не выполняет своей цели. После V-06 — «достаточно с оговорками».

**(6) Остаточные риски.** Root-ПО (RR23); окно initramfs; демон остановлен — нет слежения.
**Проверено по документам и локальным файлам:** unit nftables, текст systemd. **Требует практической
проверки:** всё в (4); поведение `firewalld` при запуске и перезагрузке **не проверено**.

## 5. S-04 — цепочки forward/input, conntrack

**(1) Проблема.** Правила покрывали только `output`: транзит контейнеров и ВМ, вход на адрес туннеля
с физического интерфейса (класс CVE-2019-14899), уже установленные соединения не описаны.

**(2) Исправление.** §6.2: `forward` — запрет по умолчанию, транзит только через TUN; `input` — на
адрес туннеля только с TUN, с физических — только ответы соединений с сервером и DHCP/NDP; при
`enforcing` сброс записей conntrack, кроме TUN и сервера; нет общего «established, related — принять».

**(3) Почему работает и где ломается.**

- [Вывод] В nftables `drop` в любой базовой цепочке хука окончателен, а `accept` одной таблицы не отменяет `drop` другой; поэтому разрешения Docker в своих таблицах не открывают обход `inet phantom`. [Не проверено] по первичному тексту в этой работе (wiki nftables недоступна); проверить тестом на стенде с правилами Docker.
- [Вывод] **Мост второго уровня.** ВМ в режиме «мост» с физическим интерфейсом (`br0` с `eth0`) пересылает кадры в семействе `bridge`; хук `inet forward` их не видит, если не загружен `br_netfilter` с `bridge-nf-call-*` [Предположение по устройству netfilter; не проверено]. Такой трафик идёт мимо туннеля, хотя G8 обещает «пересылаемый трафик». Нужно правило в семействе `bridge`/`netdev` или явное исключение в G8 (V-07).
- [Вывод] «Транзит идёт через TUN» неосуществимо без NAT на клиенте: сервер принимает из туннеля только адреса клиента (cryptokey routing, §4), пакеты с адресами контейнеров он отбросит. Нужно либо маскарадинг на TUN, либо формулировка «отбрасывается». Не утечка, а несогласованность.
- [Вывод] `input` по умолчанию `drop` без исключения для ICMP-ошибок, связанных с соединением с сервером, ломает PMTUD внешнего пути (связь с S-09, S-10). Механизм «ответы соединений с сервером» не задан: нужна метка соединения (`ct mark` из `meta mark` в `output`), а не адрес.
- [Вывод] Сброс conntrack — защита в глубину: без общего `established accept` старые соединения и так режутся правилами при каждом пакете. Требуется netlink-удаление записей; инструмент `conntrack` в стенде не указан (§11).
- [Вывод] `SO_BINDTODEVICE` обходит policy routing, но не `output`; тест из S-04 в архитектуру не перенесён. Процесс с `CAP_NET_ADMIN` может поставить метку клиента — получит только адрес и порты сервера (принять как RR).
- [Вывод] CVE-2019-14899: правило по `iifname != TUN` для адреса туннеля закрывает инъекцию; `wg-quick` ставит аналог в `prerouting` с приоритетом raw — до conntrack. В `input` пакет уже создал запись conntrack; на результат не влияет, но расход таблицы conntrack от локальной сети остаётся (Low).

**(4) Тесты.** namespace-контейнер за мостом с NAT — пакеты наружу только через TUN или никуда;
ВМ-мост L2 (veth в мосту с «физическим» интерфейсом) — проверка утечки; Docker-правила + `inet
phantom`; пакет на адрес туннеля с физического интерфейса (TCP SYN, ACK, RST) — нет ответа; соединение,
открытое до `enforcing`, — ни одного пакета после; `SO_BINDTODEVICE` от непривилегированного
процесса; ICMP «fragmentation needed»/«packet too big» к соединению с сервером принимается, к прочим — нет.

**(5) Результат: достаточно с оговорками.** Три исходных пробела закрыты для L3. L2-мост и ICMP — V-07,
V-08.

**(6) Остаточные риски.** Root-ПО с меткой клиента; L2-мост до V-07. **Проверено по документам:**
§6.2. **Требует практической проверки:** все тесты (4); семантика нескольких таблиц.
