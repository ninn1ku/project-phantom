## 1. Уровни тестирования

### 1.1. Unit

- `phantom-crypto`: сборка конфигурации `rustls` читается обратно и сверяется с таблицей профиля (версия, группа, `send_tls13_tickets = 0`, нет хранилища сеансов, `max_early_data_size = 0`, схема подписи только Ed25519, сжатие сертификатов выключено, ALPN `phantom/1`) (C-14). Verifier: вычисление отпечатка, сравнение со списком, отказ для не-Ed25519, `verify_tls12_signature` всегда ошибка (V-01).
- `phantom-config`: проверка схемы (неизвестные поля — ошибка), конверт подписи, правила версии, срока и адресата; роли ключей (C-16).
- `phantom-core`: автомат соединения и выбор транспорта на **виртуальном времени** (`tokio::time::pause` или собственный `Clock`), чтобы тайм-ауты, backoff и гистерезис проверялись детерминированно.
- `phantom-network`: генератор правил nftables — сравнение с эталонным текстом (golden) и проверка `nft -c -f` на стенде A; валидаторы IP-пакетов; форматирование адресов только из типов (S-17).
- Правило: каждый тип ошибки `ConnectError`, `RecvError`, причины `Close` имеет тест, который его порождает; автомат опирается на типы, а не на тексты.

### 1.2. Property-based (proptest)

- Кодеки кадров T2 и управляющих сообщений: `decode(encode(x)) == x`; любые байты → `Ok` либо типизированная ошибка без паники; разбиение потока на произвольные куски даёт тот же результат, что поток целиком.
- Cryptokey routing: пакет принят ⇔ адрес источника принадлежит ключу соединения (G11).
- Конверт конфигурации: любая мутация байта или поля → отказ; повтор и понижение версии → отказ.
- Генератор правил: для любых допустимых значений вывод проходит `nft -c`; имя интерфейса вне шаблона (длина > 15, кавычки, перевод строки, `;`) не принимается типом (S-17).
- Автомат клиента: model-based тест (стратегия «последовательность событий» против эталонной модели): инварианты «в `Probing`, `Connecting`, `Reconnecting`, `Blocked` трафик пользователя запрещён», «`off` только после команды `disconnect`», «`Activate` только у выбранного соединения».
- Регрессии proptest (`proptest-regressions/`) хранятся в репозитории.

### 1.3. Integration

Два узла в одном процессе или на loopback, без TUN и firewall: реальные `quinn`/`rustls`, фальшивый TUN (канал в памяти), встраиваемый эмулятор канала (§3.3) на уровне сокетов. Покрывает G2–G7, G15, сеанс (`Activate`, `Superseded`), лимиты сервера, переключение транспорта. Выполнимо на стенде A.

### 1.4. End-to-end в network namespaces

Полный клиент и сервер с TUN, маршрутами и nftables в отдельных namespaces (§3.2). Покрывает G1, G8–G11, G13, G16 и сценарии устойчивости. Стенд A — для всего, кроме systemd, resolved, сна и реальных сетей.

### 1.5. Fuzz (cargo-fuzz, libFuzzer)

Цель — **каждый разборщик недоверенного или полудоверенного ввода**. Минимальный перечень:

| Цель | Вход | Свойство |
|---|---|---|
| `fz_t2_frame` | поток байтов T2 после TLS, произвольное разбиение | нет паники; длина 0, > предела, неполный кадр — ошибка |
| `fz_control_msg` | одно управляющее сообщение (оба транспорта; кадрирование потока T1) | нет паники; неизвестный тип и превышение длины — закрытие |
| `fz_ip_ingress` | IP-пакет из туннеля (сервер) и из TUN (клиент) | версия, IHL, полная длина ≠ длине кадра, фрагменты, заголовки расширения IPv6 — отказ без паники |
| `fz_spki_pin` | DER сертификата | разбор SPKI проекта; **дифференциально** с разбором `webpki` — одинаковый SPKI или оба отказа (V-01) |
| `fz_rustls_server` | байты ClientHello/рукопожатия в `ServerConnection` с конфигурацией проекта | нет паники; verifier не вызывается с неразобранным сертификатом (S-16) |
| `fz_quinn_endpoint` | UDP-датаграммы во входящий `quinn-proto::Endpoint` с фиктивным временем | нет паники; ограниченная память; ответ ≤ 3× входа до проверки адреса |
| `fz_config_toml` | файл конфигурации | отказ без паники; сообщение об ошибке без содержимого файлов ключей |
| `fz_envelope` | подписанный конверт | подпись проверяется до разбора; разбираются те же байты; неоднозначные длины — отказ |
| `fz_allowlist` | список разрешённых ключей сервера | дубликаты, ключ сервера в списке, пересечение адресов — отказ |
| `fz_state_files` | файлы состояния: `seq`, kill switch, наибольшая версия | повреждённый kill switch → минимальная запретительная таблица |
| `fz_ipc` | сообщения CLI → демон и демон → helper | закрытый перечень операций; неизвестное — отказ (S-07) |
| `fz_nft_gen` | типизированные значения через `arbitrary` | вывод проходит `nft -c`; нет внедрения конструкций |
| `fz_netlink_reply` | ответы netlink, которые читает проект | отказ без паники |

Сторонний код (`rustls`, `quinn-proto`, `webpki`) фаззится через обвязки проекта, а не изолированно: так проверяется именно используемая конфигурация. Корпусы и найденные падения хранятся в репозитории; каждое падение превращается в регрессионный unit-тест. Время fuzz — показатель, не доказательство: G12 формулируется как «проверено N CPU-часов fuzz на версии X» (S-16).

### 1.6. Конкурентность

- `loom`: таблица сеансов сервера (`Activate`, перечитывание списка, закрытие, `Superseded`), очередь задержанных `Activate`, собственные lock-free структуры. [Вывод] `loom` моделирует только свои примитивы синхронизации; код на `tokio` проверяется через выделенное синхронное ядро с абстракцией примитивов, а не целиком.
- ThreadSanitizer: integration и E2E на nightly, `-Zsanitizer=thread` и `-Zbuild-std`. [Факт] Документация rustc: «Using it without instrumenting all the program code can lead to false positive reports»; атомарные fences не поддерживаются. Следствие [Вывод]: C-код `aws-lc-sys` неинструментирован — отчёты на его границе разбираются вручную, допускается файл подавлений с обоснованием каждой записи.

### 1.7. Память

- Miri: модули проекта с `unsafe` (ioctl TUN, передача fd helper) — в той части, что не вызывает FFI; кодеки, verifier-логика, конверт. [Факт] README Miri: «the program has no access to most platform-specific APIs or FFI», «Miri currently does not support networking»; `-Zmiri-native-lib` экспериментален и поддерживает только целые и указатели. Значит, `aws-lc-rs`, сокеты, TUN и netlink вне покрытия Miri; тесты с ними помечаются `#[cfg_attr(miri, ignore)]`, список игнорируемых публикуется.
- AddressSanitizer: `-Zsanitizer=address` с `-Zbuild-std` для integration и fuzz-целей. [Факт] ASan работает с неинструментированным кодом, но хуже находит ошибки — для `aws-lc-sys` желательно собрать C-часть с ASan [Не проверено: поддерживает ли сборочный скрипт `aws-lc-sys` такие флаги].
- RSS и утечки: длительный прогон с периодическим снятием RSS (стенд A — тренд, стенд C — абсолют).

### 1.8. Статический анализ и зависимости

- `cargo fmt --check`; `cargo clippy --all-targets -D warnings`.
- В `phantom-transport`, `phantom-core` и коде разбора сервера: `#![forbid(unsafe_code)]` и запрет `clippy::unwrap_used`, `expect_used`, `panic`, `indexing_slicing`, `arithmetic_side_effects`, `todo`, `unimplemented`, `unreachable`, `dbg_macro`, `print_stdout`, `print_stderr` (имена lint сверить с версией clippy на этапе 8 [Не проверено]). Исключения — `#[allow]` с комментарием, список исключений проверяется скриптом CI.
- `overflow-checks = true` в release-профиле или явная арифметика `checked_*` в разборе.
- `cargo deny check` по `deny.toml` из `06-rust-stack.md` §6; `cargo audit`; `cargo vet` (импорт публичных аудитов, ручной ревью крейтов с одним сопровождающим); сборка только `--locked`.
- Сборочные проверки: feature `tls12` отсутствует в графе (`cargo tree -e features`); провайдер один (`aws-lc-rs`); вызов `HandshakeSignatureValid::assertion()` и аналогов — только в одном модуле; `quinn::Connecting::into_0rtt` в серверном коде не встречается (V-01); тестовый журнал ключей (§2, T-G14-02) отсутствует в release-сборке.

### 1.9. Отсутствие секретов в журналах

Канареечный метод: тест генерирует ключи, известные только ему, прогоняет полный сценарий (подключение, переключение транспорта, ошибки, отказ verifier, ошибка конфигурации, паника в задаче) на всех уровнях журналирования, включая `TRACE` сторонних крейтов, и ищет секреты в stdout, stderr, файлах журналов, сообщениях ошибок и паник в кодировках: сырые байты, hex (оба регистра), base64 (стандарт и URL), PEM, DER, `Debug` массива байтов. **Положительный контроль**: тестовый хук намеренно пишет канарейку в журнал в каждой кодировке — сканер обязан найти все; без этого отрицательный результат не засчитывается.

## 2. Матрица прослеживаемости

Формат: ID | предусловия | действие | ожидаемый результат | уровень | выполним на стенде A.
**ПК** — положительный контроль: тот же наблюдатель в том же прогоне видит событие, когда защита выключена. Отрицательный тест утечки без прошедшего ПК считается **непройденным**, а не зелёным (S-19). Захват всегда на дальнем конце veth, в namespace `net`, а не на интерфейсе клиента (§3.4). Общий ПК для G1, G8–G10: **T-PK-01** — kill switch `off`, генератор (§3.4) шлёт UDP, TCP, ICMP, IPv4, IPv6 global/link-local/multicast, DNS 53/853, mDNS, LLMNR; захват в `net` видит каждый вид. Выполняется в начале каждого E2E-набора утечек; без него набор не запускается.

Есть: root, `CAP_NET_ADMIN`, `CAP_NET_RAW`, `/dev/net/tun`, `nft` 1.0.9, `unshare`/`nsenter`, ядро с `NET_NS`, `VETH`, `TUN`, `NF_TABLES` (`06-rust-stack.md` §3.10 [Факт по отчёту]). Нет: `ip`, `tc`, `tcpdump`, `ping`, `iperf3`, модуля netem, WireGuard в ядре, systemd как PID 1. Создание namespaces на стенде ещё **не выполнялось** [Не проверено] — первая задача этапа 8: smoke-тест harness.

### 3.2. Namespaces и veth из тестового кода

- Топология: `cli` — veth — `net` — veth — `srv` — veth — `inet` («интернет» с эхо-сервисами, DNS-ловушкой). Для G16 и G13 — дополнительный namespace `atk` с veth в `net`.
- Создание: поток ОС на namespace делает `unshare(CLONE_NEWNET)` и держит дескриптор `/proc/self/task/<tid>/ns/net`; [Вывод] `setns` действует на поток, поэтому в каждом namespace свой однопоточный runtime `tokio` на выделенном потоке — смешивать namespaces в одном многопоточном runtime нельзя.
- veth, адреса, маршруты, `lo up`, sysctl (`forwarding`, `accept_ra`) — через `rtnetlink` и `/proc/sys` внутри нужного namespace; перенос конца veth — `IFLA_NET_NS_FD`. Никаких вызовов `ip`.
- Правила в `net` и `srv` — тем же генератором `nft -f -`, что в продукте, либо фиксированными файлами теста.
- Изоляция: каждый тест создаёт свои namespaces с уникальными именами и удаляет их в `Drop`; параллельный запуск `nextest` безопасен. Сторож проверяет, что после набора не осталось интерфейсов и таблиц.

### 3.3. Userspace-эмулятор канала

**Устройство.** В `net` форвардинг ядра выключен. Эмулятор читает кадры с одного veth через `AF_PACKET` (`SOCK_RAW`, `ETH_P_ALL`, привязка к ifindex, `PACKET_IGNORE_OUTGOING`) и пишет в другой. Он работает на уровне L2/L3, поэтому переносит TCP, UDP, ICMP и IPv6 — в отличие от UDP-ретранслятора, который S-19 признаёт непригодным для T2 и ICMP. Для тестов уровня `I` — та же логика поверх сокетов в процессе.

**Возможности** (по направлениям раздельно, с seed для PRNG):

| Воздействие | Параметры |
|---|---|
| Потери | вероятность, модель Гилберта–Эллиота для пачек |
| Задержка, джиттер | базовая, распределение, ограничение «без переупорядочивания» |
| Переупорядочивание | вероятность, глубина |
| Дублирование, мутация | доля пакетов; смещение и значение байта; пересчёт контрольных сумм |
| Ограничение MTU | порог; режим «чёрная дыра» или ответ ICMP «frag needed»/PTB, сформированный эмулятором |
| Ограничение полосы, объёма | token bucket; квота байтов, после которой поток режется |
| Недоступность UDP, сброс TCP | drop по протоколу/порту; инъекция RST; можно делать и `nft` в `net` (`drop`, `reject with tcp reset`, `quota`) |
| NAT rebinding | смена адреса и порта источника клиента |
| Расписание | сценарий «время → изменение параметров» для переходов |

**Валидация самого эмулятора** (набор `emu-selftest`, обязателен перед каждым набором устойчивости): нулевые воздействия — побайтовая прозрачность и нулевая потеря на 10^6 кадров; доля потерь и переупорядочиваний по счёту порядковых номеров попадает в доверительный интервал биномиального распределения для заданного числа кадров; распределение задержки по меткам `CLOCK_MONOTONIC` на входе и выходе (общие часы хоста) совпадает с заданным с точностью, которая публикуется; порог MTU точен до байта; собственный потолок пропускной способности и добавленная задержка эмулятора измеряются и публикуются — тесты работают с запасом ниже потолка; повтор с тем же seed даёт тот же **набор решений** (тайминг планировщика ОС не детерминирован — S-19). Сверка с netem на стенде B по тем же сценариям.

### 3.4. Захват и генерация трафика

- Захват: `AF_PACKET` на дальнем конце veth в `net` (сторона клиента) и в `srv`; кольцевой буфер `PACKET_RX_RING`; запись в pcap для отладки; счётчик потерь сокета (`PACKET_STATISTICS`) обязан быть 0, иначе тест недействителен.
- Классификатор захвата: «разрешено» — только 5-tuple транспорта к серверу; всё остальное — утечка с дампом пакета.
- Генератор утечек: процессы в `cli` с разными правами (root, непривилегированный, с `SO_BINDTODEVICE`, с `SO_MARK`), во вложенных namespaces; виды трафика — как в T-PK-01.
- Вспомогательные сервисы в `inet` и `net`: эхо UDP/TCP, DNS-ловушка, фальшивые DHCPv4/DHCPv6/RA, HTTP-«портал» — собственный тестовый код, без внешних утилит.

|---|---|---|

## 4. Сценарии устойчивости

Для каждого: значение фиксируется и сравнивается с базовым (предыдущий выпуск на том же стенде); порог утверждает владелец. Во всех сценариях идёт классификатор утечек §3.4; **любая** утечка — провал независимо от остальных величин. Стенд A, если не указано иное; абсолютные значения — B/C/D.

| Сценарий | Воздействие | Измеряемые величины |
|---|---|---|
| Потери | 0, 1, 2, 5, 10, 20, 30 %; равномерные и пачками | Пропускная способность и RTT внутри туннеля; ложные `Degraded`/переключения; время до обнаружения при 30 % |
| Задержка, джиттер | Базовая задержка ступенями, джиттер с переупорядочиванием | Время установления T1/T2; выбор транспорта (п.1 §7.1); ложные тайм-ауты keepalive |
| Смена адреса клиента | NAT rebinding; смена сети с новым адресом | T1: время миграции; T2: время пересоединения; потерянные пакеты |
| Недоступность UDP | UDP drop с начала; UDP drop посреди сеанса; прерывистый | Время обнаружения; время до первого пакета через T2; время возврата на T1 после восстановления; число переключений за час |
| Сброс соединений | RST в T2; закрытие QUIC; периодические RST | Время обнаружения и восстановления; потерянные пакеты |
| Отказ сервера, резервный адрес | Основной адрес недоступен по всем транспортам | Время перехода на резервный; запасной адрес не трогается, пока основной работает (п.8 §7.1) |
| Изменение MTU | Снижение и рост MTU пути; «чёрная дыра» и ICMP | Время обнаружения; исход (T2 или `Blocked`); потерянные пакеты |
| DNS-сбой | Резолвер туннеля не отвечает; DNS локальной сети недоступен | Туннель не зависит от локального DNS; приложения получают ошибку, не утечку |
| Длительный простой | Нет трафика 1–24 ч (ускорение через виртуальное время в `I`, реальное время в ночном прогоне) | Живость после простоя; время до первого пакета; периодичность keepalive |
| Перезапуск сервера | `kill -9` и штатный рестарт | Время восстановления; `last_seq` и активация (T-V02-04) |
| Ограничение объёма | Квота байтов, затем drop | Время обнаружения; поведение автомата |
| Сон и пробуждение | Только стенды B (suspend ВМ) и D | Время восстановления; утечки в окне |

Определения: **время обнаружения** — от начала воздействия до смены состояния автомата (по журналу событий с монотонными метками); **время восстановления** — до первого успешно доставленного пакета пользователя после воздействия; **потерянные пакеты** — по порядковым номерам потока-метронома (UDP, фиксированная частота) внутри туннеля. Каждый сценарий повторяется не менее 10 раз с разными seed; публикуются медиана и межквартильный размах.

## 5. Производительность

### 5.1. Методика

- Стенд C; сравниваемые системы на **одном** оборудовании и ядре: WireGuard ядра, WireGuard userspace (реализация и версия выбираются при подготовке стенда и фиксируются; кандидаты — `wireguard-go`, `boringtun`/`gotatun` [Вывод]), PHANTOM T1, PHANTOM T2, «без туннеля» как верхняя граница.
- Фиксируется и публикуется: модель CPU и NIC, прошивка, версия ядра и драйвера, `sysctl` буферов, версии всех программ и `Cargo.lock`, флаги сборки, MTU, конфигурации туннелей.
- Подготовка: governor `performance`, turbo/boost выключен, частота фиксирована; процессы привязаны к ядрам, IRQ NIC — к другим ядрам; SMT выключен или учтён; фоновые службы остановлены.
- Прогрев: отбрасывается начальный интервал каждого прогона (длительность выбирается по пилотным измерениям и публикуется). Повторы: не менее 10 независимых прогонов на точку, с перезапуском процессов.
- Статистика: медиана, межквартильный размах, 95 % доверительный интервал медианы (bootstrap); сравнение систем — по пересечению интервалов; выбросы не удаляются, а показываются.
- Инструменты: `iperf3` (TCP и UDP, один и несколько потоков, оба направления); задержка — собственный UDP/TCP request-response с монотонными метками, распределение до p99.9 (у `ping` нет на стенде A, и ICMP не отражает путь приложения); `perf stat` (циклы, инструкции, переключения контекста), `perf record` для профиля; RSS и `smaps_rollup`; CPU — по `/proc/<pid>/stat` и `perf`.
- Публикация: сырые данные каждого прогона, скрипты подготовки стенда и запуска, журнал версий — в репозитории; итоговые цифры без сырых данных не публикуются.

### 5.2. Что измеряется

| Показатель | Как |
|---|---|
| Пропускная способность | `iperf3`, 1 и N потоков, MTU стенда, оба направления, T1 и T2 |
| Добавленная задержка | request-response без нагрузки и под нагрузкой (bufferbloat), разница с «без туннеля» |
| Время установления | От команды до первого пакета пользователя; **отдельно T1 и T2**; с разделением на TCP/QUIC-рукопожатие, TLS, `Hello`/`Config`, `Activate` |
| Время восстановления | Сценарии §4 на стенде C |
| CPU на единицу трафика | Циклы на байт и на пакет у клиента и сервера при фиксированной скорости |
| Память | RSS сервера на соединение (наклон по 1…N соединений); RSS клиента |
| Масштаб | 1 / 100 / 1000+ клиентов (генератор клиентов в namespaces на отдельной машине): пропускная способность на клиента, задержка p99, CPU и память сервера, время рукопожатия |
| Неаутентифицированная нагрузка | T-G13-01 в абсолютных значениях |
| Обновление ключей | Пауза или потери в момент обновления на обоих транспортах |

### 5.3. Микробенчмарки (criterion)

Кодеки кадров и управляющих сообщений, проверка источника пакета, классификатор, сборка правил, путь пакета TUN → транспорт с фальшивыми концами. Пределы: на стенде A — только относительное сравнение до/после изменения на одной машине (общий CPU, `DEVELOPMENT_ROADMAP.md`); не моделируют системные вызовы, кэш и NIC; не заменяют §5.2. В CI — с предупреждением, не блокирующим слияние, при статистически значимой регрессии.

Требования к производительности формулируются только как измеряемые показатели §5.2. Значения не обещаются до первых измерений на стенде C (этап 12).

## 6. Регрессионные снимки наблюдаемых характеристик

При каждом выпуске (и в CI для изменений `phantom-crypto`/`phantom-transport`) на стенде A снимается и сравнивается с эталоном в репозитории:

- Рукопожатие T1 и T2: число и размеры пакетов и TLS-записей в каждую сторону до первого прикладного пакета; число Initial-пакетов ClientHello; наличие Retry.
- ClientHello: версия, порядок и набор расширений, группы, доли ключей и их длины, схемы подписи, ALPN, SNI (наличие и значение), параметры транспорта QUIC; отпечаток в публикуемом формате (например, JA4 — формат выбрать и зафиксировать) [Предположение о пригодности формата].
- Ответ сервера на зондирование: неаутентифицированный клиент, мусор, TLS 1.2, HTTP-запрос на 443 — что именно и какого размера отвечает сервер.
- Временные характеристики: период keepalive, разброс времени пересоединения (S-20), поведение при простое.

Правило: любое расхождение снимка — непроходной CI до явного обновления эталона с записью причины в журнале изменений. Цель — заметность изменений, а не их запрет (RR1, RR4 приняты).

## 8. Независимый аудит (этап 11)

**Готово до начала:** замороженный тег; спецификация этапа 6 и закрытые Critical/High; эта стратегия и отчёт её выполнения (таблица статусов, время fuzz, покрытие); модель угроз; инструкции сборки и запуска стенда A; список `unsafe` и FFI; `deny.toml`, отчёт `cargo vet`.

**Объём:** интеграция криптографии (сборка конфигурации `rustls`/`quinn`, verifier, отсутствие 0-RTT, tickets, half-RTT, обновление ключей, подпись конфигураций); разбор недоверенного ввода (цели §1.5); привилегированный код (helper, IPC, TUN, netlink, генерация и применение правил); правила nftables (полнота цепочек, порядок, L2-мост, ICMP, жизненный цикл при загрузке); автоматы клиента и сеанса (`Activate`, `seq`, переключение транспорта).

**Формат результатов:** замечания с серьёзностью по шкале `SECURITY_FINDINGS.md`, сценарием, затронутой гарантией и воспроизведением (тест или шаги); отдельно — что аудитор не проверял. Записи заносятся в журнал; Critical и High блокируют релиз до статуса `Verified` (перепроверка не автором исправления); Medium — исправить или принять с обоснованием владельцем.

**Выбор аудитора:** опубликованные отчёты по TLS/QUIC или VPN на Rust; независимость от авторов проекта и зависимостей; готовность публиковать отчёт; отсутствие конфликта интересов; объём в человеко-днях согласуется с владельцем (платный ресурс).

**Чего внутренняя проверка не заменяет:** взгляд не автора на модель угроз и формулировки гарантий; поиск классов ошибок, о которых команда не знает, и неверных допущений о библиотеках; ручной анализ правил firewall и порядка загрузки на реальных дистрибутивах; оценку side channels и обращения с секретами в памяти (RR18).

## 9. Пороги, которые утверждает владелец

После первых измерений, на основании сырых данных: время обнаружения и восстановления для каждого сценария §4; допустимое число ложных переключений в час; максимум потерянных пакетов при переключении и плановом пересоединении; время установления T1 и T2; отношение пропускной способности и CPU на байт к WireGuard ядра и userspace; добавленная задержка (медиана, p99); RSS на соединение; число клиентов, при котором сервер обязан работать; ресурсы при N неаутентифицированных рукопожатиях и время рукопожатия легитимного клиента под этой нагрузкой (G13, S-12); время восстановления таблицы после удаления (RR23); CPU-часы fuzz на цель для выпуска; допустимая регрессия микробенчмарков; длительность ночных прогонов.
