## 1. Методика по метрикам

и утверждаются владельцем (TEST_STRATEGY §9) [Предположение].

### 1.0. Общие правила для всех метрик

**Классы среды** (обозначения в разделах 4–7): **A** — контейнер сессии; **GU** — GitHub Actions Ubuntu; **GW** —
GitHub Actions Windows; **C** — стенд производительности; **D** — реальные сети (TEST_STRATEGY §3.5).

**Абсолютный результат** (число «PHANTOM даёт X на оборудовании Y») — только на стенде C. **Относительный
регрессионный результат** (отношение «коммит B / коммит A» в одном задании на одной машине) — в A и GU. Абсолютные
числа из A, GU, GW не публикуются как показатели проекта и не сравниваются с WireGuard или чужими измерениями
[Факт: NEXT_SESSION_PROMPT §4, последний пункт требований].

**Манифест прогона** (`manifest.json`, обязателен для каждого набора; без него данные не принимаются):

| Группа | Поля |
|---|---|
| Код | commit (A и B для регрессий), хеш `Cargo.lock`, `rustc -vV`, target triple, профиль (`opt-level`, `lto`, `codegen-units`, `panic`, `debug`), `RUSTFLAGS` (отдельно отметить `target-cpu`: для сравнения с WireGuard — одинаковый базовый уровень, без `native`, если не оговорено), версии `rustls`, `quinn`, `aws-lc-rs` и их features, согласованный cipher suite и группа обмена ключами |
| Система | `uname -a`, cmdline ядра, дистрибутив, `lscpu` (модель, microcode, SMT, NUMA), флаги CPU (AES-NI, AVX2, AVX-512, VAES, SHA-NI), clocksource, governor и состояние turbo/boost (или «недоступно» с причиной), список изолированных ядер, привязка процессов и IRQ |
| Сеть | NIC: модель, драйвер, прошивка (`ethtool -i`), offloads (`ethtool -k`: TSO, GSO, GRO, UDP GSO/GRO, checksum), MTU внешнего и туннельного интерфейса, `sysctl` буферов (`net.core.{r,w}mem_*`, `net.ipv4.tcp_{r,w}mem`, `udp_mem`), congestion control внешний и внутренний, qdisc |
| Инструменты | Версии `iperf3`, генераторов, `perf`, эмулятора; для WireGuard — версия модуля ядра или userspace-реализации, `wireguard-tools` |
| Среда | Класс (A/GU/GW/C), для GU/GW — метка runner-а и версия образа (`ImageVersion` из окружения runner-а), облако, если определимо; дата и время UTC |
| Сценарий | Параметры эмулятора/netem, seed, идентификатор успешного `emu-selftest`, длительность прогрева и измерения, число повторов, порядок прогонов |

**Санитизация.** Репозиторий публичный: в манифест и сырые данные не попадают реальные IP-адреса, имена хостов,
идентификаторы аккаунтов провайдера и серийные номера оборудования (CLAUDE.md, «Git»). Адреса стенда записываются
как адреса из документационных диапазонов или как роли (`client`, `server`) [Вывод].

**Формат сырых данных.** Каталог `bench-results/<UTC-дата>_<среда>_<commit>/`: `manifest.json`; `samples.jsonl`
(одна строка — одно наблюдение: `run_id`, `system`, `metric`, `t_mono_ns`, `value`, `unit`, теги); исходный вывод
инструментов без обработки (`iperf3 --json`, `perf stat -x,` CSV, журналы задержек в формате гистограмм HDR или
построчно); скрипт обработки с хешем версии. Итоговые таблицы строятся только скриптом из сырых данных. Место
хранения (в основном репозитории или в отдельной ветке/артефактах выпуска) — вопрос объёма, решается при первом
наборе; TEST_STRATEGY §5.1 требует хранить сырые данные в репозитории [Факт: TEST_STRATEGY §5.1].

**Статистика (общая).** Единица повтора — **независимый прогон** с перезапуском процессов туннеля (TEST_STRATEGY
§5.1: не менее 10 на точку). Внутри прогона отбрасывается прогрев; из прогона получается одно сводное значение
(например, средняя скорость на установившемся участке). По прогонам: медиана, межквартильный размах, 95 %
доверительный интервал медианы бутстрепом; сравнение двух систем — отношение медиан с бутстреп-интервалом отношения
(или сдвиг Ходжеса–Лемана с интервалом); выбросы показываются, не удаляются [Факт: TEST_STRATEGY §5.1 — медиана, IQR,
bootstrap, выбросы; остальное — Вывод]. Порядок прогонов систем — чередующийся или случайный, не «сначала все
прогоны A, потом все B»: дрейф температуры и фона иначе становится разницей систем [Вывод].

### 1.1. Пропускная способность

- **Определение.** Полезная скорость (goodput) внутреннего трафика через туннель в установившемся режиме, бит/с;
  отдельно — пакеты в секунду (pps) для малых пакетов, так как туннели в userspace обычно ограничены числом
  пакетов, а не байтами [Предположение — проверяется измерением].
- **Варианты.** TCP: 1 поток и N потоков (N = числу ядер клиента и 2×), оба направления и двунаправленный режим;
  UDP: развёртка по заданной скорости до «колена» потерь; малые пакеты (UDP payload 64 байта) и полноразмерные
  (внутренний IP-пакет 1280 байт, MTU_TUN фиксирован — TRANSPORT_AND_SESSION §4.1 M1). Внутренний MSS для TCP —
  1240/1220 из-за clamping (M7) [Факт: TRANSPORT_AND_SESSION §4.1].
- **Инструменты.** `iperf3` (`--json`, прогрев через `-O`) для TCP и UDP; собственный генератор pps (UDP с
  порядковыми номерами и метками времени) — нужен также для потерь и задержки; на стенде A `iperf3` нет
  [Факт: TEST_STRATEGY §3.1], в GU ставится из apt [Предположение].
- **Повторы.** ≥ 10 прогонов на точку; длительность прогона и прогрев — по пилоту (ориентир 30–60 с, прогрев
  5–10 с) [Предположение].
- **Сырые данные.** Интервальные отчёты `iperf3` (каждая секунда), CPU обеих сторон за тот же интервал (п. 1.2),
  счётчики отбрасываний (п. 1.5) — без них «скорость» неинтерпретируема.
- **Ловушка.** Если предел — внешняя линия (например, 1 Гбит/с), все системы покажут одно и то же; тогда скорость
  неинформативна и решающей становится метрика 1.2 [Вывод].

### 1.2. Нагрузка на CPU

- **Определение.** CPU-время на единицу трафика (циклы или CPU-нс на байт и на пакет) у клиента и сервера при
  **фиксированной** предложенной нагрузке ниже насыщения всех сравниваемых систем; плюс загрузка при максимуме.
- **Инструменты.** `/proc/<pid>/stat` и `/proc/<pid>/task/*/stat` (utime, stime) для процессов туннеля;
  `/proc/stat` по ядрам (в т. ч. `softirq`) — **обязательно** для сравнения с ядерным WireGuard, потому что его
  работа идёт в softirq и kworker-ах и процессу не приписывается [Вывод]; `perf stat -a` (cycles, instructions,
  context-switches, cpu-migrations), `perf record` для профиля; eBPF (профилирование по off-CPU, задержки
  планировщика) — по возможности.
- **Ограничение стенда A.** В контейнере нет аппаратного PMU: в `/sys/bus/event_source/devices/` только
  `breakpoint msr software tracepoint uprobe`, нет `cpu`, во флагах CPU есть `hypervisor` и нет `arch_perfmon`;
  `perf` не установлен; `kernel.perf_event_paranoid = 2`; ядро собрано с `CONFIG_PERF_EVENTS=y` и
  `CONFIG_BPF_SYSCALL=y` [Факт: осмотр контейнера 2026-11-14]. Следовательно, в A доступны только программные
  события (`task-clock`, переключения контекста) и `/proc` [Вывод].
- **Повторы и статистика.** Как 1.0; CPU усредняется по тому же интервалу, что и скорость.
- **Сырые данные.** Покадровые снимки `/proc` с шагом 1 с, вывод `perf stat -x,`, частота CPU за интервал.

### 1.3. Память

- **Определение.** RSS и PSS процессов сервера и клиента; **наклон** RSS сервера на соединение (линейная
  регрессия по N = 1, 10, 100, 1000 соединений); пик под нагрузкой; память ядра на сокеты.
- **Инструменты.** `/proc/<pid>/smaps_rollup`, `/proc/<pid>/status` (`VmHWM`), `/proc/net/sockstat`; счётчики
  аллокатора или профилировщик кучи в тестовой сборке [Предположение: выбор аллокатора не сделан].
- **Особые сценарии.** IT-08 (клиент перестал читать — память сервера ограничена) [Факт: ACCEPTANCE_TRANSPORT §7];
  длительный простой и RSS-тренд — ночной прогон (TEST_STRATEGY §7, этап 8).
- **Повторы.** Наклон — по ≥ 5 прогонам на каждое N, с интервалом наклона; пик — медиана пиков.
- **Сырые данные.** Временной ряд RSS/PSS с шагом 1 с, число соединений в тот же момент.

### 1.4. Задержка

- **Определение.** Добавленная задержка = RTT через туннель − RTT того же пути без туннеля; распределение (p50,
  p90, p99, p99.9) **без нагрузки** и **под нагрузкой** (параллельный насыщающий поток — bufferbloat)
  [Факт: TEST_STRATEGY §5.2].
- **Инструменты.** Собственный UDP и TCP request-response с `CLOCK_MONOTONIC` на клиенте (RTT меряется одними
  часами, синхронизация не нужна); `ping` не используется — на стенде A его нет и ICMP не отражает путь приложения
  [Факт: TEST_STRATEGY §5.1]. Генератор — **с открытым циклом** (отправка по расписанию, задержка считается от
  запланированного момента): генератор «ждёт ответа — шлёт следующий» занижает хвост при паузах [Вывод].
- **Повторы и объём.** Для p99.9 нужно ≥ 10^5 наблюдений на прогон (≈ 100 наблюдений выше квантиля) [Вывод];
  ≥ 10 прогонов; хвостовые квантили сравниваются по прогонам, а не по объединённой выборке.
- **Сырые данные.** Все наблюдения (или гистограммы HDR без потери точности), метки отправки и приёма.

### 1.5. Потери

- **Определение.** Доля потерянных, дублированных и переупорядоченных внутренних пакетов (а) при заданных потерях
  на внешнем пути (эмулятор/netem), (б) при перегрузке (предложено больше, чем проходит), (в) на стыках —
  переключение транспорта, плановая замена соединения, обновление ключей (TEST_STRATEGY §5.2, IT-03, IT-05).
- **Инструменты.** Поток-«метроном» с порядковыми номерами (ACCEPTANCE_TRANSPORT §7, IT-03, IT-05); счётчики по
  слоям, чтобы знать **где** теряется: `PACKET_STATISTICS` эмулятора, `/proc/net/snmp` (UDP `RcvbufErrors`,
  `InErrors`), счётчики TUN, собственные счётчики PHANTOM (отбрасывание головы очереди и т. п.).
- **Статистика.** Доля потерь — с биномиальным доверительным интервалом (Вильсона или Клоппера–Пирсона); для стыков —
  распределение числа потерянных пакетов по ≥ 20 событиям [Предположение].
- **Сырые данные.** Номера и метки всех принятых пакетов метронома; моменты событий (переключение, замена).

### 1.6. Время установления соединения

- **Определение.** От команды подключения до первого прикладного пакета, **отдельно T1 и T2**, с разбиением на фазы
  (TCP/QUIC-рукопожатие, TLS, `Hello`/`Config`, `Activate`) [Факт: TEST_STRATEGY §5.2]; отдельно — время до
  работающего туннеля при закрытом UDP (гонка T1/T2, IT-02).
- **Инструменты.** Метки `CLOCK_MONOTONIC` на границах фаз в журнале клиента и сервера (диагностическая сборка);
  контроль по захвату пакетов. Измеряется при нескольких RTT, заданных эмулятором (например 0, 50, 150, 300 мс);
  результат выражается и в миллисекундах, и в RTT [Предположение о наборе RTT].
- **Повторы.** ≥ 100 установлений на конфигурацию (дёшево) [Предположение]; медиана, p90, p99.
- **Важно.** Время, кратное таймерам протокола и RTT эмулятора, мало зависит от шума CPU; поэтому в A и GU эта
  метрика пригодна для **функциональных** проверок «уложилось в N RTT/секунд», но не для публикации [Вывод].
- **Сырые данные.** Метки фаз по каждому установлению, параметры эмулятора.

### 1.7. Время обнаружения и восстановления

- **Определение.** Для каждого сценария TEST_STRATEGY §4 и IT-03, IT-04, IT-06, IT-10: (1) время обнаружения — от
  момента воздействия (по расписанию эмулятора) до смены состояния клиента; (2) время восстановления — до первого
  принятого пакета метронома после воздействия; (3) число потерянных пакетов метронома.
- **Масштаб величин.** Таймеры спецификации — секунды (`T_SUSPECT` = 2 с, обнаружение около 5 с, `max_idle_timeout`
  30 с) [Факт: TRANSPORT_AND_SESSION §6], поэтому шум планировщика контейнера (миллисекунды) относительно мал
  [Вывод]. Метрика измеряется в A/GU как функциональный критерий; пороги утверждает владелец (TEST_STRATEGY §9).
- **Часы.** Эмулятор и клиент в разных network namespaces одного ядра пользуются общими `CLOCK_MONOTONIC`
  (time namespaces не создаются) [Вывод].
- **Повторы.** ≥ 20 событий на сценарий в ночном прогоне [Предположение]; медиана и максимум.

### 1.8. Масштабирование числа клиентов

- **Определение.** При N = 1 / 100 / 1000+ одновременных клиентов (TEST_STRATEGY §5.2): скорость на клиента и
  справедливость распределения (индекс Джейна), p99 задержки, CPU и RSS сервера, время рукопожатия; отдельно —
  поток рукопожатий в секунду и время рукопожатия легитимного клиента под неаутентифицированной нагрузкой (G13, S-12).
- **Инструменты.** Генератор клиентов на уровне библиотеки (протокол без TUN, много адресов источника в одном
  namespace) — 1000 отдельных namespaces с TUN непрактичны [Вывод]; на стенде C генератор — на отдельной машине,
  его собственная загрузка CPU записывается: генератор у предела — прогон недействителен.
- **Повторы.** ≥ 5 прогонов на N; кривые с интервалами.
- **Сырые данные.** Пер-клиентные счётчики, ряд CPU/RSS сервера, распределение времени рукопожатий.

### 1.9. Обновление ключей

Пауза и потери метронома в момент обновления ключей на обоих транспортах (TEST_STRATEGY §5.2); метод — как 1.5 (в).
