# Модель угроз PROJECT PHANTOM

**Версия:** 1.0-rc. **Дата:** 2026-11-14.
**Статус:** замечания независимых проверок применены; повторная независимая проверка этой версии не проводилась;
ни одна гарантия тестами не подтверждена.
**Относится к:** `docs/architecture/ARCHITECTURE.md` v0.2 в профиле MVP (транспорты T1 и T2) с решениями,
предложенными в `docs/protocol-spec/CRYPTO_PROFILE.md` (далее CP), `docs/protocol-spec/TRANSPORT_AND_SESSION.md`
(далее TS), `docs/architecture/SYSTEM_AND_LEAK_PROTECTION.md` (далее SYS). Эти решения ещё не внесены в
ARCHITECTURE (статус «предложение»); где гарантия опирается на них, это сказано в столбце «Механизм».
**Основания правок:** `REVIEW_THREAT_MODEL.md` (далее REVIEW, M-01…M-20), `reviews/REVERIFY_HIGH.md` (V-01…V-09),
`research/08-availability-loss-causes.md` (далее R8: K1–K11, O1–O20, F1–F14, M1–M10, R-1…R-8),
`testing/TEST_STRATEGY.md` (далее TST: ID тестов и стенды A–D). Соответствие замечаниям — §11, открытые вопросы — §12.

Система не называется «непробиваемой», «невидимой» или «неблокируемой». Необнаружимость и неблокируемость не
обещаются. Документ описывает, что система защищает, от кого, при каких допущениях и что остаётся незащищённым.

## 1. Система и границы доверия

```
 [оператор: ключ подписи] --B6: подписанные конверты (G15)--> [phantom-server] -> [ОС сервера: NAT,
       |                                                            ^              фильтр назначения] -> Интернет
       | B7: якорь доверия и первая конфигурация                    |
       |     (QR, файл, вручную)                    недоверенная сеть: локальная сеть, провайдер,
       v                                            транзит, хостинг; обновления — через туннель
 [клиент: приложения -> ОС (TUN, маршруты, nftables) <- phantom-guard <-B5-> phantom-netd] --+
                              CLI (A14) -> управляющий сокет сторожа
```

| Граница | Что по одну сторону | Что по другую |
|---|---|---|
| B1 | Процессы PHANTOM клиента и их ключи | Остальные процессы и пользователи устройства |
| B2 | Устройство клиента | Локальная сеть и всё, что за ней |
| B3 | Процесс сервера и его ключи | Остальные процессы сервера, хостинг-провайдер |
| B4 | Сервер | Интернет и конечные сервисы |
| B5 | **Целевая.** Привилегированный сторож `phantom-guard` (TUN, маршруты, nftables, закрытый перечень операций) | Непривилегированный `phantom-netd` (сеть, разбор протокола). Схема предложена SYS §2.5, в ARCHITECTURE не внесена (S-18) |
| B6 | Рабочее место оператора с ключом подписи | Сервер и клиенты (получают только подписанные конверты) |
| B7 | Канал первичной доставки якоря доверия и первой конфигурации (QR, файл, вручную) | Узел, принимающий их без предшествующего состояния. Процедура не описана — §12, M-17 |

Модель «свой клиент — свой сервер»: оператор сервера и пользователь — одно лицо или доверяющие друг другу лица.

## 3. Атакующие

| ID | Атакующий | Возможности | Чего не может (допущение) |
|---|---|---|---|
| T1 | Пассивный наблюдатель на пути | Видит и записывает весь трафик клиента или сервера, в том числе для расшифровки в будущем; расшифровывает QUIC Initial (ключи из DCID, RFC 9001 §5.2) | Взломать TLS 1.3 сегодня |
| T2 | Активный атакующий на пути | Всё из T1; отбрасывает, задерживает, изменяет, повторяет и вставляет пакеты; сбрасывает соединения; подделывает ICMP; блокирует адреса, порты и протоколы; ограничивает скорость и объём; выбирает симптом для диагностики клиента | Получить приватные ключи сторон |
| T3 | Зондирующий | Подключается к серверу с многих адресов, отправляет произвольные и ранее записанные данные | Аутентифицироваться без ключа клиента |
| T4 | Локальная сеть клиента | Всё из T2 на первом участке; DHCP (включая option 121), RA, DNS, ARP/NDP; captive portal; подменяет неаутентифицированное время (NTP), пока kill switch в `off` | Исполнять код на устройстве |
| T5 | Хостинг-провайдер сервера | Видит трафик сервера в обе стороны; доступ к диску и памяти ВМ | — (§7: вне защиты) |
| T6 | Локальный непривилегированный процесс или пользователь клиента | Читает общедоступные файлы и файлы состояния с неверными правами, открывает сокеты (в том числе с `SO_BINDTODEVICE`), обращается к управляющим сокетам | Получить root, `CAP_NET_ADMIN`/`CAP_NET_RAW`, читать память чужих процессов |
| T7 | Чужой клиент системы | Действительный ключ клиента; произвольные данные внутри туннеля к любым назначениям | Знать ключи других клиентов |
| T8 | Конечный сервис | Видит трафик с адреса сервера; отпечатки браузера и приложений | Видеть адрес клиента |
| T9 | Атакующий с квантовым компьютером в будущем | Расшифровывает записанный сегодня обмен ключами на эллиптических кривых | Взломать ML-KEM-768 |
| T10 | Поставщик зависимости или обновления | Подменяет зависимость или обновление конфигурации | Подделать подпись оператора |

Модель наблюдателя T1–T3 — по `docs/research/05-network-resilience.md` §5.3 и R8 §1. T11 угрожает только A7;
защита от него — лишь backoff и резервные адреса (RR24).

## 4. Что система защищает

### 4.1. Гарантии

Кода нет: **каждая гарантия имеет статус «заявлена, тестами не подтверждена»** до прохождения перечисленных тестов
на указанном стенде. Стенды TST: **A** — контейнер разработки; **B** — ВМ с systemd; **C** — стенд
производительности; **D** — реальные сети. Пометка «только вне A» — часть гарантии в контейнере разработки не
проверяется. ID вида T-Gxx-nn и T-S…/T-V… — TST §2; T-KU, T-ID, T-RPK, T-HR, T-AL и подобные — CP; T-01…T-13 — TS §9.

## 5. Что остаётся видимым

### Сети клиента и транзиту (T1, T2, T4, T11)

Полный перечень признаков профиля MVP — R8 §4, **O1–O20, для измерения**: это не утверждение о реакции какого-либо
фильтра. Снимки и метрики — TST §6, R8 M1, M2, M9, M10. Кратко:

- O1, O17, O18: адрес и порт сервера; UDP/443 и TCP/443 на одном адресе; связка «UDP Initial, через ~250 мс TCP SYN»;
  интервалы повторов и переход на запасной адрес.
- O2, O9, O12, O13: версия QUIC, длины CID, транспортные параметры (видны после расшифровки Initial, доступной
  любому), spin bit, пробы PMTU; Initial размером REQ_UDP = 1319 байт (TS §4.2).
- O3–O8: ALPN `phantom/1`; одна группа `X25519MLKEM768` с одной долей 1216 байт; SNI нет при сервере, заданном IP;
  `signature_algorithms` из одной схемы Ed25519; расширения типа сертификата RPK; в T1 ClientHello читает любой
  наблюдатель (RFC 9001 §5.2).
- O10, O11: первый полёт > 1200 байт, client Initial — не меньше двух датаграмм; размеры ответа сервера.
- O14–O16: размеры и время пакетов повторяют внутренний трафик (padding нет); вложенные рукопожатия; ритм keepalive
  и планового пересоединения с двумя соединениями в окне замены.
- O19: ответ на зонд (RR1). O20: «двойная роль» сервера видна сети сервера.
- Мимо туннеля в `enforcing` уходят только: транспорт к серверу; DHCP/NDP/MLD; трафик к LAN при `allow_lan`;
  однократный запрос имени сервера в `off`, если сервер задан именем (G9); трафик портального браузера в окне
  `portal` (RR31). Трафик в состоянии `off` не защищается.

### Хостинг-провайдеру и сетям сервера (T5, T1)

- Адрес клиента и время его соединений.
- Весь трафик сервера к конечным сервисам: адреса назначения, DNS, открытое содержимое там, где приложение не
  шифрует само.
- Корреляция входящих и исходящих потоков по времени и объёму.

### Оператору сервера

- Всё перечисленное для T5, а также соответствие «ключ клиента → внутренний адрес → потоки». Журналы ограничены
  белым списком (G18), но оператор технически может наблюдать трафик. Система не защищает пользователя от
  оператора сервера.

### Конечным сервисам (T8)

- Адрес сервера вместо адреса клиента; для IPv6 — адрес NAT66 сервера, а не постоянный адрес клиента (SYS §3.6).
- Всё, что раскрывает само приложение: cookies, учётные записи, отпечаток браузера, WebRTC, часовой пояс, язык.

### Ключи сторон

- `Certificate` обеих сторон (raw public key) передаётся под ключами рукопожатия (RFC 8446 §4.4); клиент раскрывает
  идентичность только аутентифицированному серверу (RFC 8446 App. E.1) — G17. Пассивный наблюдатель ключей не видит.
  Зондирующий (T3), прошедший фильтр ClientHello, получает открытый ключ сервера.

## 7. Вне рамок

Система не пытается защитить от:

- компрометации конечного устройства, сервера или их операционных систем, включая ПО с правами root (RR7, RR23);
- оператора сервера и хостинг-провайдера как наблюдателей трафика;
- глобального наблюдателя, сопоставляющего трафик на входе и выходе;
- идентификации пользователя конечными сервисами по данным приложений;
- блокировки адреса сервера, «белых списков» и полного отключения связи (доступность не гарантируется, §4.2);
- обнаружения факта использования туннеля (необнаружимость не обещается, RR1, RR4);
- физического доступа и принуждения.

Система не является средством анонимности. На платформах, кроме Linux, kill switch обеспечивает ОС, и G8 там
формулируется отдельно (SYS §6).

## 8. Запреты проекта

- Не использовать чужую инфраструктуру без согласия владельца.
- Не вмешиваться в чужой трафик; диагностические пробы — только к собственному серверу.
- Не выдавать сервер за сторонний сервис: чужие домены и сертификаты не используются.
- Не применять congestion control, игнорирующий потери (BBR из `quinn` запрещён как экспериментальный, TS §0).
- Не собирать телеметрию по умолчанию.
- Не обещать необнаружимость и неблокируемость; эмуляция опубликованных правил фильтрации — только для проверки
  диагностики собственного клиента (R8 §5.2).

## 9. Допущения, требующие проверки

1. **Закрыто:** свойства TLS 1.3 (шифрование сертификатов, защита согласования, forward secrecy при выключенном
   resumption, защита идентичности клиента) сверены с текстом RFC 8446 §4.4, App. E.1, E.2 (REVIEW §0, CP §2.1).
   TLS 1.3 теперь определён RFC 9846 («minor update», CP §0). Непрочитанные части — RR22.
2. Поведение `rustls` 0.23.46 и `quinn` 0.11.12 при профиле CP (нет tickets, нет 0-RTT, одна группа, RPK) выведено
   из исходников и подтверждается тестами этапа 8; RPK в `quinn` и чтение согласованной группы в T1 — CP §5 п. 1, 3.
3. Права и возможности ядра для kill switch и тестов утечек на стенде A — по `06-rust-stack.md` §3.10; создание
   namespaces на стенде A не выполнялось (TST §3.1). Флаг таблицы `persist` есть в ядре 6.18 по исходнику;
   минимальные версии ядра и `nft` дистрибутивов MVP не установлены (§12, M-01).
4. `quinn`: 0.5-RTT на сервере возникает только при вызове `Connecting::into_0rtt()` (запрещён); MTU discovery
   включён по умолчанию, профиль задаёт `min_mtu = initial_mtu = 1319`; ICMP библиотека не обрабатывает (TS §2.1).
   Подтверждается на практике T-G03-03, T-HR1, T-13.
5. DNS: systemd-resolved или обычный `/etc/resolv.conf` (SYS §2.4); права D-Bus resolved не проверены.
6. Состояние узла (`state`, `seq`, `killswitch.state`) записывается атомарно и не утрачивается незаметно; при
   утрате `state` обновления по сети не принимаются (V-05).
7. Часы узла не уходят в будущее за пределы `grace` (RR30); в `off` время может подменить T4, поэтому G15 опирается
   на монотонность версии, а не на часы.
8. Якорь доверия и первая конфигурация доставлены по B7 без подмены (процедура — §12, M-17).
