## 1. Насколько можно доверять исходным отчётам

Сетевая политика среды закрывает прямой доступ к `rfc-editor.org`,
`datatracker.ietf.org`, `noiseprotocol.org`, `wireguard.com`, `usenix.org`,
`rustsec.org` и другим первичным сайтам. Открываются `github.com`, `crates.io`
и веб-поиск. Следствия:

- Большинство утверждений **[Факт]** в отчётах R1–R5 опираются на выдержки из
  поисковой выдачи по первичным страницам, а не на прочитанный полный текст.
  Это слабее, чем чтение источника, и в каждом отчёте оговорено.
- Напрямую прочитаны: спецификации и код в GitHub-репозиториях (Noise rev 34,
  Shadowsocks 2022, Hysteria 2, RFC 4555 по копии), метаданные crates.io,
  локальный клон базы RustSec.
- Lead Architect выборочно сверил утверждения, на которых стоят решения раздела 5
  (перечень — `AGENT_TASKS.md`). Найдены и исправлены три неточности и одно
  противоречие между отчётами (статус `X25519MLKEM768`: R3 считал его черновиком,
  R4 — RFC 10024; верно второе). Одно утверждение подтвердить не удалось
  (требование RFC 9484 о 1280 байт) — оно помечено и вынесено в риски.
- Отчёты прочитаны Lead Architect в части резюме, сводных таблиц, выводов,
  рекомендаций и разделов «Не удалось проверить»; R4 — целиком. Разделы с
  описанием отдельных протоколов в R1, R2, R3, R5 прочитаны выборочно.

**Вывод для процесса.** До этапа 6 (спецификация) нормативные тексты, на которые
спецификация будет ссылаться, должны быть прочитаны целиком. Для этого нужен
доступ к `rfc-editor.org` и `datatracker.ietf.org` (вопрос к владельцу, см.
`PROJECT_STATUS.md`).

найден ли независимый аудит основной реализации.

### Наблюдения

1. **Две группы по криптографии.** Протоколы со своей криптографией на
   общем секрете (Shadowsocks, VMess) не дают forward secrecy и дали
   практические атаки: decryption oracle, replay, partitioning oracle (R2 §2–3,
   R4 §3.3). Протоколы, отдавшие криптографию TLS 1.3 или QUIC, этих классов
   ошибок не имеют, но наследуют видимые признаки TLS (R2 §10).
2. **Формальный анализ есть только у WireGuard и у TLS 1.3.** Доказательства
   WireGuard относятся к протоколу целиком и на протокол «по мотивам» не
   переносятся (R4 §2.3). **[Вывод]**
3. **Независимых аудитов прокси-реализаций не найдено**, кроме Outline (R2,
   резюме п. 7). Из библиотек аудиты есть у `rustls` (2020, версия 0.16) и
   `snow` (2024); у `quinn` не найден (R4 §8).
4. **Стандартизованный и реализованный путь к post-quantum есть только через
   TLS 1.3:** `X25519MLKEM768`, RFC 10024, включён по умолчанию в `rustls` с
   провайдером `aws-lc-rs` (R4 §6.3; сверено по crates.io). У IKEv2 путь
   нормативный, но ML-KEM для него на дату проверки не опубликован как RFC
   (R1, резюме п. 3). У Noise и WireGuard стандартного пути нет (R4 §6.4).
5. **TCP как несущий транспорт везде описан как запасной** (R1, резюме п. 5;
   R3 §2, §8.2): вложенные повторные передачи и congestion control ухудшают
   внутренний TCP. Это деградация производительности, не безопасности.
6. **Туннель L3 в датаграммах QUIC** не имеет вложенной повторной передачи и
   head-of-line blocking (R3 §4, §8.2) — структурно он ближе к WireGuard, чем
   к TCP-туннелям.

## 3. Что известно о фильтрации (кратко, по R5)

Методы фильтрации меняются; у каждого наблюдения в R5 указан период измерений.

| Класс признака | Что показано в публикациях | Следствие для дизайна |
|---|---|---|
| Фиксированные заголовки | OpenVPN опознаётся на трафике провайдера, включая большинство «обфусцированных» конфигураций | Свой узнаваемый wire format — недостаток |
| «Полностью случайный» поток | Блокировка по принципу исключения | «Выглядеть как ничто» — не стратегия |
| Активное зондирование | «Молчащий» сервер выдают тайм-ауты и закрытие соединения | Порт либо отвечает как стандартный сервис, либо закрыт |
| Отпечаток TLS ClientHello | Редкий отпечаток — признак | Знать и отслеживать свой отпечаток |
| Блокировка UDP и QUIC | 3–5 % сетей без UDP; блокировки QUIC, в том числе по SNI | TCP-транспорт на 443 обязателен |
| Вложенное TLS-рукопожатие, RTT между уровнями | Туннель в TLS различим статистически; padding снижает точность, но не устраняет признак | Не обещать неразличимость |
| Блокировка по адресу, лимит объёма, «белые списки» | Смена транспорта не помогает | Несколько адресов; часть случаев — вне возможностей проекта |

Ни одно из рассмотренных решений не закрывает все классы (R2 §10, R5 §1).
Отсюда формулировка цели: PHANTOM не добивается неразличимости, а убирает
дешёвые признаки (свой wire format, молчащие порты, единственный транспорт) и
измеряет результат.

## 4. Разногласие между потоками и его разрешение

**Вопрос.** Что является криптографическим ядром: Noise по образцу WireGuard
(рекомендация R1 §5.1) или TLS 1.3 как единственный слой (рекомендация R4 §10)?

| Критерий | Noise по образцу WireGuard | TLS 1.3 / QUIC |
|---|---|---|
| Требование «не комбинировать примитивы самостоятельно» | Нарушается обвязкой: anti-replay, rekey, cookie, TCP-framing, версии — свои | Выполняется: всё перечисленное — часть протокола и библиотеки |
| Формальный анализ | Отличный, но только для WireGuard «как есть» | Отличный для TLS 1.3 |
| Post-quantum | Стандартного пути нет | RFC 10024, реализовано |
| Второй транспорт (TCP) | Проектировать самим | TLS поверх TCP — штатный режим |
| Защита от downgrade и смена алгоритмов | Нет согласования; миграция — свой механизм | Штатное защищённое согласование |
| Вид на проводе | Свой формат; при фиксированных размерах — сигнатура | Стандартные протоколы (совпадает с выводом R5 §5.1 п. 3) |
| Ответ неаутентифицированному | Молчание (`mac1`) — по R5 само является признаком | Обычный TLS-сервер |
| Объём доверенного кода | Малый | Большой, включая C и ассемблер в AWS-LC |
| Аудит реализаций | `snow` — 2024 | `rustls` — 2020; `quinn` — не найден |
| Производительность | Лучше (по чужим измерениям) | Хуже в userspace, особенно на приёме (R3, резюме п. 4) |

**Решение (ADR-0003, Proposed).** TLS 1.3 — единственный криптографический
слой. Решающие доводы: требование проекта о несамостоятельной криптографии,
готовый PQ-путь, один слой на оба транспорта. Цена принята явно: больший объём
доверенного кода, отсутствие аудита `quinn`, более низкая ожидаемая
производительность.

**Что из рекомендаций R1 сохраняется** — на другом уровне, без своей криптографии:

- cryptokey routing: внутренний адрес клиента привязан к его ключу;
- роуминг с проверкой пути — средствами QUIC (path validation);
- защита от DoS до аутентификации — Retry и anti-amplification QUIC;
- отсутствие разбора цепочек X.509 до аутентификации — закреплённые ключи;
- разделение control plane и data plane;
- жёсткая клиентская политика маршрутизации против TunnelVision и TunnelCrack.

**Что из рекомендаций R1 не принимается:** собственное Noise-рукопожатие,
собственный гибрид «по принципу RFC 9370», обфускация заголовков по образцу
AmneziaWG (эффективность рецензируемо не оценена — R1 §5.1 п. 9).

## 5. Заимствуем и не заимствуем

### Заимствуем

| № | Идея | Откуда | Основание |
|---|---|---|---|
| 1 | Вся криптография канала — TLS 1.3 из зрелой библиотеки | Trojan, Hysteria 2, TUIC, MASQUE | R2 §11, R4 §10 |
| 2 | IP-пакеты в QUIC DATAGRAM, управление — в потоке | MASQUE, Hysteria 2, TUIC | R3 §4, §12 |
| 3 | Единая абстракция «датаграмма, а без ненадёжной доставки — кадр в потоке» | RFC 9297 (capsule) | R3 §12 |
| 4 | Гибридный обмен `X25519MLKEM768`, заданный явно | RFC 10024, `rustls` | R4 §6.3 |
| 5 | Cryptokey routing | WireGuard | R1 §5.1 п. 8 |
| 6 | Гонка транспортов с форой, память «UDP сломан» по сети с backoff, сброс при смене сети | Chromium, curl, RFC 8305 | R3 §10 |
| 7 | Сохранение congestion control на внешнем соединении | RFC 9298 | R3 §8.2 |
| 8 | Консервативный фиксированный MTU, MSS clamping, DPLPMTUD как проверка | RFC 8899, практика | R3 §8.1 |
| 9 | Политика маршрутизации межсетевым экраном, а не только таблицей маршрутов | Выводы из TunnelVision, TunnelCrack | R1 §4 |
| 10 | Аутентификация, привязанная к каналу, вместо bearer-токена | TUIC; стандартная форма — RFC 9729 | R2 §11 п. 2 |
| 11 | Ответ неаутентифицированному клиенту как от обычного сервера на своём домене | Trojan, Hysteria 2 masquerade | R2 §11 п. 4, R5 §5.1 п. 4 |
| 12 | Проверка captive portal до любых выводов о сбое; «аномалия» ≠ «блокировка» | RFC 8908/8910, методика OONI | R5 §3 |
| 13 | SOCKS5 только как локальный интерфейс | RFC 1928 | R2 §11 п. 8 |

Пункты 10 и 11 относятся к транспорту HTTP/3, который в MVP не входит
(раздел 6).

### Не заимствуем

| Идея | Причина |
|---|---|
| REALITY и любая выдача себя за сторонний сервис | Противоречит рамкам проекта |
| Brutal и congestion control без реакции на потери | Вред чужому трафику; сам является признаком |
| Собственный record layer, stream-шифры, ключи из паролей | Закрытые классы ошибок (R2 §2–3, R4 §3.3) |
| Собственное рукопожатие на Noise | Раздел 4 |
| BLAKE3 в роли KDF | Нет стандарта, нет места в TLS и Noise (R4 §5) |
| 0-RTT для данных | Воспроизводимость early data (R3, резюме п. 8) |
| «Полностью случайный» транспорт без оболочки | Известный признак (R5, резюме п. 2) |
| «Молчащий» порт | Известный признак (R5, резюме п. 3) |
| Сжатие в туннеле | Класс атак VORACLE (R1 §5.2 п. 5) |
| Multipath QUIC в прототипе | На дату проверки не RFC (R3 §11) |
| Перехват UDP/443 приложений ради маскировки | Вмешательство в трафик пользователя |
| Подражание ClientHello браузера | Имитация с постоянной ценой поддержки; решение отложено, см. раздел 7 |

## 6. Рекомендуемая архитектура (кратко)

Подробно — `docs/architecture/ARCHITECTURE.md`; решения — ADR-0003…0009.

1. **Криптография.** Только TLS 1.3 (`rustls` + `aws-lc-rs`), только группа
   `X25519MLKEM768`, без 0-RTT и без resumption. Своей криптографии нет.
2. **Идентичность.** Взаимная аутентификация TLS по закреплённым ключам
   Ed25519. Публичный WebPKI в MVP не участвует.
3. **Транспорты MVP.** T1 — QUIC: IP-пакеты в DATAGRAM, управление в одном
   двунаправленном потоке. T2 — TLS 1.3 поверх TCP, порт 443: те же сообщения
   с префиксом длины.
4. **Сеанс.** Сеанс — это пара «ключ клиента → внутренний адрес». Смена
   транспорта или сети — новое полное рукопожатие и атомарный перенос маршрута
   на новое соединение. Отдельных токенов сеанса нет.
5. **Сеть.** L3-туннель через TUN, IPv4 и IPv6, фиксированный MTU, MSS clamping.
6. **Защита от утечек.** Kill switch и DNS — правилами межсетевого экрана и
   policy routing; состояние «заблокировано» при любом сбое туннеля.
7. **Выбор транспорта.** Автомат с гонкой, backoff, гистерезисом и лимитом
   переключений; диагностика сообщает наблюдения, а не причины.
8. **После MVP.** T3 — HTTP/3 с CONNECT-IP на собственном домене, с
   аутентификацией по RFC 9729 и обычным сайтом для остальных клиентов.
