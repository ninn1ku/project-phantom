# 08. Причины потери доступности соединения и их диагностика (поток T1)

**Проект:** PROJECT PHANTOM, этапы 4–6. **Дата:** 2026-11-14.
**Статус:** аналитический отчёт для модели угроз и для логики диагностики клиента. Не руководство по настройке
и не инструкция по обходу фильтрации. Ничто здесь не обещает необнаружимости или неблокируемости.

## 0. Рамки, метод, метки

- Предмет — легальный личный туннель «свой клиент — свой сервер». Задача — понять, почему соединение
  перестаёт работать, как причины различаются по наблюдениям клиента и сервера и что из трафика PHANTOM
  видно снаружи. Рекомендации ограничены диагностикой, измерением и резервированием собственных серверов.
- Основа — `05-network-resilience.md` (далее «05 §N», источники «[05:N]»). Его факты не повторяются; здесь
  уточняются те, что сверены с первоисточником, и добавлено новое.
- Прочитаны локально: RFC 8446 (§2, §4.1.2, §4.2, §4.4, §5.4, D.4, E.1, E.3), RFC 9000 (§14.1, §17.2, §17.4,
  §10.3, §21.14, §8.1 — правило «трёх кратных»), RFC 9001 (§4.3, §5.2, §7, §8.1, §8.2), RFC 9308 (§2, §3.2,
  §8–§11), RFC 10024 (§4.1, §4.2, §6), RFC 8899 (§4.3, §4.6.1), RFC 8305 (§5), RFC 9221 (§3). Исходники
  `rustls` 0.23.46 (`src/client/hs.rs`) и `quinn-proto` 0.11.19 (`config/transport.rs`, `cid_generator.rs`,
  `config/mod.rs`, `lib.rs`) из `~/.cargo/registry/src/`.

**Уточнения по первоисточникам.**

- K2. **[Факт]** RFC 9308 §2: от 3 % до 5 % сетей блокируют весь UDP; приложение поверх QUIC должно либо
  принять отказ, либо уметь переходить на другой транспорт. Там же: при переходе на TLS поверх TCP
  нельзя молча снижать ожидаемую конфиденциальность и целостность. RFC 9308 §8: порт, не сопоставляемый
  с зарегистрированной службой, может приводить к блокировке устройствами, определяющими приложение
  по порту.
- K7, K9. **[Факт]** Zohaib et al. (USENIX Security 2025), полный текст: с 7 апреля 2024 года GFW
  расшифровывает client Initial, фильтрует по SNI, после срабатывания отбрасывает UDP-пакеты тройки
  (IP клиента, IP сервера, порт сервера) 180 секунд; задержка срабатывания — от 60 мс до 7,5 с, более 90 %
  в пределах секунды; состояние потока UDP отслеживалось 60 секунд; Initial, разделённый на несколько
  датаграмм, не собирался (на январь 2025 года). Под умеренной нагрузкой эффективность падала.
- K3, K9. **[Факт]** Wu et al. (USENIX Security 2023), полный текст: пять правил-исключений по первому
  TCP payload (Ex1: среднее число единичных битов на байт ≤ 3,4 или ≥ 4,6; Ex2: первые шесть байтов
  печатные; Ex3: больше половины печатных; Ex4: больше 20 подряд печатных; Ex5: начало как у TLS или
  HTTP). Блокировка — 180 секунд на тройку, только для части диапазонов популярных дата-центров,
  вероятностно (оценка p = 26,3 %). Значения 26,3 % и правило шести байтов, помеченные в 05 как вторичные,
  подтверждены.
- K4. **[Факт]** Xue et al. (USENIX Security 2024), полный текст: протокольно-независимый признак —
  вложенное TLS-рукопожатие; у всех проверенных обфусцированных прокси в стандартной конфигурации доля
  истинных срабатываний выше 70 %; за 30 дней у провайдера обработано более 110 млн потоков при верхней
  оценке ложных срабатываний 0,0544 %; padding повышает трудность незначительно; мультиплексирование
  перспективно, но ограничено. «Голые» VPN-протоколы из оценки исключены как тривиально определяемые —
  то есть **полнотуннельный L3-VPN в этой работе не измерялся**.

## 2. Признаки, различение, измерение, риск ложного вывода

«Клиент видит» — только то, что доступно без внешней точки. «Сервер видит» — счётчики собственного
сервера (с ограничениями журналирования, §5.4). Риск ложного вывода — качественная оценка **[Вывод]**.

| Класс | Клиент видит | Чем отличается от соседних | Различающее измерение | Риск ложного вывода |
|---|---|---|---|---|
| K1 | Нет ответа ни по UDP, ни по TCP на любой порт адреса; иногда ICMP unreachable или RST | От K2: TCP тоже не проходит. От K11 «сервер упал»: сервер не видит входящих SYN/Initial | Сервер: приходят ли SYN и Initial от клиента. Клиент: второй адрес сервера в другом ASN | Высокий без данных сервера: отказ хостинга и блокировка неразличимы для клиента |
| K2 | UDP без ответа, TCP 443 работает | От K1: TCP есть. От K11 «PMTU»: не проходят и малые пакеты | Малый QUIC Initial (минимум 1200 байт, RFC 9000 §14.1) против большого; сервер: пришёл ли Initial | Средний: сеть без UDP (3–5 %) и целевая блокировка QUIC дают одно решение — T2; различать не нужно |

От K9: блок держится и для других соединений той же тройки | Сервер: дошёл ли ClientHello; сравнение TTL и IP ID пакета RST с пакетами сервера **[Предположение: метод из литературы, источник здесь не сверен]** | Средний |
| K4 | Работает минуты или часы, затем обрыв, иногда с последующим блоком адреса | От K8: обрыв не на фиксированном объёме. | K11 | Разное: см. ниже | — | См. ниже | — |

**K11 — обычные сбои подробнее.**

- **PMTU.** **[Факт]** RFC 8899 §4.3: «чёрная дыра» — пакеты определённого размера теряются без
  уведомления; признаки — подтверждённый PTB, серия потерянных проб размера текущего PLPMTU, избыточные
  потери пакетов определённого размера. RFC 8899 §4.6.1: PTB нужно проверять по процитированному пакету и
  по данным, которые трудно знать атакующему вне пути. **[Вывод]** Для T1 это важно вдвойне: ARCH §6.1
  требует UDP payload около 1310 байт; сеть с меньшим путём делает T1 непригодным, и это неотличимо от
  K2 без пробы размера. Поддельный PTB — способ вынудить переход на T2 (S-10).
- **NAT и тайм-ауты состояния.** **[Факт]** RFC 9308 §3.2: состояние UDP в middlebox живёт гораздо меньше,
  чем TCP; по исследованию 2010 года запись может исчезнуть через 30 секунд простоя; часть firewall не
  пропускает пакеты сервера без недавнего пакета клиента. `quinn-proto` 0.11.19 по умолчанию: idle
  timeout 30 с, keep-alive выключен **[Факт: `config/transport.rs`]**. **[Вывод]** Без keepalive простой
  дольше тайм-аута NAT выглядит как внезапная блокировка UDP; различие — восстанавливается ли путь
  после пакета клиента и меняется ли внешний порт (видно серверу).
- **Captive portal.** Признаки и порядок — 05 §3.2, RFC 8908/8910 [05:43]. В `enforcing` портал нельзя
  пройти без описанного исключения (S-08); до прохождения счётчики неудач не должны расти.
- **Отказ сервера.** Процесс не слушает (TCP RST, ICMP port unreachable или тишина при фильтре хостера),
  перегрузка (QUIC Retry, рост RTT), ошибка ключа или конфигурации (TLS alert после полного обмена).
  **[Факт]** RFC 9000 §10.3: после потери состояния сервер может ответить stateless reset. **[Вывод]**
  Stateless reset и TLS alert — положительные признаки «сервер жив, проблема в состоянии или ключах», их
  нельзя смешивать с сетевыми отказами (типы `ConnectError`, ARCH §5.1).
- **Часы.** Неверное время не ломает рукопожатие на закреплённых ключах (сроки сертификата не
  проверяются, ARCH §3.1 шаг 1), но ломает проверку срока подписанной конфигурации (V-04).
- **Смена сети, сон, роуминг.** Дают серии тайм-аутов, похожие на K1/K9; различаются по событиям ОС.

## 3. Дерево диагностики

Правило: идти от дешёвых и невидимых сети проверок к дорогим и раскрывающим. Каждый уровень либо даёт
положительный признак и заканчивает диагностику, либо разрешает следующий. Одно наблюдение — не вывод
(05 §3.4); повтор на ту же тройку — не раньше паузы, превышающей типичное окно K9.

| Уровень | Проверка | Что раскрывает наблюдателю | Итог |
|---|---|---|---|
| 0. Локально, без пакетов | Интерфейс поднят, есть адрес и маршрут по умолчанию; события смены сети и сна; системный статус captive portal; часы в допустимом диапазоне; таблица `inet phantom` на месте; конфигурация проходит `check` | Ничего | Нет сети, портал, сбой хоста — стоп, сообщение пользователю |
| 1. Пассивно | Что уже пришло: ICMP-ошибки к соединению с сервером, RST, TLS alert, stateless reset, QUIC Retry | Ничего нового | Положительный признак причины K11 или «сервер жив» |
| 2. Один транспорт, текущий адрес | Повтор T1 после паузы; полный Initial и ответ сервера | Адрес, порт, факт QUIC, ClientHello (Initial расшифровывается любым, RFC 9001 §5.2) | Работает — стоп; нет ответа — уровень 3 |
| 3. Второй транспорт, тот же адрес | T2: TCP SYN на 443, затем TLS | Адрес, порт 443, ClientHello T2, связка «UDP, затем TCP» | TCP нет — K1/K10 вероятнее; TCP есть, TLS рвётся — K3/K7; TLS есть, T1 нет — K2/K11-PMTU |
| 4. Проба пригодности на рабочем транспорте | Проба меньшим пакетом; передача объёма выше известных порогов (05 §3.4) и оценка скорости | Объём и ритм проб | Обрыв по размеру — PMTU; по объёму — K8; низкая скорость — K8 или перегрузка |
| 5. Данные сервера | Оператор сверяет агрегированные счётчики сервера: приходили ли SYN, Initial, ClientHello от клиента | Ничего в сети клиента | Различает «не доходит до сервера» и «не возвращается к клиенту» |
| 6. Запасной адрес | Только когда на текущем не работает ни один транспорт (ARCH §7.1 п. 8) | Запасной адрес и связь двух адресов одним клиентом | Работает — K1 для основного вероятен |
| 7. Другая сеть | Только действием пользователя | Местоположение пользователя в новой сети | Различает политику сети и состояние сервера |

**Замечания к дереву.**

- **[Вывод]** Уровень 5 — главное преимущество модели «свой сервер»: оператор владеет второй точкой
  измерения, которой у клиентов массовых сервисов нет. Счётчики должны быть агрегированными и
  кратковременными (A9, S-14) и включаться оператором; адреса клиентов в постоянный журнал не пишутся.
- **[Вывод]** Уровни 2–3 и 6 раскрывают наблюдателю структуру конфигурации: набор транспортов, порядок,
  запасные адреса. Это цена диагностики; ограничивается частотой и бюджетом проб (RR17).
- **[Вывод]** Активный атакующий на пути может вызвать любой симптом уровней 2–4 и тем самым направлять
  диагностику: блокировкой основного адреса заставить раскрыть запасной; поддельным PTB — перейти на
  T2; сбросом TCP — держать клиента в `Reconnecting`. Дерево должно иметь лимиты, а не только порядок.
- Клиент сообщает наблюдения, а не причины (ARCH §7.2). Таблица §2 — для разработчика и оператора, а не
  текст для пользователя.

## 4. Наблюдаемые снаружи характеристики трафика PHANTOM (профиль MVP)

Перечень для **измерения**. Ни одна строка не утверждает, как на признак реагирует конкретный фильтр.

## 5. План измерений на стенде

### 5.1. Стенд и его пределы

Network namespaces с veth, userspace-ретранслятор между «клиентской сетью» и «сервером» (ARCH §11).
Без netem и `tcpdump`: захват — через `AF_PACKET`-сокет из тестового кода или счётчики `nft`. Ретранслятор
уровня UDP не воспроизводит ICMP — для PMTU и PTB нужен пересыльщик уровня IP (S-19). Измерения
производительности здесь непригодны; измеряется поведение.

### 5.2. Внесённые неисправности

Каждая — независимая конфигурация ретранслятора; проверяется, какое наблюдение выдаёт клиент и что он
делает. Эмуляция опубликованных правил служит только проверке диагностики собственного клиента.

| ID | Неисправность | Ожидаемое наблюдение клиента | Ожидаемое действие |
|---|---|---|---|
| F1 | Отброс всего UDP | «UDP: нет ответа; TCP 443: работает» | T2, память по сети |
| F2 | Отброс первого UDP-пакета ≥ 1001 байт с заголовком QUIC v1 и состояние 420 с на четвёрку (по [05:10], вторично) | То же, что F1 | То же; без повторов T1 чаще окна |
| F3 | Отброс всего к адресу | «Нет ответа ни по UDP, ни по TCP» | Пауза, затем запасной адрес; не раньше лимита |
| F4 | RST в обе стороны после первого сегмента ClientHello T2 | «TCP соединяется, TLS обрывается сбросом» | Не считать отказом сервера |
| F5 | Обрыв соединения после 16 КБ данных | «Рукопожатие есть, данные останавливаются на ~16 КБ» | Критерий пригодности не выполнен |
| F6 | Ограничение 150 кбит/с | «Скорость ниже порога» | Сообщение; без циклических переключений |
| F7 | Отброс пакетов > 1300 байт, с PTB и без | «Малые проходят, большие нет» | T1 непригоден в этой сети; T2 |
| F8 | Поддельный PTB без связи с соединением | Нет изменения | PTB отвергнут (RFC 8899 §4.6.1) |
| F9 | Сброс состояния NAT после 30 с простоя | Восстановление после пакета клиента | Без переключения транспорта |
| F10 | Captive portal: перехват HTTP и DNS | «Портал» | Счётчики неудач не растут |
| F11 | Сервер остановлен: RST/ICMP; затем тишина | «Сервер не слушает» против «нет ответа» | Разные наблюдения |
| F12 | Остаточная блокировка 60/180/420 с; вариант — повтор продлевает таймер [05:20] | «Нет ответа N с, затем работает» | Нет повторов к той же тройке внутри окна |
| F13 | Случайные потери 1/5/20 %, задержка до 1 с | «Потери» | Нет ложного переключения при 1–5 % |
| F14 | Смена «сети» (новый шлюз) и «сон» | Новая сеть | Память по сети не переносится |

### 5.4. Критерии приёмки (предложение; числа задаёт владелец)

- M5 ≥ максимальному задокументированному окну K9 для той же тройки; повтор раньше — дефект.
- M6 не больше необходимого: запасной адрес не появляется ни в одном прогоне без F3.
- M7 = 0 при потерях до 5 % на интервале теста; M8 — каждая F классифицируется верно не реже чем в
  заданной доле прогонов, F5 и F7 различаются всегда.
- M2: любое изменение отпечатка между выпусками фиксируется и объясняется в журнале выпуска.
- Все отрицательные тесты имеют положительный контроль (S-19): прогон без неисправности проходит.
- Серверные счётчики для уровня 5 дерева содержат только агрегаты; проверка журнала по белому списку
  полей (S-14).

## 6. Что проект принципиально не устраняет и что из этого следует

**Не устраняется** **[Вывод]**: блокировка адреса, префикса или ASN сервера (K1); «белый список» и
отключение связи (K10); ограничения, применяемые ко всему зарубежному трафику (K8 в широкой форме);
статистическое выделение туннеля (K4); раскрытие факта сервиса одним зондом в MVP (O19, RR1). Смена
транспорта от K1 и K10 не помогает (05 §1.6). При K10 связи с собственным сервером нет, и клиент должен
сообщить это, не перебирая адреса.

**Требования к резервированию серверов** (предложение для ARCH §7.1, §9 и модели угроз):

1. **R-1.** Не меньше двух адресов у разных провайдеров, в разных ASN и префиксах; один провайдер с двумя
   адресами не защищает от K1 по диапазону.
2. **R-2.** Ключи идентичности: либо общий ключ для всех серверов (компрометация одного — всех), либо
   отдельный на сервер. ARCH §3.2 разрешает клиенту «до двух» закреплённых значений для ротации — при
   отдельных ключах этого не хватит. Решение нужно записать явно.
3. **R-3.** Новые адреса доставляются подписанным конвертом (G15) по работающему туннелю; если все адреса
   недоступны, канала доставки нет — нужна внеполосная процедура оператора. Канал доставки не определён
   (S-03).
4. **R-4.** Запасные адреса не проверяются клиентом, пока основной работает (ARCH §7.1 п. 8); их исправность
   проверяет оператор собственным мониторингом из своей сети.
5. **R-5.** Лимит раскрытия: за эпизод не больше одного нового адреса; следующий — после паузы. Атакующий,
   блокирующий основной адрес, иначе перечисляет все запасные (§3).
6. **R-6.** Не размещать сервер на адресе, общем с чужими сервисами: блокировка адреса задевает соседей
   (05 §4).
7. **R-7.** Запасной сервер выдерживает нагрузку всех клиентов; сеансовое состояние (`last_seq`, список
   ключей) согласовано между серверами — иначе клиент, перешедший на другой сервер, упрётся в V-02.
8. **R-8.** Сообщение пользователю при исчерпании адресов — наблюдение («ни один адрес не отвечает ни по
   одному транспорту в этой сети»), без слова «заблокировано».
