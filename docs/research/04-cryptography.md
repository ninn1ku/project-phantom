## Резюме

1. **[Вывод]** Рекомендуемый базовый вариант — **(B): TLS 1.3 как единственный криптографический слой** (QUIC через `quinn` + TLS-over-TCP через `rustls`, провайдер `aws-lc-rs`), взаимная аутентификация по закреплённым ключам (pinning), гибридный обмен `X25519MLKEM768`, 0-RTT выключен. Это единственный из трёх вариантов, где путь к post-quantum стандартизован и уже реализован в библиотеке без собственного комбинирования примитивов.
2. **[Факт]** Гибрид `X25519MLKEM768` для TLS 1.3 опубликован как RFC 10024 (август 2026), общая конструкция гибридов — RFC 9954 (июль 2026) [29][30]. В `rustls` (ветка 0.23, провайдер `aws-lc-rs`) он включён и по умолчанию стоит первым в списке групп (feature `prefer-post-quantum`) [31].
3. **[Факт]** Noise Protocol Framework (rev 34, 2018) не содержит согласования версий и алгоритмов, не определяет транспорт для датаграмм, anti-replay, расписание rekey и защиту от DoS — всё это остаётся на приложении [1]. WireGuard доопределил эти части, и именно WireGuard целиком (а не «Noise IK вообще») имеет символические и вычислительные доказательства [7][8][9].
4. **[Вывод]** У варианта (A) нет стандартизованного PQ-пути: PSK-слот WireGuard требует отдельного протокола доставки PSK (Rosenpass, схема Mullvad), `hfs`-расширение Noise осталось черновиком 2018 года, PQNoise — научная работа без спецификации в составе Noise [47][49][51][54]. Любой из этих путей в собственном протоколе — это самостоятельное комбинирование, запрещённое требованиями проекта.
5. **[Факт]** Аудиты Rust-библиотек неравномерны: `rustls`/`ring`/`webpki` — Cure53, 2020 (версия 0.16) [35]; `snow` — Trail of Bits, 2024-01, 10 замечаний [36]; RustCrypto `aes-gcm`/`chacha20poly1305` — NCC Group, 2020, 5 человеко-дней [39]; RustCrypto `ml-kem` независимого аудита не имеет [40]; для `quinn` независимый аудит не найден.
6. **[Факт]** Модуль AWS-LC 3 (static) имеет сертификат FIPS 140-3 № 5314 (активен, включает ML-KEM) [34]. Это единственный путь к FIPS среди рассмотренных Rust-стеков.
7. **[Вывод]** Вариант (C) (TLS/QUIC снаружи + Noise внутри) оправдан только если внешний TLS терминируется недоверенным посредником; иначе он удваивает поверхность ошибок без прироста гарантий.
8. **[Вывод]** Главные остаточные риски рекомендации: давность аудита `rustls`, отсутствие аудита `quinn` и DoS-уязвимости 2026 года в `quinn-proto` [45], отсутствие PQ-аутентификации, видимость TLS-сервера для активного зондирования, утечки метаданных.

## 2. Noise Protocol Framework

### 2.1. Назначение и устройство

**[Факт]** Noise — framework для построения протоколов согласования ключей на основе Diffie-Hellman; актуальная ревизия спецификации — 34 (11 июля 2018) [1]. Протокол задаётся именем вида `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`: handshake pattern + DH + AEAD + hash. Спецификация оценивает каждое сообщение по трём шкалам: source (аутентичность отправителя, уровни 0–2), destination (конфиденциальность, уровни 0–5) и identity hiding (10 уровней) [1][4].

### 2.2. Паттерны, релевантные PHANTOM

| Pattern | Что известно заранее | Round trips до полной защиты | Identity hiding (кратко) | Замечания |
|---|---|---|---|---|
| `NK` | static ключ responder | 1 | initiator анонимен | Нет аутентификации клиента на уровне Noise |
| `XX` | ничего | 1.5 | static ключи обеих сторон передаются зашифрованно | Взаимная аутентификация без предварительного знания ключей; нужен внешний механизм доверия |
| `XK` | static ключ responder | 1.5 | static initiator передаётся в 3-м сообщении, после аутентификации responder | Лучшая защита идентичности initiator |
| `IK` | static ключ responder | 1 | static initiator шифруется в 1-м сообщении только на static ключ responder | Основа WireGuard |
| `IKpsk2` | static responder + PSK | 1 | как `IK` | PSK подмешивается после второго сообщения; PQ-слот WireGuard |

**[Факт]** Для первого сообщения `IK` спецификация и Noise Explorer дают одинаковую картину: payload зашифрован только на DH с static ключом получателя — «encryption to a known recipient, forward secrecy for sender compromise only, vulnerable to replay»; последующая компрометация static ключа responder раскрывает это сообщение (включая static ключ initiator) [1][2].
**[Факт]** Для паттернов, начинающихся с `K` или `I`, responder получает только «weak» forward secrecy для своих transport-сообщений, пока не получит transport-сообщение от initiator [1]. Следствие для дизайна: responder не должен отправлять чувствительные данные до первого сообщения initiator (в WireGuard эту роль играет первое data-сообщение/keepalive как key confirmation [7]).
**[Не проверено]** Числовые уровни из таблиц спецификации (по памяти, §7.7–7.8): `IK` — сообщения (source, destination) = (1,2), (2,4), далее (2,5); identity hiding initiator 4, responder 3. `XK` — (0,2), (2,1), (2,5); initiator 8, responder 3. `XX` — (0,0), (2,1), (2,5); initiator 8, responder 6. `NK` — (0,2), (2,1), (0,5); responder 3. Перед использованием в protocol-spec сверить с первичным текстом [1].

### 2.3. Формальный анализ

- **[Факт]** Noise Explorer (Kobeissi, Nicolas, Bhargavan; EuroS&P 2019) автоматически генерирует модели ProVerif для произвольных паттернов и публикует результаты по каждому сообщению [2][3].
- **[Факт]** «A Spectral Analysis of Noise» (Girol и др., USENIX Security 2020) — анализ в Tamarin, уточняющий уровни из спецификации [4].
- **[Факт]** Dowling, Rösler, Schwenk — модель fACCE и вычислительные доказательства для паттернов Noise (ePrint 2019/436) [5].
- **[Факт]** Noise* (ePrint 2022/607, IEEE S&P 2022) — библиотека верифицированных реализаций Noise [6]. Это не Rust-библиотека; в стек PHANTOM напрямую не ложится **[Вывод]**.
- **[Факт]** WireGuard: (i) символическое доказательство в Tamarin (Donenfeld, Milner; на сайте WireGuard работа обозначена как draft, датирована 7 июня 2018) [7]; (ii) Dowling и Paterson (ACNS 2018, ePrint 2018/080): протокол в исходном виде не укладывается в модель eCK, потому что key confirmation является частью транспортного слоя; доказательство дано для минимально изменённого варианта с дополнительным сообщением [7][9]; (iii) Lipp, Blanchet, Bhargavan (EuroS&P 2019): первое механизированное вычислительное доказательство в CryptoVerif для протокола целиком, включая transport data [8].

**[Вывод]** Доказательства относятся к конкретным протоколам. Собственный протокол «по мотивам WireGuard» (другой паттерн, другой framing, TCP-режим, иные таймеры) наследует только общий анализ паттерна, но не доказательства WireGuard.

### 2.4. Ограничения Noise, значимые для VPN

1. **[Факт]** Нет согласования версий и алгоритмов внутри протокола: имя протокола фиксировано, выбор передаётся вне Noise [1]. **[Вывод]** Любой переход (в том числе на PQ) требует собственного механизма версионирования и собственной защиты от downgrade.
2. **[Факт]** Nonce — 64-битный счётчик; значение 2^64−1 зарезервировано (используется в `REKEY`); `REKEY` меняет только ключ, поэтому при 2^64 сообщений нужен новый handshake [1].
3. **[Факт]** Встроенный транспорт рассчитан на упорядоченную доставку без потерь; для датаграмм нужны явные nonce и собственная защита от replay на стороне получателя — спецификация это допускает, но не определяет [1].
4. **[Вывод]** Rekey по времени/объёму, anti-replay window, защита от DoS (cookie), roaming, обработка одновременных handshake — вне Noise. Это и есть основная часть работы WireGuard поверх `IKpsk2`.
5. **[Не проверено]** Спецификация (§12.1, по памяти) для 25519 не требует отвергать нулевой результат DH и даже не рекомендует такую проверку ради единообразия реализаций; безопасность обеспечивается хешированием transcript. См. раздел 4.1.

## 3. AEAD: ChaCha20-Poly1305 и AES-256-GCM

### 3.1. Назначение и гарантии

**[Факт]** Оба алгоритма — AEAD с требованием уникальности пары (key, nonce); для AES-GCM повтор пары катастрофичен и для конфиденциальности, и для целостности [15]. ChaCha20-Poly1305 определён в RFC 8439, AES-GCM — в NIST SP 800-38D **[Не проверено: тексты не открывались]**.

### 3.2. Лимиты использования ключа

- **[Факт]** RFC 9001 (QUIC-TLS), §6.6: для `AEAD_AES_128_GCM` и `AEAD_AES_256_GCM` confidentiality limit — 2^23 пакетов, integrity limit — 2^52 неверных пакетов; при достижении лимита конфиденциальности требуется key update, при достижении лимита целостности — закрытие соединения [13].
- **[Не проверено]** Для `AEAD_CHACHA20_POLY1305` в RFC 9001: integrity limit 2^36 неверных пакетов, confidentiality limit выше числа возможных пакетов (подтверждено только рабочими материалами QUIC WG, не текстом RFC).
- **[Факт]** `draft-irtf-cfrg-aead-limits` остаётся Internet-Draft CFRG (не RFC): ревизия -11 (декабрь 2025) истекла в июне 2026, зеркала показывают ревизию -12 от августа 2026 со сроком до февраля 2027 [14]. Документ даёт формулы single-user и multi-user лимитов; при rekeying следует применять multi-user лимиты [15].
- **[Факт]** WireGuard: `REKEY_AFTER_MESSAGES` = 2^60, `REKEY_AFTER_TIME` = 120 с, `REJECT_AFTER_TIME` = 180 с, `REJECT_AFTER_MESSAGES` = 2^64 − (размер окна) − 1 [10][11]. **[Вывод]** При rekey каждые 2 минуты лимиты AEAD на практике недостижимы; ограничителем служит время.

### 3.3. Известные атаки и ошибки интеграции

- **[Факт]** Ни AES-GCM, ни ChaCha20-Poly1305 не являются key-committing: partitioning oracle attacks (Len, Grubbs, Ristenpart; USENIX Security 2021) позволили, в частности, восстанавливать пароли серверов Shadowsocks [16]. **[Вывод]** Опасно только там, где ключ AEAD выводится из низкоэнтропийного секрета или выбирается атакующим; в handshake с эфемерным DH/KEM это неприменимо, но запрещает схему «пароль → ключ AEAD → проверка расшифрованием» в любом транспорте PHANTOM.
- **[Факт]** `aes-gcm` (RustCrypto): RUSTSEC-2023-0096 — `decrypt_in_place_detached` оставлял расшифрованный plaintext в буфере при неверном tag **[Не проверено: номер и детали по памяти]**.
- **[Вывод]** Nonce-misuse в PHANTOM исключается конструктивно, если nonce — счётчик, привязанный к ключу сессии, и ключ никогда не переживает процесс (нет сохранения состояния счётчика на диск).

### 3.4. Производительность и side channels

**[Не проверено]** AES-GCM с AES-NI/PCLMULQDQ (x86-64) и ARMv8 Crypto Extensions обычно быстрее ChaCha20-Poly1305; без аппаратного ускорения — заметно медленнее, а табличные реализации AES уязвимы к cache-timing. ChaCha20-Poly1305 — constant-time по конструкции (ARX) на любом CPU. **[Вывод]** Для прототипа безопасный выбор по умолчанию — ChaCha20-Poly1305 (Noise) либо согласование cipher suite средствами TLS 1.3 (вариант B), где выбор делает библиотека.

## 4. X25519 и Ed25519

### 4.1. X25519 (RFC 7748)

- **[Факт]** RFC 7748 оставляет проверку all-zero результата на усмотрение реализации/протокола («MAY check»); TLS и HPKE (RFC 9180) её требуют [18][19].
- **[Факт]** Без проверки точка малого порядка от партнёра даёт фиксированный shared secret — отсутствие contributory behaviour; в июле 2026 по этому поводу вышел advisory Mbed TLS [18].
- **[Факт]** `ring` возвращает ошибку при нулевом результате [64]; `x25519_dalek::StaticSecret::diffie_hellman` такой проверки не делает — отсюда RUSTSEC-2026-0072 для `hpke-rs-rust-crypto` (исправлено в 0.6.0) [19].
- **[Вывод]** В PHANTOM проверку не нужно писать самим: в варианте B её выполняет TLS-стек; в варианте A нужно убедиться, что её делает выбранный resolver `snow`, либо что паттерн не зависит от contributory behaviour (transcript hashing в Noise).

### 4.2. Ed25519 (RFC 8032)

- **[Факт]** «Taming the many EdDSAs» (Chalkias, Garillot, Nikolaenko; ePrint 2020/1244) показывает расхождения реализаций в уравнении проверки, свойствах binding/malleability и между batch- и одиночной проверкой [20]. ZIP-215 явно фиксирует критерии проверки (cofactored-уравнение, допуск неканонических кодировок точек) ради совместимости с batch-проверкой [20][22].
- **[Факт]** `ed25519-dalek` 2.x: документация указывает, что декодирование ключа следует правилам ZIP-215, критерии RFC 8032/NIST «currently unsupported»; `verify_strict` дополнительно отвергает weak keys [21].
- **[Факт]** RUSTSEC-2022-0093: в `ed25519-dalek` < 2.0 раздельные типы секретного и публичного ключа позволяли построить signing oracle и извлечь приватный ключ; исправлено в 2.0 [23].
- **[Вывод]** Ed25519 нужен PHANTOM только для долговременных подписей (сертификаты TLS, подпись конфигураций/обновлений). Расхождения правил верификации критичны для консенсус-систем, а не для двухточечного VPN с одной реализацией; тем не менее следует выбрать один режим (`verify_strict` либо проверка средствами TLS-стека) и зафиксировать его в protocol-spec.

## 5. KDF и хеш-функции: HKDF, BLAKE2s, BLAKE3

- **[Не проверено]** HKDF (RFC 5869) — extract-then-expand на HMAC; используется в TLS 1.3 (HKDF-SHA256/384) и в Noise (HKDF на HMAC выбранного hash; в WireGuard — BLAKE2s).
- **[Факт]** BLAKE3: единственный IETF-документ — индивидуальный `draft-aumasson-blake3-00` (июль 2024, Informational), истёк в январе 2025; принятия CFRG и RFC нет [25]. BLAKE3 использует 7 раундов функции сжатия против 10 у BLAKE2 [63].
- **[Не проверено]** В Noise rev 34 определены hash-функции SHA256, SHA512, BLAKE2s, BLAKE2b; BLAKE3 среди них нет.
- **[Вывод]** BLAKE3 неуместен как KDF в handshake PHANTOM: нет стандарта, нет места в Noise и TLS, меньший запас раундов. Допустим вне криптографического ядра (контрольные суммы, дедупликация). Для KDF — только HKDF в составе стандартного протокола; самостоятельно вызывать `hkdf` для «склейки» секретов — это уже комбинирование примитивов.

## 6. Post-quantum

### 6.1. Стандарты NIST

- **[Факт]** FIPS 203 (ML-KEM), FIPS 204 (ML-DSA), FIPS 205 (SLH-DSA) утверждены 13 августа 2024 (вторичные источники) [27].
- **[Факт]** FIPS 206 (FN-DSA/Falcon) по состоянию на 2026 год — не финализирован; источники расходятся, опубликован ли initial public draft [27].
- **[Факт]** HQC выбран в марте 2025 как резервный KEM на кодах; план NIST — draft примерно через год, финал в 2027. По состоянию на конец октября 2026: «FIPS under development» (вторичный источник) [28]. Номер FIPS официально не подтверждён.
- **[Факт]** Финальный NIST IR 8547 (сообщается о публикации 27 октября 2026; вторичные источники): квантово-уязвимые алгоритмы с открытым ключом — deprecated после 2030 и disallowed после 2035; гибриды с утверждённым PQ-алгоритмом под запрет 2035 не подпадают (со слов представителя NIST в pqc-forum) [55].

### 6.2. Harvest-now-decrypt-later

**[Вывод]** HNDL угрожает конфиденциальности записанного сегодня трафика, но не аутентификации (подделать подпись «задним числом» нельзя). Поэтому приоритет PHANTOM — PQ key exchange; PQ-подписи можно отложить. **[Факт]** Это же обоснование приводит Mullvad для своей схемы [54] и на нём строит срочность IR 8547 [55].

### 6.3. Гибридный обмен в TLS 1.3

- **[Факт]** RFC 9954 «Hybrid Key Exchange in TLS 1.3» (июль 2026, Informational) — конструкция конкатенации; конкретных алгоритмов не задаёт [29].
- **[Факт]** `draft-ietf-tls-ecdhe-mlkem` (последняя ревизия -05, май 2026, Standards Track) опубликован как RFC 10024 (август 2026); определяет `X25519MLKEM768` (codepoint 0x11EC), `SecP256r1MLKEM768`, `SecP384r1MLKEM1024` [30]. Дата «10 августа 2026» — по вторичному источнику.
- **[Факт]** `rustls`: `X25519MLKEM768` доступен с провайдером `aws-lc-rs`; feature `prefer-post-quantum` включён по умолчанию и ставит гибрид первым в `DEFAULT_KX_GROUPS` [31]. Актуальная стабильная версия ветки 0.23 — 0.23.46 (crates.io, 2026-11-11); 0.24 — в стадии `0.24.0-dev.2` (2026-10-14), провайдеры вынесены в отдельные crates (`rustls-aws-lc-rs`, `rustls-ring`) [31][32].
- **[Не проверено]** Поддержка с 0.23.22 и приоритет по умолчанию с 0.23.27 — по стороннему issue. **[Факт]** При `default-features = false` приоритет гибрида молча теряется (сообщения сторонних проектов) [31]. **[Вывод]** В PHANTOM список групп надо задавать явно и проверять тестом на согласованную группу.
- **[Факт]** OpenSSL ≥ 3.5.0 и Chrome ≥ 131 (BoringSSL) предлагают `X25519MLKEM768` по умолчанию (документация Cloudflare) [33].
- **[Факт]** AWS-LC FIPS 3.0 включает ML-KEM-512/768/1024; сертификат CMVP № 5314 «AWS-LC 3 Cryptographic Module (static)» активен, sunset 2031-06-04 [34].

### 6.4. PQ для Noise и WireGuard — что реально существует

### 6.5. Риски реализации ML-KEM

- **[Факт]** KyberSlash: зависящее от секрета время деления в ряде реализаций Kyber, включая reference; восстановление ключа за минуты/часы; reference исправлен 1 декабря 2023 (TCHES 2025) [41]. RUSTSEC-2023-0079 — `pqc_kyber` не исправлен, рекомендован `ml-kem` [41].
- **[Факт]** RUSTSEC-2025-0144 — timing side-channel в подписи RustCrypto `ml-dsa` (деление заменено на constant-time Barrett reduction) [41]. **[Вывод]** Класс ошибок «компилятор/деление ломает constant-time» актуален и для чистого Rust.

## 7. Сопутствующие механизмы

### 7.1. Anti-replay sliding window

**[Факт]** RFC 6479 (Informational, 2012) описывает окно anti-replay без битовых сдвигов: окно хранится блоками, при переходе в новый блок старые обнуляются; размер избыточности — степень двойки [56]. **[Не проверено]** RFC 4303 (ESP) требует минимум 32 и рекомендует 64 позиции; WireGuard использует алгоритм RFC 6479 с окном порядка 8192 счётчиков. **[Факт]** В QUIC защита от replay обеспечивается номерами пакетов и входит в протокол; в TLS-over-TCP порядок гарантирует TCP, а счётчик записей неявный **[Не проверено: общеизвестно, тексты не открывались]**.

### 7.2. Ротация ключей и PFS

**[Факт]** WireGuard инициирует новый handshake по `REKEY_AFTER_TIME`/`REKEY_AFTER_MESSAGES` и отбрасывает пакеты на ключах старше `REJECT_AFTER_TIME` [10][11]. Каждый handshake использует свежие ephemeral ключи, что и даёт PFS.
**[Факт]** TLS 1.3 при `psk_ke` (PSK без DH) forward secrecy не обеспечивает (вторичное зеркало текста RFC) [59]. **[Вывод]** В варианте B: только (EC)DHE/гибридные группы, resumption либо выключен, либо только `psk_dhe_ke`; периодическое переустановление соединения даёт свежий обмен ключами (KeyUpdate обновляет симметричные ключи, но не добавляет новой DH-энтропии **[Не проверено]**).

### 7.3. Cookie / анти-DoS

**[Факт]** В WireGuard каждое handshake-сообщение несёт `mac1` (MAC на ключе, выведенном из static public key responder) и `mac2` (MAC на последнем полученном cookie, иначе нули); cookie reply отправляется, когда `mac1` верен, `mac2` неверен и responder под нагрузкой; cookie reply шифруется XChaCha20-Poly1305 [10][11][12]. **[Вывод]** Побочный эффект `mac1`: сервер не отвечает тому, кто не знает его public key, — устойчивость к сканированию.
**[Не проверено]** В QUIC аналогичную роль играют Retry-токены и anti-amplification limit (RFC 9000).

### 7.4. Key confirmation

**[Факт]** В WireGuard key confirmation — первое transport-сообщение initiator; из-за этого протокол не укладывается в стандартные модели key exchange без модификации [7][9]. **[Факт]** В TLS 1.3 явное подтверждение — сообщения `Finished` обеих сторон (MAC над transcript) [59].

### 7.5. Защита от downgrade

**[Вывод]** Noise: согласования нет, значит downgrade внутри протокола невозможен, но любой внешний механизм выбора версии нужно защищать самостоятельно (например, включением в prologue — он входит в transcript hash **[Не проверено]**). TLS 1.3: согласование параметров покрыто transcript и `Finished`; гибридная группа выбирается сервером из предложенных. Для PHANTOM достаточно жёстко ограничить конфигурацию: только TLS 1.3, только гибридные группы, без fallback на классический X25519 там, где обе стороны — наши.

### 7.6. Обнуление секретов и constant-time

**[Факт]** `zeroize` использует `write_volatile` и memory fences, но документация прямо перечисляет ограничения: копии при move/`Copy`, реаллокации `Vec`/`String`, копии у заимствующего кода; очистка регистров вне возможностей crate; `Pin` помогает против перемещений на стеке [57]. **[Вывод]** `zeroize` — гигиена, а не гарантия; секреты следует держать в типах библиотеки (ключи `rustls`/`aws-lc-rs`), не копировать в собственные буферы.
**[Факт]** RUSTSEC-2024-0344: в `curve25519-dalek` < 4.1.3 LLVM вставил условный переход в `Scalar29::sub`/`Scalar52::sub` — утечка по времени, возникшая из-за оптимизации компилятора [24]. **[Вывод]** Constant-time в Rust — свойство «best effort»; собственный код не должен ветвиться по секретам и сравнивать их обычным `==`.

## 9. Варианты криптографической архитектуры для PHANTOM

### 9.1. Вариант A — Noise (`IKpsk2`/`XK` + PSK) поверх UDP и тот же канал поверх TCP

- **PFS:** да, после завершения handshake; первое сообщение `IK` защищено только static ключом responder [1][2].
- **Identity hiding:** static ключ initiator в `IK` раскрывается при последующей компрометации static ключа responder; `XK` защищает initiator лучше ценой лишнего сообщения. Static ключ responder по сети не передаётся; сервер молчит без верного `mac1` (при WireGuard-подобной конструкции) [10].
- **KCI:** для `IK` спецификация отмечает KCI-подобную слабость первого сообщения (компрометация static ключа получателя) [1]; WireGuard заявляет устойчивость к KCI для сессии в целом [7][9].
- **Replay:** первое сообщение `IK` воспроизводимо на уровне Noise [1]; WireGuard закрывает это timestamp'ом (TAI64N) в первом сообщении и счётчиком + окном для данных **[вторичные источники]**.
- **Downgrade:** согласования нет — нет и downgrade, но нет и штатного пути миграции.
- **Путь к PQ:** только PSK-слот (нужен второй протокол доставки PSK) либо нестандартные расширения (раздел 6.4). Стандартизованного пути нет.
- **Сложность и поверхность ошибок:** криптографическое ядро маленькое (`snow`), но всё вокруг — anti-replay, rekey-таймеры, cookie, roaming, framing для TCP, версионирование — пишется самостоятельно. Это проектирование протокола, а не интеграция.
- **Проверяемость:** превосходная для WireGuard «как есть» [7][8][9] и для паттернов в целом [2][4][5]; для собственной обвязки — никакой. `snow` прошёл один аудит [36].
- **Производительность:** лучшая из трёх: 1-RTT handshake, минимальные накладные расходы, один AEAD на пакет.

### 9.2. Вариант B — TLS 1.3 / QUIC (`rustls` + `quinn`) как единственный слой

- **PFS:** да при (EC)DHE/гибридных группах; требуется отключить `psk_ke` и 0-RTT [59].
- **Identity hiding:** сертификат клиента шифруется и отправляется после аутентификации сервера; сертификат сервера зашифрован от пассивного наблюдателя, но активный атакующий может его запросить; SNI открыт без ECH (ECH — RFC 9849, 2026) [58]. **[Не проверено: формулировки RFC 9846 Appendix F]**.
- **KCI:** аутентификация подписью над transcript; компрометация ключа клиента не позволяет выдать себя за сервер перед этим клиентом **[Не проверено: по общей теории SIGMA]**.
- **Replay:** защищён в 1-RTT; 0-RTT данные воспроизводимы — 0-RTT запретить [59].
- **Downgrade:** согласование версии и групп защищено transcript; конфигурация «только TLS 1.3 + только гибрид» устраняет остаток.
- **Путь к PQ:** стандартизован и реализован: `X25519MLKEM768` (RFC 10024) в `rustls`+`aws-lc-rs` по умолчанию [30][31]. PQ-аутентификация (ML-DSA в сертификатах) — **[Не проверено]**, для HNDL не требуется.
- **Аутентификация:** raw public keys (RFC 7250) поддерживаются `rustls` 0.23 [46] либо самоподписанные сертификаты с pinning по SPKI. **[Вывод]** RPK убирает разбор цепочек X.509 из пути доверия.
- **Сложность и поверхность ошибок:** большой объём стороннего кода (`rustls`, `quinn`, AWS-LC на C/asm), но почти ничего криптографического не пишется самостоятельно; ошибки смещаются в конфигурацию (verifier, список групп, 0-RTT, resumption).
- **Проверяемость:** TLS 1.3 — один из наиболее проанализированных протоколов (в т.ч. Tamarin-модель draft 21, CCS 2017) [60]; `rustls` — аудит 2020 года [35]; AWS-LC — FIPS 140-3 [34]; `quinn` — аудит не найден, DoS-advisories 2026 [45].
- **Производительность:** QUIC в userspace тяжелее WireGuard; гибридный ClientHello больше (ML-KEM-768 добавляет порядка 1.2 КБ в каждую сторону **[Не проверено]**); TLS-over-TCP страдает от TCP-over-TCP — как и TCP-режим варианта A.

### 9.3. Вариант C — TLS/QUIC снаружи + сквозной Noise внутри

- **Свойства:** не хуже сильнейшего из слоёв, если слои независимы по ключам. PQ-конфиденциальность даёт внешний TLS с гибридом — но только до точки его терминации.
- **Когда оправдан:** внешний TLS терминируется посредником (relay, CDN, обфусцирующий прокси), которому нельзя доверять содержимое; тогда внутренний Noise даёт end-to-end.
- **Цена:** два handshake, двойное шифрование и двойные накладные на пакет (MTU), две библиотеки, два набора advisories; при end-to-end через недоверенный relay PQ-стойкость определяется уже внутренним Noise — то есть возвращается проблема варианта A.
- **Связывание слоёв:** без channel binding слои независимы; добавлять собственное связывание — самостоятельное комбинирование. **[Вывод]** Допустимо только «чистое» наложение без общих ключей.
- **Проверяемость:** каждый слой в отдельности проверяем; композиция в целом не анализировалась.

### 9.4. Сводное сравнение

| Критерий | A: Noise | B: TLS 1.3/QUIC | C: TLS + Noise |
|---|---|---|---|
| PFS | да (после handshake) | да (без `psk_ke`, 0-RTT) | да |
| Identity hiding клиента | `IK`: слабое; `XK`: сильное | сильное (после аутентификации сервера) | как у внутреннего слоя |
| Скрытность сервера от зондирования | высокая (`mac1`) | низкая на уровне TLS | как у внешнего слоя |
| KCI | оговорки для 1-го сообщения `IK` | устойчив | не хуже B |
| Replay | решается обвязкой | решён протоколом (0-RTT выкл.) | решён |
| Downgrade / agility | нет согласования | штатное, защищённое | два механизма |
| Путь к PQ | нестандартный | стандартизован, реализован | только до терминации TLS |
| Объём собственного крипто-кода | значительный (обвязка) | минимальный (конфигурация) | значительный |
| Формальный анализ | отличный для WireGuard как есть | отличный для TLS 1.3 | по слоям |
| Аудит реализаций | `snow` 2024 | `rustls` 2020; `quinn` — нет | оба набора |
| Производительность | лучшая | средняя | худшая |

## 10. Рекомендация

**[Вывод]** Рекомендуется **вариант B** со следующим профилем:

1. `rustls` (стабильная ветка) + `aws-lc-rs`; только TLS 1.3; группы — только `X25519MLKEM768` (задать явно, проверить тестом); cipher suites по умолчанию библиотеки.
2. QUIC (`quinn`) как основной транспорт, TLS-over-TCP как fallback — один и тот же `rustls`-конфиг и одна модель идентичности.
3. Взаимная аутентификация: raw public keys либо самоподписанные сертификаты с pinning по SPKI; публичный WebPKI не используется.
4. 0-RTT выключен; resumption выключен либо только `psk_dhe_ke` с коротким временем жизни tickets; периодическое пересоединение для свежего обмена ключами.
5. Никаких собственных KDF, «склеек» секретов, дополнительных MAC поверх TLS.

Обоснование: (i) требование «без самостоятельного комбинирования» выполняется буквально — комбинирование X25519 и ML-KEM выполнено в RFC 10024 и в библиотеке; (ii) PQ-защита от HNDL доступна сразу; (iii) согласование и защита от downgrade — штатные; (iv) один криптографический слой на оба транспорта; (v) есть путь к FIPS.

Вариант A остаётся разумной альтернативой, только если использовать протокол WireGuard без изменений (готовая реализация) — тогда на него распространяются его доказательства; собственный «Noise-протокол» для PHANTOM не рекомендуется. Вариант C рассматривать только при появлении в threat model недоверенного терминатора TLS.

### 10.1. Остаточные риски рекомендации

1. Аудит `rustls` относится к версии 0.16 (2020); кодовая база с тех пор существенно изменилась [35].
2. Для `quinn` независимый аудит не найден; в 2026 году — два DoS-advisory в `quinn-proto` [45]. Сервер PHANTOM доступен из сети без аутентификации до завершения handshake.
3. AWS-LC — код на C и ассемблере; ошибки памяти возможны, несмотря на FIPS-валидацию.
4. ML-KEM — молодой стандарт; гибрид страхует от его взлома, но не от ошибок реализации (класс KyberSlash) [41].
5. Аутентификация остаётся классической (Ed25519/ECDSA): активная атака с квантовым компьютером в будущем возможна; HNDL это не затрагивает.
6. TLS-сервер отвечает любому клиенту: активное зондирование и fingerprinting — вне криптографии, но это прямое следствие выбора B (в отличие от `mac1` в WireGuard).
7. Метаданные (размеры, тайминги, SNI без ECH) не скрываются.
8. Ошибки конфигурации: verifier, принимающий любой ключ; утрата `prefer-post-quantum` при `default-features = false`; случайно включённый 0-RTT.
9. Side channels и остатки секретов в памяти: `zeroize` и constant-time — best effort [24][57].
10. Хранение долговременных ключей на диске и их ротация — вне этого исследования.
11. TCP-over-TCP в fallback-режиме — деградация производительности, не безопасности.

## 11. Открытые вопросы к главному архитектору

1. Входит ли в threat model активное зондирование сервера? Если да, нужен отдельный слой перед TLS (задача потока по транспортам), и это меняет оценку варианта A.
2. Нужна ли совместимость с существующими клиентами WireGuard? Если да — вариант A «WireGuard как есть» становится обязательным транспортом.
3. Допустим ли C/asm-код (AWS-LC) в доверенной базе, или требуется чистый Rust (тогда `ring`/RustCrypto без FIPS и без аудированного ML-KEM)?
4. Нужен ли FIPS-режим в принципе?
5. Модель идентичности: raw public keys или сертификаты; кто и как распределяет pin'ы.
6. Требуется ли PQ-аутентификация уже в прототипе?
7. Будет ли внешний TLS терминироваться третьей стороной (критерий для варианта C)?

## 12. Не удалось проверить

1. Первичные тексты на `datatracker.ietf.org`, `csrc.nist.gov`, `docs.rs`, `rustsec.org`, `noiseprotocol.org` напрямую не открывались (сетевые ограничения среды); все ссылки на них получены из поисковой выдачи.
2. Числовые уровни payload security и identity hiding в таблицах Noise (§7.7–7.8) для `IK`/`XK`/`XX`/`NK`; текст §12.1 о нулевом результате DH; набор hash-функций.
3. Точные формулировки RFC 9001 §6.6 для ChaCha20-Poly1305; лимиты RFC 8446/9846 §5.5; содержимое ревизии -12 `draft-irtf-cfrg-aead-limits`.
4. Страница RFC 10024 на rfc-editor.org (дата и статус взяты из Datatracker-ссылки, страницы автора и вторичной публикации); признак «Recommended» для `X25519MLKEM768` в реестре IANA.
5. Версии `rustls`, с которых гибрид доступен и предпочитается по умолчанию; поведение в 0.24.
6. Текущие версии и наличие аудитов: `aws-lc-rs`, `chacha20poly1305`, `aes-gcm`, `hkdf`, `blake3`, `ml-kem`, dalek-crates; полный перечень advisories по каждому crate на rustsec.org.
7. Статус HQC (опубликован ли draft FIPS) и FIPS 206 на ноябрь 2026; первичная страница NIST IR 8547.
8. Текущее состояние Rosenpass (версия, завершён ли CryptoVerif-proof, аудит); реакция проекта WireGuard на предложение message type 5/6.
9. RFC 4303 (размер окна), размер окна WireGuard, детали whitepaper WireGuard (TAI64N, формулировки о KCI и identity hiding).
10. Поддержка ML-DSA в `rustls`; размеры ключей/шифртекстов ML-KEM-768 по FIPS 203.
11. Производительность AES-GCM и ChaCha20-Poly1305 на целевых платформах — нужны собственные измерения.
12. Формальный анализ QUIC handshake; RFC 9846 Appendix F (свойства безопасности TLS 1.3).
