# PROJECT PHANTOM — транспорт и сеанс: спецификация (этап 6, поток N1)

**Статус:** черновик спецификации этапа 6, независимая проверка транспортной части ADR-0006, ADR-0009, ADR-0010.
**Дата:** 2026-11-14. Кода нет; ничего из описанного не запускалось. Числа с пометкой «⟂» — стартовые значения,
уточняются измерением на этапе 12. Ключевые слова MUST/SHOULD/MAY — в смысле RFC 2119.

## 0. Вердикт

|---|---|---|

## 2. Повторная оценка транспорта: факты из первичных текстов

### 2.1. QUIC и DATAGRAM

1. **[Факт D §3]** Поддержка DATAGRAM объявляется параметром `max_datagram_frame_size` (0x20); без ненулевого значения
   от пира отправлять DATAGRAM нельзя. Протокол приложения MUST определить реакцию на отсутствие параметра.
   **Решение:** при отсутствии параметра или если после рукопожатия `max_datagram_size()` < 1 + MTU_TUN, клиент
   закрывает соединение с кодом `MTU_UNUSABLE` (§5.6); это наблюдение F3 (§7.3).
2. **[Факт D §4–§6]** DATAGRAM не фрагментируется, не повторяется, подчиняется congestion control (§5.4), получатель
   MAY их отбрасывать (§5.3); соединение с DATAGRAM отличимо по реакции на потери (§6).
3. **[Факт-код qp `frame.rs` 901–913, `datagrams.rs` 82–96]** `quinn` всегда пишет DATAGRAM с полем длины.
   `max_size()` = `current_mtu` − (1 + длина DCID + 4 + длина тега) − 9 и меньше лимита пира. Значение **меняется во
   времени**: после обнаружения «чёрной дыры» `current_mtu` падает до `min_mtu` (`mtud.rs` 155–167), очередь слишком
   больших датаграмм выбрасывается (`drop_oversized`, `mod.rs` 1429, 1799, 3089).
4. **[Факт-код qp `transport_parameters.rs` 170]** Параметр `max_datagram_frame_size` берётся как
   `min(datagram_receive_buffer_size, 65535)`; отдельно его не задать. Поэтому предел длины принятой датаграммы
   проверяет PHANTOM (§5.2).
5. **[Факт-код qp `config/transport.rs`]** Значения по умолчанию: `initial_mtu` = `min_mtu` = 1200; DPLPMTUD включён:
   интервал 600 с, верхняя граница 1452, `black_hole_cooldown` 60 с, шаг 20; `max_idle_timeout` 30 с;
   `keep_alive_interval` выключен; CUBIC (есть NewReno и BBR с пометкой «Experimental!», `congestion/bbr/mod.rs`);
   `enable_segmentation_offload` (GSO) включён; буфер отправки датаграмм 1 МиБ; `EndpointConfig::max_udp_payload_size`
   1472 (`config/mod.rs` 60). Порог чёрной дыры — более 3 «подозрительных» серий потерь (`mtud.rs` 528).
6. **[Факт-код qp `mod.rs` 478, 646]** Клиентские Initial и ack-eliciting серверные Initial дополняются до
   `min(min_mtu, current_mtu)`. PATH_CHALLENGE дополняется только до 1200 (`MIN_INITIAL_SIZE`, `mod.rs` 1063).
7. **[Факт-код qn `endpoint.rs` 243–265, `connection.rs` 1102; qp `mod.rs` 3106]** `Endpoint::rebind` на клиенте
   меняет сокет; соединение лишь берёт новый CID и шлёт PING. Оценки MTU, RTT и окно перегрузки клиента **не
   сбрасываются** (`path_changed` в `quinn` 0.11.12 не вызывается). Сервер при смене IP клиента создаёт путь с
   `initial_mtu` (`mod.rs` 3069–3081), при смене только порта сохраняет состояние — это совпадает с **[Факт Q §9.4]**.
8. **[Факт-код qu]** На Linux сокет получает `IP_MTU_DISCOVER = IP_PMTUDISC_PROBE` и для IPv6 `IPV6_PMTUDISC_PROBE` +
   `IPV6_DONTFRAG`; если опция недоступна, `may_fragment()` = true, и `quinn` отключает MTUD (qn `endpoint.rs` 140). В
   qp и qn нет обработки ICMP. **[Вывод]** Внешний ICMP PTB не уменьшает размер пакетов T1 ни в ядре, ни в библиотеке.
   Версия `quinn-udp`, которая попадёт в `Cargo.lock`, локально не проверена.
9. **[Факт Q §14]** QUIC MUST NOT использоваться на пути без 1200 байт UDP payload; датаграммы MUST NOT
   фрагментироваться на IP; DF MUST ставиться где возможно. **[Факт Q §14.1]** Дополнение Initial проверяет путь в обе
   стороны. **[Факт Q §14.2.1]** ICMP с PMTU < 1200 MUST игнорироваться; PMTU по ICMP нельзя увеличивать.
10. **[Факт Q §8, §8.1]** До проверки адреса сервер шлёт не более 3× принятого. Retry: токен повторяется во всех
    следующих Initial; второй Retry невозможен (§8.1.2). **[Факт-код qn `incoming.rs`]** Сервер выбирает `retry()`,
    `refuse()`, `ignore()` и видит `remote_address_validated()`.
11. **[Факт Q §8.2]** Path validation проверяет только направление «к пиру»; обратное подтверждает пир. Тайм-аут
    проверки — 3 × max(PTO) (§8.2.4). До подтверждения рукопожатия миграция запрещена (§9). **[Факт Q §10.1]**
    Эффективный idle timeout — минимум двух объявленных, не меньше 3 PTO. **[Факт R §6.2.2]** Начальный RTT 333 мс,
    первый PTO около 1 с.
12. **[Факт A §3.2]** Протокол приложения должен назначить сторону, отвечающую за keepalive; ориентир для NAT — 30 с;
    RFC 8085 (по цитате в A) требует не менее 15 с.
13. **[Факт K §4.1, §4.2]** Доля ключа клиента X25519MLKEM768 — 1216 байт, сервера — 1120 байт. **[Вывод]**
    ClientHello не помещается в один Initial (C-13), первый полёт сервера тоже длиннее 1200 байт.
14. **[Факт-код rl `client/hs.rs` 890–960]** Клиент `rustls` отвергает HRR с уже предложенной группой, HRR без
    изменений и HRR с пустым cookie; HRR только с cookie принимает.

### 2.2. CONNECT-IP, HTTP Datagrams, гонка

- **[Факт I §7.2]** Конечная точка с IPv6 MUST обеспечить MTU туннеля ≥ 1280: дополнением Initial (51 байт накладных,
  Initial ≥ 1331) или ICMPv6 echo с 1232 байтами данных (MUST, если нет внешней гарантии первого); если QUIC не несёт
  1280 — MUST прервать поток запроса. Это снимает пометку «не проверено» с риска ADR-0010. **[Факт I §10.1]** Слишком
  большой пакет SHOULD отбрасываться с ICMP PTB. **[Факт I §10]** MAY отключить congestion control для датаграмм —
  PHANTOM этим **не** пользуется.
- **[Факт H §3.2, §3.3, §3.5]** Капсула `Type (i), Length (i), Value`; неизвестный тип MUST пропускаться; лишние или
  недостающие байты — ошибка; слишком длинную капсулу SHOULD отбрасывать без буферизации.
- **[Факт E §5, §8]** Connection Attempt Delay 250 мс, минимум 100 мс (не меньше 10 мс), максимум 2 с. **[Факт A §2]**
  Откат не должен понижать защиту; UDP целиком закрыт в 3–5 % сетей (по измерениям, цитируемым в A).

## 4. MTU и размер датаграммы (S-10)

### 4.1. Нормативные требования

- **M1.** MTU интерфейса TUN MUST быть фиксированным и одинаковым для T1 и T2: `MTU_TUN = 1280` на клиенте и на
  сервере. Оно не меняется ни при смене транспорта, ни по `Config` (поле `mtu` в `Config` MUST совпадать с локальным
  значением, иначе закрытие `CONFIG_MISMATCH`). Обоснование: 1280 — минимум IPv6 (I §7.2); меньшее значение нарушает
  IPv6, большее увеличивает долю сетей, где T1 непригоден.
- **M2 (инвариант T1).** Всё время, пока соединение T1 активно или кандидат на активацию, MUST выполняться
  `max_datagram_size() ≥ 1 + MTU_TUN` (1 — байт контекста, §5.2). Нарушение — немедленное закрытие с `MTU_UNUSABLE` и
  наблюдение F3.
- **M3.** Профиль `quinn` для T1 на обеих сторонах MUST задавать `min_mtu = initial_mtu = REQ_UDP` (§4.2),
  `EndpointConfig::max_udp_payload_size ≥ REQ_UDP`, MTUD включён с `upper_bound` по умолчанию. Следствия **[Факт-код,
  §2.1 п. 3, 5, 6]**: (а) все клиентские Initial и ack-eliciting серверные Initial идут размером не меньше REQ_UDP,
  поэтому завершённое рукопожатие доказывает прохождение REQ_UDP в обе стороны на момент рукопожатия (Q §14.1; I §7.2,
  первый способ); (б) детектор чёрной дыры опускает `current_mtu` не ниже `min_mtu`, поэтому M2 не нарушается
  библиотекой. Цена: если путь сузился ниже REQ_UDP, `quinn` этого не увидит — это ловит проба размера (§4.3).
- **M4.** Сокет T1 MUST запрещать IP-фрагментацию. Клиент и сервер MUST отказать в T1, если `may_fragment()` сокета
  истинно (§2.1 п. 8).
- **M5.** Процесс PHANTOM MUST NOT формировать ICMP. Пакеты больше MTU_TUN в туннель не попадают по построению: при
  пересылке в TUN ядро само отвечает ICMP PTB / «fragmentation needed» (для IPv4 без DF — фрагментирует). Так
  выполняется I §10.1 без собственного генератора ICMP. **[Вывод]** Если датаграмма всё же больше
  `max_datagram_size()` (ошибка), она отбрасывается со счётчиком и M2 проверяется.
- **M6.** Входящий ICMP по внешнему пути MUST NOT влиять на выбор транспорта и память по сети; «T1 непригоден по MTU»
  решается только собственными аутентифицированными пробами (§4.3). Это закрывает для T1 сценарий S-10 «поддельный
  ICMP переводит на T2» (§2.1 п. 8). В T2 PMTUD ведёт ядро: поддельный PTB может уменьшить MSS внешнего TCP —
  остаточный риск к RR5 (**[Не проверено]** для Linux). Поддельный PTB внутри туннеля через NAT сервера — обычный
  остаточный риск NAT.
- **M7.** MSS clamping MUST стоять на сервере в forward для SYN и SYN-ACK через TUN (MSS 1240 для IPv4, 1220 для IPv6)
  и на клиенте в forward для транзитного трафика; локальные сокеты берут MSS из MTU TUN. UDP-приложениям clamping не
  помогает; внутренний QUIC (1200) при 1280 проходит.

### 4.2. Расчёт REQ_UDP

Профиль фиксирует длину CID 8 байт на обеих сторонах (по умолчанию в `quinn`, `cid_generator.rs` 49–55); иначе REQ_UDP
пересчитывается при проверке конфигурации.

| Поле 1-RTT пакета (Q §17.3.1, D §4, T §5.3) | Байт на проводе | Граница `quinn` |
|---|---|---|
| Первый байт | 1 | 1 |
| DCID | 8 | 8 |
| Packet Number | 1–4 (Q §12.3) | 4 |
| DATAGRAM: тип + длина (varint от 1281 — 2 байта) | 3 | 9 |
| Контекст PHANTOM | 1 | 1 |
| IP-пакет | 1280 | 1280 |
| Тег AEAD | 16 | 16 |
| **UDP payload** | **1310–1313** | **REQ_UDP = 1319** |
| Внешний IP-пакет, IPv4 / IPv6 | 1338–1341 / 1358–1361 | 1347 / 1367 |

REQ_UDP берётся по границе `quinn`, потому что `max_size()` считает именно её (§2.1 п. 3). Расчёт RFC 9484 (51 байт, I
§7.2) больше на 8 байт Quarter Stream ID и длину CID 20 — к PHANTOM не относится. **[Вывод]**

### 4.3. Проба размера (SizeProbe)

Проба идёт в DATAGRAM с контекстом 1 (§5.2) и проверяет оба направления. Формат после контекста: `kind` (1 байт: 1 —
BIG, 2 — SMALL, 3 — ACK, 4 — ECHO), `id` (8 байт), нули до нужной длины; иное содержимое — отброс со счётчиком. Аналог
ICMPv6 echo из I §7.2 (второй способ), но внутри TLS.

- Клиент шлёт BIG (длина 1 + MTU_TUN) и SMALL (64 байта) со случайным `id`. Сервер отвечает на каждую пробу ACK (64
  байта), а на BIG ещё и ECHO длиной 1 + MTU_TUN; не более 4 проб в секунду на соединение ⟂, лишние молча
  отбрасываются.
- Попытка: пара BIG + SMALL. Ожидание ответа `T_PROBE = max(3·PTO, 1 с)` ⟂. До 3 попыток (MAX_PROBES из P §5.1.2) с
  интервалом T_PROBE.
- Исходы (наблюдения, не причины — ARCH §7.2):
  - ACK и ECHO для BIG пришли — размер проходит в обе стороны;
  - на BIG пришёл ACK, ECHO нет во всех попытках — «сервер → клиент не пропускает REQ_UDP»;
  - на SMALL ответы есть, на BIG ничего во всех попытках — «клиент → сервер не пропускает REQ_UDP»;
  - нет ответов и на SMALL — потеря связи, а не MTU (§7.3, F4).
- Проба MUST выполняться: (1) после рукопожатия T1 и до `Activate`; (2) после каждой смены локального адреса (rebind,
  миграция) — так как `quinn` клиента не сбрасывает оценку MTU (§2.1 п. 7), а path validation проверяет только 1200
  байт (§2.1 п. 6); (3) после пробуждения (§7.4); (4) при подозрении на потерю связи (§6, «Потеря связи»); (5) раз в
  10 мин ⟂ при наличии трафика (по образцу PMTU_RAISE_TIMER 600 с, P §5.1.1).
- Неуспех BIG при успехе SMALL — наблюдение F3; T1 закрывается с `MTU_UNUSABLE`.

## 5. Кадрирование и управляющие сообщения (S-15, C-13)

### 5.1. Общий формат TLV

```
Message { Type (i), Length (i), Value (Length байт) }
```

`(i)` — varint QUIC (Q §16). Формат совпадает с капсулой (H §3.2).

- **L1.** Varint MUST иметь кратчайшую кодировку; иная — ошибка `PROTOCOL_ERROR`. Это строже QUIC (Q §16 допускает
  некратчайшую) и убирает неоднозначность разбора.
- **L2.** Значение MUST содержать ровно поля описания: лишние или недостающие байты — `PROTOCOL_ERROR` (по образцу H
  §3.3).
- **L3.** Предел `Length`: управляющее сообщение ≤ 1024 байт ⟂; кадр пакета T2 — не больше MTU_TUN. Превышение —
  `PROTOCOL_ERROR` до чтения значения (H §3.5); пакет короче 20 байт отбрасывается со счётчиком.
- **L4.** Типы `0x00–0x3F` — обязательные: неизвестный тип → закрытие `PROTOCOL_ERROR`. Типы `0x40` и выше —
  необязательные: неизвестный тип молча пропускается по длине (как H §3.2). Так совместимое расширение возможно без
  нарушения правила «неизвестное обязательное — закрытие».
- **L5.** Числа фиксированной длины — big-endian.

### 5.2. T1: распределение по каналам QUIC

- Управление — **единственный** двунаправленный поток, открытый клиентом (stream ID 0), поток TLV-сообщений. Сервер:
  `max_concurrent_bidi_streams = 1`, `max_concurrent_uni_streams = 0`; клиент: оба 0. Попытку открыть иной поток QUIC
  отвергает сама (STREAM_LIMIT_ERROR). Окно потока — 16 КиБ ⟂. Закрытие потока 0 любой стороной — закрытие соединения.
- Данные — DATAGRAM: `Context (i)` + содержимое (D §5.1 рекомендует такой префикс). Контекст 0 — IP-пакет; контекст 1
  — SizeProbe (§4.3); иные — молча отбросить со счётчиком (ненадёжный канал, закрывать нельзя: датаграмма не
  повторяется).
- Длина IP-пакета MUST быть 20…MTU_TUN и совпадать с полем длины IP-заголовка, иначе пакет отбрасывается со счётчиком
  — это ошибка пересылки, а не нарушение протокола (I §7.2).
- Буфер отправки датаграмм MUST быть уменьшен с 1 МиБ (§2.1 п. 5) до порядка BDP: старт 64 КиБ ⟂ (I §10: не
  увеличивать пачечность очередями).

### 5.3. T2: кадры поверх TLS 1.3/TCP

Поток после рукопожатия — последовательность TLV. Тип `0x00` — IP-пакет (по образцу DATAGRAM-капсулы H §3.5);
управляющие типы — те же, что в T1. SizeProbe в T2 не используется.

- Конец потока без `close_notify` и обрыв посреди кадра — ошибка (C-15). Записи TLS не выравниваются по кадрам.
- **Очередь.** Отправитель держит две очереди: управление (приоритет) и пакеты (ограниченная, отбрасывает голову при
  переполнении; старт 64 КиБ ⟂). Буфер сокета уменьшается, чтобы очередь жила в приложении, а не в ядре
  (`TCP_NOTSENT_LOWAT` — **[Не проверено]**). Даже так `Ping` T2 стоит за байтами в TCP: RTT по `Pong` — только
  диагностика, не основание для переключения (S-15, RR16).

### 5.4. Управляющие сообщения

| Тип | Имя | Направление | Значение | Правила |
|---|---|---|---|---|
| 0x01 | `Hello` | К→С | `version` (i), `caps` (i, битовая маска) | Первое сообщение клиента, ровно одно, в течение `T_HELLO` = 5 с ⟂ после рукопожатия |
| 0x02 | `Config` | С→К | `v4` (1 байт флаг, 4 байта адрес, 1 байт префикс), `v6` (флаг, 16, 1), `mtu` (2), `dns_count` (1, ≤ 4), адреса DNS (4 или 16 с байтом семейства), `keepalive_ms` (i), `lifetime_s` (i), `caps` (i) | Ровно одно, сразу после `Hello`; повтор — `PROTOCOL_ERROR`; ограничения ARCH §9 |
| 0x03 | `Activate` | К→С | `seq` (8) | Только после `Config`; не чаще лимита (§5.5) |
| 0x04 | `Activated` | С→К | `seq` (8) | Ответ на принятый `Activate`, после переключения маршрута |
| 0x05 | `ActivateRejected` | С→К | `seq` (8), `min_next_seq` (8) | `seq` не больше сохранённого; клиент ставит счётчик = `min_next_seq` и повторяет |
| 0x06 | `Superseded` | С→К | `seq` (8) нового активного | Прежнему активному соединению |
| 0x07 | `Ping` | обе | `id` (8) | Не более 4 без ответа; сервер отвечает не чаще 4/с ⟂, лишние игнорирует |
| 0x08 | `Pong` | обе | `id` (8) | Неизвестный `id` — игнорировать со счётчиком |
| 0x09 | `GoAway` | С→К | `seconds` (i, ≤ 3600) | Сервер скоро закроет соединение (срок жизни, остановка); клиент начинает плановую замену (§8.2) |
| 0x0A | `Close` | обе | `code` (i) | Последнее сообщение; в T1 код дублируется в CONNECTION_CLOSE приложения |

Числовые поля `Config` проверяются: `mtu` = MTU_TUN; `keepalive_ms` в 5000…60000; `lifetime_s` в 600…7200; адреса — из
диапазонов, разрешённых подписанной конфигурацией. Строк в сообщениях нет: это исключает журналирование текста от
пира.

**Версия.** ALPN `phantom/1` — главный признак версии: он защищён рукопожатием. `Hello.version` MUST равняться 1 при
ALPN `phantom/1`, расхождение — `VERSION_MISMATCH`. Необязательные возможности — пересечение `caps`.

**Порядок на сервере.** Клиент аутентифицирован (ARCH §3.1, шаг 5) → ждать `Hello` `T_HELLO` → `Config` → соединение
«кандидат». Пакеты от кандидата отбрасываются со счётчиком; отдельный признак «пробного» соединения не нужен — им
является отсутствие `Activate` (S-15). `Activate` переводит соединение в «активное». Любое сообщение не по порядку —
`PROTOCOL_ERROR`.

**Порядок на клиенте.** Пакеты в соединение до `Activated` не отправляются; полученные по неактивному соединению
отбрасываются, кроме окна стока 2 с ⟂ после `Activated` нового (§8.2).

### 5.5. Активация

- Сервер хранит для ключа последний принятый `seq` (ARCH §4). `seq` ≤ сохранённого → `ActivateRejected`. Это закрытое
  TLS сообщение собственного клиента, поэтому раскрытие `min_next_seq` ничего не даёт постороннему. **[Вывод]**
- Лимит: не более 6 активаций на ключ в минуту ⟂. Превышение **задерживает** ответ `Activated` до освобождения квоты,
  но не отвергает (ARCH §4).
- Сервер сначала переключает маршрут, затем шлёт `Superseded` прежнему и `Activated` новому, затем закрывает прежнее
  через 2 с ⟂ с `SUPERSEDED`.

### 5.6. Коды `Close`

| Код | Имя | Действие клиента |
|---|---|---|
| 0 | `NO_ERROR` | Плановое закрытие |
| 1 | `PROTOCOL_ERROR` | Ошибка реализации: `Halted(Protocol)` после 3 повторов за 10 мин |
| 2 | `VERSION_MISMATCH` | `Halted(Version)` |
| 3 | `CONFIG_MISMATCH` | `Halted(Config)` |
| 4 | `KEY_REVOKED` | `Halted(Auth)`, не повторять |
| 5 | `SUPERSEDED` | Нормально, если клиент сам активировал другое; иначе — признак второго устройства с тем же ключом (ARCH §4), диагностика |
| 6 | `LIFETIME_EXPIRED` | Плановая замена не успела: `Reconnecting` |
| 7 | `SERVER_SHUTDOWN` | `Reconnecting` |
| 8 | `RESOURCE_LIMIT` | `Reconnecting` с backoff; не наблюдение о сети |
| 9 | `HELLO_TIMEOUT` | Как 1 |
| 10 | `MTU_UNUSABLE` | F3 (§7.3) |

`PROTOCOL_ERROR`, `VERSION_MISMATCH`, `CONFIG_MISMATCH`, `KEY_REVOKED` не учитываются в памяти по сети.

### 5.7. Рукопожатие TLS в T1: HRR, Retry, размер (C-13)

- Сервер MUST NOT отправлять HRR (одна группа у обеих сторон). Клиент отвергает HRR с предложенной группой и без
  изменений; HRR только с cookie принимает — группа та же, понижения нет, лишний RTT (§2.1 п. 14). **[Вывод]**
- ClientHello с долей 1216 байт (K §4.1) занимает не меньше двух Initial по REQ_UDP. Память на сборку ClientHello
  входит в лимит рукопожатий (S-12).
- Retry (`retry()` для `Incoming` без проверенного адреса): одновременных рукопожатий > 64 ⟂ или > 8/с ⟂ с одного /24
  (IPv4) или /64 (IPv6). После Retry ClientHello повторяется с токеном (Q §8.1.2).
- Анти-усиление: два Initial по 1319 байт разрешают серверу 7914 байт до проверки адреса (Q §8.1); первый полёт
  сервера (ServerHello с долей 1120 байт — K §4.2, сертификат Ed25519, CertificateRequest, CertificateVerify,
  Finished) — оценочно 2–3 КБ **[Предположение]**.

## 6. Keepalive, idle timeout, время жизни соединения

- **T1.** `max_idle_timeout` = 30 с ⟂ на обеих сторонах (эффективное — минимум двух, ≥ 3 PTO, Q §10.1). За keepalive
  отвечает **клиент** (A §3.2 требует назначить сторону): `keep_alive_interval` = 15 с ⟂ — нижняя граница RFC 8085 по
  цитате в A, меньше ориентира NAT 30 с. Сервер keepalive не шлёт: нового адреса клиента он не знает, пока клиент не
  отправит пакет (Q §9). `Ping` на потоке управления — раз в 60 с ⟂, проверка живости процесса сервера.
- **T2.** Клиент шлёт `Ping` после 15 с ⟂ без отправленных кадров; сервер закрывает соединение без входящих байтов 60
  с ⟂. TCP keepalive ядра — резерв (интервал **[Не проверено]**).
- **Потеря связи.** «Подозрение»: за `T_SUSPECT` = 2 с ⟂ клиент отправлял пакеты, но ничего не получил (T1: датаграммы
  или данные потока; T2: байты). Тогда T1 шлёт SizeProbe SMALL, T2 — `Ping`, раз в 1 с до 3 раз; любой ответ снимает
  подозрение, иначе «соединение потеряно» (§7). Обнаружение около 5 с ⟂; idle timeout — последний рубеж. Потери
  отдельных датаграмм основанием не служат.
- **Срок жизни.** 3600 с ⟂ плюс равномерный разброс 0…600 с ⟂ на каждое соединение (S-20); клиент начинает замену
  (§8.2) за 120 с ⟂ до конца. Сервер закрывает по `lifetime_s` из `Config` + 900 с ⟂ (`LIFETIME_EXPIRED`), не
  полагаясь на клиента (ARCH §4), и за 300 с до этого шлёт `GoAway`. Обновление ключей — C-07 (этап 5).

## 7. Автомат клиента (S-13)

### 7.1. Состояния

Kill switch (ARCH §6.2): `off` только в `Disconnected`; во всех остальных — `enforcing`.

| Состояние | Трафик пользователя | Смысл |
|---|---|---|
| `Disconnected` | обычная сеть, `off` | Исходное; только по команде |
| `WaitNetwork` | запрещён | Нет маршрута по умолчанию или нет адреса на физических интерфейсах |
| `Connecting` | запрещён | Гонка транспортов по списку адресов (§8.1) |
| `Connected(T)` | через туннель | Есть соединение с `Activated`; T ∈ {T1, T2} |
| `Suspect(T)` | через туннель | Подозрение потери связи (§6, «Потеря связи»), идут пробы |
| `Switching(T→T')` | через туннель (старое) | Новое соединение поднимается; старое активно до `Activated` |
| `Reconnecting` | запрещён (пакеты отбрасываются) | Активное соединение потеряно; попытки с backoff |
| `Blocked` | запрещён | Три круга по всем адресам и транспортам без успеха; редкие попытки |
| `Halted(R)` | запрещён | Неустранимое без человека: R ∈ {Auth, Pin, Version, Config, Protocol, Portal} |

### 7.2. Переходы

| Из | Событие | В | Примечание |
|---|---|---|---|
| `Disconnected` | команда `connect` | `WaitNetwork` или `Connecting` | Включается `enforcing` |
| любое, кроме `Disconnected` | команда `disconnect` | `Disconnected` | Единственный путь к `off` |
| любое активное | сеть пропала | `WaitNetwork` | Соединения закрываются без учёта в памяти |
| `WaitNetwork` | сеть появилась | `Connecting` | Ключ сети вычисляется заново (§7.5) |
| `Connecting` | первое аутентифицированное соединение + `Config` + (для T1) SizeProbe + `Activated` | `Connected(T)` | Проигравшие закрываются без `Activate` |
| `Connecting` | исчерпан круг адресов (§8.1) | `Reconnecting` | Круг = 1 |
| `Connecting`, `Reconnecting`, `Blocked` | ошибка закрепления ключа сервера | `Halted(Pin)` | Не наблюдение о транспорте; не учитывается в памяти |
| любое с соединением | `Close` с кодом 2, 3, 4 или 1 ×3 | `Halted(...)` | §5.6 |
| `Connected(T)` / `Suspect(T)` | подозрение (§6) / ответ на пробу | `Suspect(T)` / `Connected(T)` | |
| `Suspect(T)` | нет ответа на 3 пробы | `Reconnecting` | Наблюдение F4, если в этом круге T' к тому же серверу успешен |
| `Connected(T1)` | смена локального адреса | `Connected(T1)` | rebind + SizeProbe + проба живости; провал за 3 с ⟂ → `Switching` к новому соединению |
| `Connected(T2)` | смена локального адреса | `Switching(T2→?)` | TCP не переживает смену адреса; гонка заново |
| `Connected(T2)` | серия успешных фоновых проб T1 (§7.6) | `Switching(T2→T1)` | |
| `Connected(T)` | `GoAway`, срок жизни (§6, «Срок жизни») | `Switching(T→T*)` | T* выбирается гонкой с учётом памяти |
| `Switching` | `Activated` нового | `Connected(T')` | Старое закрывается после стока 2 с |
| `Switching` | новое не поднялось, старое живо | `Connected(T)` | Повтор через backoff; плановая замена — до истечения срока |
| `Switching` | новое не поднялось, старое потеряно или истекло | `Reconnecting` | Отмечено в S-13 |
| `Reconnecting` | успех / 3 круга без успеха | `Connected(T)` / `Blocked` | |
| `Blocked` | таймер backoff, смена сети, пробуждение, команда | `Connecting` | Никогда не переходит в `Disconnected` сам |
| `Halted(R)` | команда `connect` или смена сети (для Pin — одна попытка на сеть) | `Connecting` | Пользователь видит наблюдение |

Backoff в `Reconnecting`: 1, 2, 4, 8, 16, 32, 60 с ⟂ с разбросом ±20 %; в `Blocked` — удвоение до 300 с ⟂.

### 7.3. Наблюдения «T1 не работает» и память

Наблюдения о T1 в сети N (каждое — одно событие):

- **F1.** Попытка T1 к адресу A не получила ни одного пакета, прошедшего защиту Initial, за `T1_HS_MAX` = 6 с ⟂, **и**
  в том же круге T2 к A аутентифицирован.
- **F2.** От сервера пришли пакеты, но рукопожатие T1 не завершилось за `T1_HS_MAX`, и T2 к A аутентифицирован.
- **F3.** SizeProbe BIG не прошёл при прошедшем SMALL (§4.3), отсутствие DATAGRAM или нарушение M2.
- **F4.** Установленное T1 потеряно (§6, «Потеря связи»), а T2 к тому же адресу аутентифицирован не позже 10 с ⟂
  спустя.

Не являются наблюдениями: ошибки аутентификации и закрепления, коды §5.6 из списка исключений, отказ обоих транспортов
(это отказ сервера или сети целиком), события в первые 10 с ⟂ после пробуждения или смены сети, `RESOURCE_LIMIT`.

Правила:

1. **Одно наблюдение** переводит текущий сеанс на T2 (доступность важнее), но **не меняет память**. Так снимается
   противоречие п. 3 и п. 7 ARCH §7.1.
2. **Память** «T1 непригоден в N» ставится при двух наблюдениях за 10 мин ⟂. Срок метки: 5 мин, удвоение при каждой
   следующей метке подряд, потолок **60 мин** ⟂. Первый успех T1 в N сбрасывает уровень удвоения.
3. Пока метка действует, T1 не участвует в стартовой гонке. По истечении метки — одна фоновая проба T1 (рукопожатие,
   SizeProbe, без `Activate`). Потолок 60 мин гарантирует, что проба T1 происходит хотя бы раз в час: запирания
   навсегда нет.
4. Фора T1 в гонке (п. 2 ARCH §7.1 — подделываемый признак) **не задерживает T2**: T2 стартует через D (§8.1) всегда;
   полученный пакет QUIC лишь продлевает попытку T1 до `T1_HS_MAX`. Побеждает первое соединение, прошедшее
   аутентификацию и (для T1) SizeProbe.

### 7.4. Сон и пробуждение

- Признак пробуждения: скачок разницы `CLOCK_BOOTTIME − CLOCK_MONOTONIC` больше 5 с ⟂ или сигнал системы (logind
  `PrepareForSleep`, **[Не проверено]** в стенде, S-19).
- После пробуждения: активное соединение считается подозрительным; одна проба живости (2 с ⟂) и SizeProbe. Успех —
  `Connected`; неуспех — `Reconnecting` с немедленной гонкой, без учёта в памяти. Срок жизни соединения считается по
  `CLOCK_BOOTTIME`: проспавшее срок соединение не используется.
- Kill switch на время сна не снимается.

### 7.5. Ключ сети и что хранится

- Ключ N = HMAC-SHA-256 с локальным случайным секретом от (имя физического интерфейса, IP и MAC шлюза по умолчанию).
  Совпадение шлюзов у разных сетей даёт общую запись — ошибка в сторону лишней пробы. **[Вывод]**
- Запись: метка T1 (срок, уровень удвоения), сглаженный RTT (для D), последний работавший адрес, наблюдения за 10 мин.
  До 32 записей, вытеснение по давности, удаление через 24 ч ⟂. По умолчанию только в оперативной памяти — история
  перемещений не пишется на диск (S-13); запись на диск — опция, файл 0600. Метка действует только в своей сети.

### 7.6. Возврат на T1 и анти-flapping

- С T2 на T1: минимум 60 с ⟂ на T2 и **две** успешные фоновые пробы T1 подряд с интервалом не меньше 30 с ⟂; затем
  `Switching` по схеме «сначала новое».
- Бюджет переключений: не более 4 смен транспорта за 10 мин ⟂. При превышении клиент **замораживает** текущий
  работающий транспорт на 10 мин ⟂ (ограничено временем, а не «до смены сети»). Заморозка не мешает уйти с транспорта,
  который перестал работать: потеря соединения всегда ведёт в `Reconnecting` с гонкой обоих транспортов. Так атакующий
  не запирает клиента на неработающем T2 (S-13 п. 6).
- Остаток: атакующий, блокирующий UDP раз в 60 мин, держит клиента на T2 большую часть времени. На T2 теряются
  миграция (G16) и устойчивость к поддельному RST — это потеря доступности, а не только производительности; RR5
  следует переформулировать.

### 7.7. Captive portal (связь с S-08)

Исключений в firewall автомат не открывает. «TCP 443 соединяется, но вместо ServerHello приходит иное» →
`Halted(Portal)`, несовпадение ключа → `Halted(Pin)`, оба с подсказкой. Механизм прохода портала — решение S-08.

## 8. Адреса сервера и плановое пересоединение

### 8.1. Список адресов и порядок перебора

- Конфигурация задаёт упорядоченный список до 8 ⟂ адресов сервера (IPv4 и IPv6), для каждого — UDP-порт T1 и TCP-порт
  T2 (по умолчанию 443/443). Отпечаток ключа общий.
- Порядок: последний работавший адрес в этой сети (§7.5), затем список по порядку с чередованием семейств, начиная с
  IPv6 (First Address Family Count = 1 — значение из E §8; сам раздел E §4 о сортировке не читался).
- На каждом адресе — гонка: T1 сразу (если не помечен), T2 через D. D = 250 мс без истории; с историей —
  `clamp(2·srtt, 100 мс, 2 с)` (E §5; ARCH говорил 3 с — снижено до максимума E §8).
- Следующий адрес стартует, когда текущий за 2 с ⟂ не дал ни одного ответа ни по одному транспорту, или сразу после
  явного отказа (RST, ICMP unreachable от ядра) на обоих. Не больше 4 ⟂ одновременных попыток. Первая успешная попытка
  отменяет остальные (E §5).
- Круг исчерпан, когда все адреса провалились (тайм-аут `T1_HS_MAX` и тайм-аут TCP+TLS 8 с ⟂).
- Запасные адреса не проверяются, пока работает основной (ARCH §7.1 п. 8). Если клиент работает на запасном, раз в 10
  мин ⟂ фоновая проба первого адреса списка; переход — по схеме «сначала новое».

### 8.2. «Сначала новое, потом закрыть старое»

Для плановой замены (§6, `GoAway`), возврата на T1, смены адреса и перехода с запасного адреса.

1. Поднять новое соединение (гонка §8.1 с учётом памяти), аутентификация, `Hello`, `Config`.
2. `Config` MUST совпасть с текущим (адреса, MTU, DNS); иначе `Close(CONFIG_MISMATCH)` нового, старое работает.
3. Для T1 — SizeProbe; затем `Activate{seq+1}`. До `Activated` пакеты идут по старому.
4. После `Activated` — по новому; принятое по старому ещё 2 с ⟂ доставляется; сервер шлёт старому `Superseded` и
   `Close(SUPERSEDED)`.
5. Неуспех — повтор через 5, 10, 20 с ⟂, пока старое живо; если старое истекло или потеряно — `Reconnecting` (S-13).
   Два соединения в окне замены видны наблюдателю (TM §5); утечки нет.

## 10. Не проверено и открытые вопросы

1. `quinn-udp` прочитан в версии 0.6.3 на docs.rs, а не из локального реестра; не-Linux не рассматривался. Поведение
   DPLPMTUD `quinn` при `min_mtu = initial_mtu = 1319` выведено из кода `mtud.rs`, не запускалось.
2. Нетипичность размера Initial 1319 для наблюдателя; поддельный PTB для TCP в Linux; `TCP_NOTSENT_LOWAT`; TCP
   keepalive — не проверены.
3. RFC 8305 §4, RFC 6455, RFC 8085, RFC 4787 не читались; ссылки на них — через цитаты в прочитанных RFC.
4. Числа «⟂» не измерены; особенно `T_SUSPECT`, `T1_HS_MAX`, потолок памяти 60 мин, бюджет переключений. Ключ сети по
   шлюзу и MAC — эвристика.
5. Captive portal (S-08), фильтр назначения (S-11), лимиты (S-12) здесь не решаются; автомат и коды `Close` оставляют
   им место.
6. Требуют правки (делает lead): ARCH §5.2 («отбрасывается с ICMP» → M5), §5.4 (→ §5.4 здесь), §6.1 (REQ_UDP 1319
   вместо «около 1310»), §7 (→ §7 здесь); RR5 модели угроз (§7.6).
