# PROJECT PHANTOM — документ передачи на реализацию

**Дата:** 2026-11-14. **Кому:** разработчику, который начинает реализацию
(Claude Opus 5.5, режим High effort), и владельцу проекта.
**Состояние проекта:** исследование, архитектура и спецификация готовы как
документы. **Кода нет. Ни одна гарантия тестами не подтверждена.**
**Реализацию начинать только после отдельного разрешения владельца.**

Этот файл самодостаточен как карта: он говорит, что строим, почему так, в
каком порядке и чем проверяем. Полные нормативные правила лежат в детальных
документах; здесь на них стоят точные ссылки. При расхождении действует
порядок приоритета из раздела 2.

## 1. Что мы создаём

Приватный туннель уровня L3 «свой клиент — свой сервер»: IP-пакеты клиента
идут через зашифрованное соединение к серверу владельца и выходят в интернет с
его адреса.

Цели в порядке приоритета:

1. Конфиденциальность, целостность и взаимная аутентификация канала,
   включая защиту записанного сегодня трафика от будущего квантового
   противника.
2. Отсутствие утечек мимо туннеля: DNS, IPv6, пересылаемый трафик, моменты
   сбоя и загрузки.
3. Устойчивая связь при смене сети, потерях, недоступности UDP и отказе
   отдельного сервера или адреса.
4. Производительность — измеряемая и сравниваемая с WireGuard на одном стенде.
5. Единое сетевое ядро, пригодное для клиентов на Linux, Windows, Android,
   macOS и iOS.

Чего проект **не** обещает и что запрещено заявлять в коде, документации и
сообщениях пользователю:

- необнаружимость, «неотличимость от HTTPS», невозможность блокировки;
- работу при блокировке адреса сервера, при «белых списках» и отключении сети;
- анонимность: одноузловой туннель её не даёт;
- защиту от оператора сервера, хостинг-провайдера и скомпрометированного
  устройства.

Запреты проекта (`docs/threat-model/THREAT_MODEL.md`, «Запреты»): не выдавать
сервер за сторонний сервис, не использовать чужую инфраструктуру, не
вмешиваться в чужой трафик, не применять congestion control без реакции на
потери, не собирать телеметрию по умолчанию, не писать собственную криптографию.

Устойчивость к сетевой фильтрации рассматривается как задача надёжности: проект
убирает дешёвые отличительные признаки, даёт запасные транспорт и адреса и
**измеряет** собственные наблюдаемые характеристики. Анализ причин потери
доступности — `docs/research/08-availability-loss-causes.md`.

## 3. Архитектура в одном разделе

```
 приложения -> ядро ОС: TUN + nftables (владелец таблиц: phantom-guard)
                              |
                       phantom-netd (без привилегий)
          сеанс и автомат | T1: QUIC DATAGRAM | T2: TLS 1.3 / TCP 443
                              |  TLS 1.3, X25519MLKEM768, RPK Ed25519
                         phantom-server -> NAT -> интернет
```

| Решение | Суть | ADR | Нормативный текст |
|---|---|---|---|
| Криптографический слой | Только TLS 1.3 из `rustls`; собственного рукопожатия и прямых вызовов AEAD/KDF нет | 0003 | CRYPTO_PROFILE §2.1, §2.8 |
| Обмен ключами | Единственная группа `X25519MLKEM768` (RFC 10024); 0-RTT и resumption выключены | 0004 | CRYPTO_PROFILE §4, CP-03, CP-06…10 |
| Идентичность | Raw public keys (RFC 7250), Ed25519, с обеих сторон; отпечаток `ed25519-spki-sha256:<64 hex>` | 0013 | CRYPTO_PROFILE §3.4, CP-15, CP-16 |
| Транспорт T1 | QUIC (`quinn`): IP-пакет в DATAGRAM с байтом контекста; один поток для управления; CUBIC | 0006 | TRANSPORT §5.2 |
| Транспорт T2 | TLS 1.3 поверх TCP 443; те же сообщения в формате «тип, длина, значение» | 0006 | TRANSPORT §5.3 |
| Сеанс | «Ключ клиента → внутренний адрес»; маршрут переносится только по `Activate{seq}` | 0007 | TRANSPORT §5.4, §5.5 |
| MTU | TUN 1280; для T1 `min_mtu = initial_mtu = 1319`; собственная проба размера | 0010 | TRANSPORT §4 |
| Выбор транспорта | Гонка T1 и T2 с форой; память «T1 не работает» по сети; защита от частых переключений | 0009 | TRANSPORT §7 |
| Kill switch | Сторож `phantom-guard` владеет таблицами nftables; запрет по умолчанию в output, forward, input | 0014 | SYSTEM §1, §4 |
| Привилегии | Сторож с привилегиями без разбора сети; демон туннеля без привилегий | 0014 | SYSTEM §2, §3 (S-07) |
| Конфигурация | Подписанный конверт: версия, срок, адресат, минимальная версия; автоматического отката нет | — | SYSTEM §1.8 |
| Клиенты | Собственный клиент на едином ядре; INCY и Happ — только через будущий T3 | 0015 | CLIENT_COMPATIBILITY §8 |

### Почему TLS 1.3, а не собственный протокол на Noise

Альтернативы сравнивались дважды, разными исполнителями
(`docs/research/07-comparative-report.md` §4; CRYPTO_PROFILE §2.8; TRANSPORT §3).

| Критерий | TLS 1.3 + QUIC/TCP (выбрано) | Протокол на Noise по образцу WireGuard | WireGuard как есть (+Rosenpass) | HTTP/3 + CONNECT-IP сразу |
|---|---|---|---|---|
| Своя криптографическая обвязка | Нет | Да: защита от повторов, обновление ключей, версии, режим TCP | Нет | Нет |
| Post-quantum | Стандарт RFC 10024, реализовано в библиотеке | Стандарта нет | Отдельный протокол доставки ключа | Как у TLS |
| Запасной транспорт TCP | Штатный | Проектировать самим | Нет | HTTP/2 |
| Формальный анализ | Есть для TLS 1.3; не покрывает гибридную группу, QUIC и слой сеанса | Только для WireGuard без изменений | Есть | Как у TLS |
| Объём доверенного кода | Большой, включая C и ассемблер (AWS-LC) | Малый | Малый | Наибольший |
| Производительность | Ожидается ниже WireGuard; не измерено | Ожидается выше | Эталон | Ожидается ниже |
| Зрелость библиотек Rust | `rustls`, `quinn` зрелые; аудит `quinn` не найден | `snow` — один аудит | Зрелые | `h3` экспериментален |

Выбор сделан из-за требования не писать собственную криптографию и из-за
готового пути к post-quantum. Цена принята осознанно и записана как остаточные
риски (раздел 11).

## 4. Обязательные требования

Нарушение любого пункта — дефект, блокирующий слияние.

### 4.1. Криптография (CRYPTO_PROFILE §4, параметры CP-01…CP-30)

- Конфигурацию TLS собирает **одна** функция для обоих транспортов;
  `install_default` не используется.
- `rustls` подключается с `default-features = false` и явным списком features;
  feature `tls12` выключена; CI проверяет дерево features.
- Провайдер содержит ровно одну группу и одну схему подписи (Ed25519).
- Suite `TLS13_AES_128_GCM_SHA256` остаётся в провайдере: без него `quinn` не
  создаёт конфигурацию.
- После рукопожатия обе стороны явно проверяют версию, группу, ALPN и
  идентичность пира (CP-13). В T2 сервер фильтрует ClientHello до тяжёлых
  операций (CP-12).
- `Connecting::into_0rtt()` в `quinn` запрещён; сервер не шлёт данных до
  `Finished` клиента (CP-14).
- Собственный verifier обязан вызывать проверку подписи рукопожатия
  библиотекой. Тест «верный ключ в сертификате, чужой приватный ключ» —
  обязательный, в обе стороны (CP-16, T-RPK4).
- Обновление ключей по таймеру и срок жизни соединения исполняет и клиент, и
  сервер (CP-20, CP-21; значения стартовые).
- Секреты не экспортируются и не попадают в журналы; объекты `rustls` не
  выводятся через `Debug` (CP-22, CP-28).
- Нижние границы версий: `rustls` ≥ 0.23.46, `rustls-webpki` ≥ 0.103.16,
  `quinn-proto` ≥ 0.11.18, `aws-lc-sys` ≥ 0.39, `tokio` ≥ 1.53.3.

### 4.2. Протокол (TRANSPORT §5)

- Формат сообщения: `Type (varint), Length (varint), Value`. Varint — только
  кратчайшая кодировка; длина проверяется до чтения значения; лишние байты —
  ошибка (правила L1–L5).
- Типы `0x00–0x3F` обязательные: неизвестный — закрытие. Типы `0x40` и выше
  пропускаются.
- Сообщения: `Hello`, `Config`, `Activate`, `Activated`, `ActivateRejected`,
  `Superseded`, `Ping`, `Pong`, `GoAway`, `Close` (таблица §5.4). Строк в
  сообщениях нет.
- Сервер: аутентификация → `Hello` в пределах тайм-аута → `Config` →
  соединение-кандидат. Пакеты кандидата отбрасываются. Маршрут переносится
  только по `Activate`. Сообщение не по порядку — закрытие.
- Клиент не отправляет пакеты до `Activated`.
- `Config` не может ослабить локальную политику: значения проверяются по
  диапазонам подписанной конфигурации.
- Адрес источника пакета из туннеля должен принадлежать ключу соединения;
  сервер фильтрует и назначение (SYSTEM §3, S-11).

### 4.3. Сеть и утечки (SYSTEM §1, §3, §4, §5)

- Kill switch имеет два состояния: `off` и `enforcing`. `off` — только после
  явной команды отключения. Режима «разрешить, если туннель упал» нет.
- Правила покрывают output, forward и input; IPv6 либо в туннеле, либо
  запрещён; DNS — только через туннель.
- Правила формирует и применяет только сторож; значения из сети попадают к
  нему как типизированные данные, никогда как текст команд. Командная
  оболочка не используется.
- Падение демона туннеля не меняет правил.
- Доступ к локальной сети по умолчанию закрыт.

### 4.4. Код

- В разборе недоверенного ввода запрещены `unwrap`, `expect`, `panic!`,
  индексация без проверки и `unsafe`; lint-правила — TEST_STRATEGY §1.8.
- Каждый разборщик недоверенного ввода имеет fuzz-цель (13 целей,
  TEST_STRATEGY §1.5).
- Типы секретов не реализуют `Debug` и `Display`.
- Зависимость добавляется только с обоснованием; `cargo-deny` и `cargo-audit`
  в CI; версии закреплены в `Cargo.lock`.
- Сообщения пользователю описывают наблюдения, а не причины; слово
  «заблокировано» не используется (TRANSPORT §7; исследование 08 §3).

## 6. Клиент-серверное взаимодействие

1. Клиент запускает гонку: T1 сразу, T2 с форой (TRANSPORT §7, §8.1).
2. Рукопожатие TLS 1.3: `X25519MLKEM768`, RPK обеих сторон, ALPN `phantom/1`.
   Клиент раскрывает свой ключ только после проверки сервера (гарантия G17).
3. Проверки после рукопожатия на обеих сторонах (CP-13).
4. `Hello` → `Config`. Соединение — кандидат.
5. Для T1 — проба размера в обе стороны (TRANSPORT §4.3).
6. Клиент выбирает соединение и шлёт `Activate{seq}`; сервер переключает
   маршрут, отвечает `Activated`, прежнему соединению — `Superseded`.
7. Данные: IP-пакеты в DATAGRAM (T1) или в кадрах (T2).
8. Keepalive, обнаружение потери связи, обновление ключей по таймеру
   (TRANSPORT §6; CP-20).
9. Плановая замена соединения до истечения срока жизни: сначала новое,
   `Activate`, затем закрытие старого (TRANSPORT §8.2).
10. Потеря связи: пробы → другой транспорт → следующий адрес сервера → редкие
    попытки. Kill switch всё это время в `enforcing`.

## 7. Ключи и сеансы

| Ключ | Назначение | Хранение | Ротация |
|---|---|---|---|
| Идентичность сервера (Ed25519) | Аутентификация в TLS | Файл 0600, в systemd — `LoadCredential` | Вручную; клиент хранит набор допустимых отпечатков на время перехода |
| Идентичность клиента (Ed25519) | Аутентификация в TLS | То же | Вручную; отзыв — удаление отпечатка, сервер сразу рвёт соединения ключа |
| Подпись конфигураций (Ed25519) | Обновления конфигурации | Вне сервера | Смена якоря — SYSTEM §1.8 |
| Сеансовые ключи TLS | Канал | Только внутри библиотеки | Автоматически у лимита; по таймеру; новое соединение по сроку жизни |

Роли ключей не совмещаются (CRYPTO_PROFILE §3.10). Счётчик `seq` клиент хранит
на диске; при потере или откате сервер отвечает `ActivateRejected` с
`min_next_seq`. Один ключ — одно устройство.

## 8. Резервирование и восстановление

- Два транспорта разной природы; T2 — режим совместимости с известной
  деградацией (TCP поверх TCP).
- Список адресов сервера; запасные не используются и не проверяются, пока
  основной работает (TRANSPORT §8.1).
- Требования к серверной инфраструктуре R-1…R-8 — исследование 08 §6: адреса в
  разных сетях, общий набор ключей клиентов, независимые ключи серверов,
  процедура замены адреса через подписанную конфигурацию.
- Блокировку адреса и отключение сети проект не устраняет: единственное
  средство — запасной адрес и быстрая доставка новой конфигурации.
- Диагностика — дерево из восьми уровней (исследование 08 §3). Счётчики
  собственного сервера используются как вторая точка измерения.

## 9. Тесты и критерии готовности

Стратегия — `docs/testing/TEST_STRATEGY.md`: 133 тест-кейса с прослеживаемостью
к гарантиям и замечаниям (§2), стенды (§3), устойчивость (§4),
производительность (§5), снимки наблюдаемых характеристик (§6), CI (§7), аудит (§8).

| Стенд | Что проверяется |
|---|---|
| A — контейнер разработки | Unit, property, integration, сквозные в network namespaces, fuzz, утечки с положительным контролем |
| B — виртуальная машина с systemd | Порядок загрузки, сторож и таблица с владельцем, firewalld и Docker, systemd-resolved |
| C — физический стенд | Производительность, сравнение с WireGuard, нагрузка |
| D — реальные сети и устройства | Сон и пробуждение, смена сети, мобильные сети |

Правила:

- Отрицательный тест утечки без прошедшего положительного контроля считается
  **не пройденным**.
- Числовых целей производительности нет: значения измеряются, пороги
  утверждает владелец (TEST_STRATEGY §9).
- Матрица тестов написана по архитектуре v0.2 и до начала этапа I1 приводится
  к спецификации (RECONCILIATION, N-15).
- Гарантия считается подтверждённой только после прохождения её тест-кейсов;
  до этого в документах стоит «заявлена, не подтверждена».
- Замечание из `SECURITY_FINDINGS.md` переводится в `Verified` только после
  прохождения тестов и только не автором исправления.

Критерии «этап закрыт» — TEST_STRATEGY §7. Проект не называется
production-ready до внешнего аудита и закрытия его замечаний High и Critical.

## 10. План реализации

Каждый этап заканчивается зелёным CI, обновлением `PROJECT_STATUS.md` и
записью о проверке. Следующий этап не начинается при открытых High.

## 11. Известные ограничения и нерешённые вопросы

### 11.1. Не подтверждено практикой

| № | Что | Где описано | Если не подтвердится |
|---|---|---|---|
| 1 | RPK работает через `quinn` | CRYPTO_PROFILE §5 п. 1 | Самоподписанный сертификат с тем же отпечатком SPKI |
| 2 | Таблица nftables с `owner` и `persist` из собственного процесса; минимальные версии ядра и `nft` | SYSTEM §1.1 | Запасной режим со слежением; гарантия G8 сужается |
| 3 | Поведение `quinn` при `min_mtu = initial_mtu = 1319` | TRANSPORT §4, §10 | Пересмотр схемы MTU |
| 4 | Чтение согласованной группы в T1 | CRYPTO_PROFILE §5 п. 3 | Тест через `rustls::quic` без `quinn` |
| 5 | Проверка Ed25519 в AWS-LC при `S ≥ L` | CRYPTO_PROFILE §5 п. 6 | Тест; при отказе — замечание |
| 6 | Размер ClientHello и число пакетов Initial | CRYPTO_PROFILE §5 п. 2 | Влияет на оценку наблюдаемости и на Retry |
| 7 | Вся производительность и все числовые параметры (тайм-ауты, лимиты, сроки) | Помечены в спецификациях | Уточнение по измерениям |
| 8 | Совместимость сервера с outbound `masque` в Xray-core; наличие модуля в сборках INCY и Happ | CLIENT_COMPATIBILITY §4.4, §10 | Режим совместимости отменяется |

### 11.2. Остаточные риски, которые остаются при любой реализации

- Сервис обнаруживается: собственный ALPN, одна группа и одна схема подписи в
  ClientHello, нетипичный размер первых пакетов, регулярное пересоединение.
  Перечень признаков O1–O20 — исследование 08 §4. Как на них реагируют
  конкретные сети, проект не утверждает; это предмет измерений.
- Профиль с единственной гибридной группой увеличивает ClientHello сверх одного
  пакета; сети, которые плохо обрабатывают такие рукопожатия, сделают
  соединение недоступным.
- Блокировка адреса сервера и отключение сети не устраняются.
- Анализ размеров и времени пакетов не устраняется.
- Аутентификация остаётся классической (Ed25519).
- Аудит `rustls` относится к 2020 году; аудит `quinn` не найден; AWS-LC — код
  на C и ассемблере.
- Другое ПО с правами администратора может вмешаться в правила firewall; окно
  при загрузке системы до старта сторожа не исключается полностью.

Полный список — `docs/threat-model/THREAT_MODEL.md`, «Остаточные риски».

### 11.3. Состояние независимых проверок

| Что | Состояние |
|---|---|
| Выбор TLS 1.3, профиль, идентичность | Проверено двумя независимыми исполнителями по документам, RFC и исходникам |
| Транспорт, MTU, автомат клиента | Проверено и переработано независимым исполнителем; результат второй раз не проверялся |

## 13. Как начинать

1. Прочитать этот файл целиком, затем `RECONCILIATION.md` и три документа
   приоритета 1.
2. Прочитать `SECURITY_FINDINGS.md` и `docs/architecture/reviews/REVERIFY_HIGH.md`:
   там перечислены ошибки, которые уже были найдены в проекте.
3. Получить разрешение владельца и его ответы на вопросы раздела 11.4.
4. Выполнить этап I0 и записать результаты до написания основного кода.
5. Не закрывать замечания правкой документов: только тестом и только
   проверкой не автора.
6. При любом сомнении, меняющем гарантию, — остановиться и записать вопрос
   владельцу в `PROJECT_STATUS.md`.
